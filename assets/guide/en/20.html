Coding Agents: The Human Assigns the Task and Reviews the PR; the Agent Runs the Loop

Companion to diagram #20 · Chapter 3 "The Evolution of Programming"

A coding agent frees the developer from directing every line. The human describes the task; the agent reads code, edits files, runs commands, checks results, fixes mistakes and delivers a reviewable change. Claude Code's docs define it as an agentic coding tool that reads your codebase, edits files, runs commands and integrates with your development tools, available in the terminal, IDE, desktop app and browser. OpenAI's Codex CLI is a coding agent that runs in your local terminal, with a cloud version as well.

This article walks one concrete task from start to finish to show what happens at each step and why.

1. A real run

The task: "Users report that Chinese file names become garbled when exporting CSV. Please fix it."

Step 1: understand and locate. The agent has no ready-made map of the project, so it searches for clues:

$ grep -rn "Content-Disposition" src/
src/export/handler.py:48:    resp.headers["Content-Disposition"] = f"attachment; filename={name}"

One command finds the suspicious line. This reflects the design Anthropic describes: Claude Code puts files such as CLAUDE.md straight into context and uses primitives like glob and grep to explore the environment and retrieve files just in time, instead of relying on a pre-built index. That sidesteps stale indexes and complex syntax trees: if the code just changed, the search results are already current.

Step 2: hypothesise and plan. After reading the surrounding code, the agent concludes that the file name is not encoded in the RFC 5987 filename*=UTF-8''... form. Plan: fix the header and add a test.

Step 3: write a failing test first. It exports a file named "报表.csv" and asserts that the header carries the correctly encoded name, runs it, and confirms it fails. A test that has never failed proves nothing.

Step 4: edit and rerun. It changes line 48 and reruns. The new test passes, but an old test fails because it asserted the old header format.

Step 5: read the output and correct. The agent decides the old assertion encoded the wrong old behaviour, updates it, and says explicitly in its summary: "modified one existing test, because…".

Step 6: verify everything and deliver. Full test suite, type check and lint; once all pass it commits, opens a PR and describes the change.

Step 7: human review. Is the change sensible? Was that existing test modified correctly?

Compared with the previous article, the human appears only at the start (define the task) and the end (review). Locating, editing, verifying and correcting all happen inside the agent's loop.

2. Why does the loop work?

In the abstract:

understand the task → search and read code → plan
→ edit files → run build / tests / lint
→ read output → fix → … → all green
→ commit / open PR → human review

This is what Anthropic calls "LLMs using tools based on environmental feedback in a loop". Environmental feedback is the fundamental reason an agent can correct itself. A single generation may be wrong, but the compiler, tests and logs say where; the agent reads the concrete error, edits and verifies again. The failing old test in step 4 is the environment correcting the agent.

Conversely, with no tests, steps 4 and 5 lose their footing and the agent can only "feel" done. An agent's ceiling is largely set by the quality of the feedback it can get.

3. Managing context: subagents

On a large task an agent may read dozens of files and run many commands, and the output quickly fills the context. As Chapter 1 explained, the longer the context, the more easily information in the middle is overlooked.

One remedy is subagents. Each Claude Code subagent runs in its own context window with a custom system prompt, specific tool access and independent permissions. In plan mode, for instance, it delegates codebase research to a read-only Plan subagent, so bulky exploration output stays in a separate context and only conclusions return to the main session. Codex and Cursor also support subagents: spawn specialised agents in parallel and gather their results.

Think of a subagent as a function call: the main agent asks a clear question ("find every caller of the export API") and gets a short answer back, without carrying the whole search.

4. Permissions and sandboxes

If an agent can run commands, you must control what it can do:

Category Examples Policy
Read-only Read files, grep, run tests Allow automatically
Local and reversible Edit workspace files Allow automatically; Git can roll back
Side effects Install dependencies, network access Confirm or allow-list
Irreversible / high risk DB migrations, production, push, secrets Always require human confirmation

The sandbox limits writable directories and network access. The principle is to keep the cost of mistakes bounded, not to hope none are made.

5. What does the human do now?

A workflow shared by a developer on X is typical: hand PRDs and meeting notes to the agent and align on requirements through repeated questioning, capturing conclusions in a Spec or CONTEXT.md; split complex requirements into independently verifiable issues, giving only the independent parts to subagents working in parallel in separate worktrees; have the coding agent write tests first, then bring in other agents for cross-review; run end-to-end tests before human review, and keep every MR small.

The human's work concentrates on three things: stating the task clearly, providing executable verification, and reviewing the result. The rule file should state the stack, what is forbidden, and which operations require stopping to ask (DB migrations, production, secrets).

6. Pitfalls

  • "What the agent delivers can be merged directly." Agents over-engineer and declare victory when tests are thin. A modified existing test, as in step 5, is exactly what a reviewer should watch: it may be right, or the agent may have weakened a correct assertion to get green.
  • "More context is better." Part of the point of subagents is to keep the main session clean.
  • "Agents can replace tests." The opposite: the more autonomous the agent, the more it depends on automated tests.
