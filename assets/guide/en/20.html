Coding Agents: Humans Give Tasks and Review PRs; the Agent Runs the Loop

Companion to diagram #20 · Chapter 3 "The Evolution of Programming"

Overview

Coding agents free developers from line-by-line direction: the human describes a task, and the agent reads code, edits files, runs commands, checks results, fixes mistakes, and finally delivers a reviewable change. Claude Code's docs define it as an agentic coding tool that reads your codebase, edits files, runs commands and integrates with your development tools, available in the terminal, IDE, desktop app and browser. OpenAI's Codex CLI is a coding agent that runs locally in the terminal, with a cloud version as well.

Core Mechanisms

1. The loop. A typical task cycle:

Understand task → search and read code → plan
→ edit files → run build / tests / lint
→ read output → fix → … → all pass
→ commit / open PR → human review

This is exactly Anthropic's "LLM using tools based on environmental feedback in a loop". Environmental feedback (compile errors, failing tests, logs) is the fundamental reason agents can self-correct.

2. Just-in-time context retrieval. Anthropic explains that Claude Code drops files such as CLAUDE.md directly into context while using primitives like glob and grep to navigate the environment and retrieve files just in time, sidestepping stale indexes and complex syntax trees.

3. Subagents and context isolation. Each Claude Code subagent runs in its own context window with a custom system prompt, specific tool access and independent permissions. For example, in plan mode it delegates codebase research to a read-only Plan subagent so exploration output stays in a separate context. Codex and Cursor also support subagents: spawn specialized agents in parallel, then collect the results.

4. Permissions and sandboxing. If an agent can run commands, you must control what it can do: which commands are auto-allowed, which need confirmation, whether it can reach the network, which directories it can write.

Engineering Practice and Numbers

  • The human role shifts to defining tasks and reviewing results. A workflow one developer shared on X is typical: hand the agent PRDs, meeting notes and similar material first, align on requirements through repeated questioning, and capture conclusions in a Spec or CONTEXT.md; split complex requirements into independently acceptable issues, and only give genuinely independent parts to subagents developing in parallel in separate worktrees; the coding agent writes tests first, then other agents cross-review; run end-to-end tests before human review, and keep every MR small.
  • Give the agent executable verification: tests, type checks, lint, build. Without them, the agent can only rely on "it seems right".
  • Rules files should spell out the tech stack, prohibitions, and operations that require stopping to ask (e.g. database migrations, production, secrets).

Common Misconceptions

  • "What the agent delivers can be merged directly." Agents over-engineer and may declare completion when tests are insufficient; human review is still essential.
  • "More context is better." One point of subagents is precisely to isolate context and keep the main session clean.
  • "Agents can replace tests." Quite the opposite: the more autonomous the agent, the more it depends on automated tests.
