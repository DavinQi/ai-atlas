A 7-Day Roadmap: What an Individual or Small Team Can Start This Week

Companion to diagram #28 · Chapter 4 "AI Coding Today"

The previous articles covered principles; this one compresses them into a checklist an individual or small team can execute within a week. The roadmap itself is the speaker's suggestion based on Alibaba's practice handbook, not any company's official process. The handbook's core advice for teams starting out: you don't need a complete system at once. First build a project map, standardise complex requirements, provide verifiable feedback and connect the chain of production facts, forming a basic closed loop.

Unlike the previous articles, this one goes day by day, stating for each what to do, why, and what "done" looks like.

Day 1: run one real small task end to end

What. Pick a well-bounded bug or small feature that has tests, and let a coding agent do it from start to finish. Record everything: how long did it take, where did it get stuck, how many times did you step in?

Why. Experience first, design the process second. Many teams start by writing conventions aimed at imagined problems instead of real ones. Every "stuck" you record today is raw material for the coming days.

Done when. One merged MR plus a list of problems.

Day 2: write the project rule file

What. Write AGENTS.md or CLAUDE.md in the repository root: stack, directory layout, build and test commands, prohibitions, and operations that require stopping to ask (DB migrations, secrets, production). Commit it to Git.

Why. Day 1's list probably includes things like "it used the wrong package manager" or "it didn't know the test command". Those are exactly what a rule file is for.

Note. Don't write dozens of rules at once. The developer on X who shared how they use Orca suggests adding one when the agent keeps making the same mistake. His example rules include "existing tests may only be added to, never changed or deleted" and "stop and ask me before touching DB migrations, payment keys or production". The first targets the risk from Chapter 3: an agent editing tests to make them pass.

Day 3: fill in the project map

What. Describe the responsibilities, entry points and dependencies of key modules. Let the agent read the code and draft it; a person proofreads.

Why. This is the "project map" from context engineering (article 2). Proofreading is valuable in itself: wherever the agent misunderstood in its draft, the code is probably unclear.

Day 4: one command for verification

What. Make compilation, type checks, lint and unit tests run with a single command, write that command into the rule file, and require the agent to run it after every change.

Why. This is the seconds layer of layered verification (article 4). Without it, every change the agent makes has to be checked by you. Today's investment may have the highest return of the week.

Day 5: do a medium-sized feature with a spec

What. Pick something more complex than Day 1. Let the agent read the requirement and code and ask questions first; write constraints, acceptance criteria and non-goals into a spec; then implement.

Why. Practise article 3's "clarify before building" and feel the effect of separating constraints from assumptions. Compare with Day 1: was there less rework?

Day 6: build review habits

What. Keep MRs small; in review, look at test results and core logic first, watching closely for changes to tests; send all comments back to the agent at once for rework rather than fixing things yourself.

Why. If you fix it yourself the agent learns nothing and repeats the mistake; if you send it back, and add it to the rule file when needed, problems actually converge.

Day 7: retrospect and capture

What. Answer three questions:

  1. Where does the agent keep making mistakes? → Add a rule.
  2. Which workflow has been repeated more than three times? → Turn it into a Skill (another developer's "rule of three").
  3. What were this week's lead time and rework counts? → Record them as the baseline.

Why. Without Day 1 and Day 7 data to compare, you cannot tell whether anything improved. The METR study in article 6 shows that feelings are unreliable.

After the week

The seven days map onto four basic loops: the project map (Days 2–3), standardised requirements (Day 5), verifiable feedback (Days 4 and 6), and measurement and capture (Day 7). The chain of production facts (article 5) usually needs infrastructure support and can be the next stage's goal.

Anthropic's advice in Building effective agents applies here too: start with the simplest solution and add complexity only when it demonstrably helps. The handbook also notes that while methods are still immature, letting team members explore separately and share regularly finds effective paths better than standardising too early; converge on a unified workflow once practices stabilise.

Common misconceptions

  • "Buy the most expensive tool and go multi-agent first." Until a single agent + rules + verification loop works, multiple agents only amplify chaos.
  • "You'll see 10× productivity in a week." The week's goal is to build the loop and a baseline, not to post results.
  • "Once the rule file is written, leave it alone." It should evolve with the project and the team's experience.
