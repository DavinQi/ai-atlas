The Troubleshooting Evidence Chain: Collect Evidence First, Then Infer the Root Cause

Companion to diagram #26 · Chapter 4 "AI Coding Today"

Overview

The most common mistake in production troubleshooting is guessing the root cause first, then looking for evidence to prove it. Humans do this, and agents do it even more: models are naturally good at producing "plausible-sounding" explanations. The evidence chain reverses the order: collect factual evidence in a fixed way first, then infer the root cause from the complete request chain; escalate when evidence is insufficient instead of guessing.

Core Mechanisms

The Qwen user-growth team's approach (per Alibaba's handbook):

  1. Unified TraceId: connect logs, upstream/downstream state and code call relationships.
  2. Evidence first: troubleshooting does not start from guessing the root cause; it first collects facts such as the TraceId, structured logs, upstream/downstream state, code locations and call relationships.
  3. Judge from the complete request chain.
  4. Tiered diagnosis: obvious errors are located directly from logs by a diagnostic agent; when evidence is insufficient or states conflict, the existing evidence goes to an agent with full code context for further analysis.
  5. Standardization: fix the evidence-collection method, escalation conditions and conclusion format, so troubleshooting moves from personal experience to a reusable, verifiable engineering process.

A minimal evidence chain:

Symptom (error / alert / user report)
→ TraceId → logs and state at every hop
→ matching code location and recent changes
→ hypothesis → confirm or refute with evidence
→ conclusion (root cause + evidence + fix + regression test)

Key Papers and Milestones

  • ReAct (2022): gathering information by interacting with the environment mitigates hallucination and error propagation in pure reasoning — the evidence chain applies this principle to operations
  • Google SRE Book: systematic incident handling and postmortem culture
  • Alibaba's AI Native R&D Paradigm Practice Handbook: TraceId evidence chains and tiered diagnosis

Engineering Practice and Numbers

  • Observability is a prerequisite: without a unified TraceId and structured logs, even the strongest agent has nothing to work with.
  • Give agents read-only access: during troubleshooting an agent should be able to read logs, tables and call chains, but not change production directly. The X developer mentioned earlier uses a read-only database MCP and a log Skill.
  • Fixed conclusion format: root cause, evidence, impact scope, fix, regression test. Evidence must be reviewable by a human.
  • Evidence becomes an asset: the handbook notes production evidence chains and diagnostic capabilities are continually read, verified and updated by later agents.
  • Include multi-end dependencies in the evidence: another team in the handbook uses a unified workspace to judge cross-project contracts, avoiding falsely concluding "fixed" on stale dependencies when a shared capability changed but consumers were not rebuilt.

Common Misconceptions

  • "The model's root cause sounds reasonable, so it must be right." An explanation without evidence is only a hypothesis.
  • "Tests pass after the fix, so we're done." Add a regression test that reproduces the original problem.
  • "Collecting evidence is slow; just let the agent change things." A fixed collection process can be automated and is faster than repeated trial and error.
