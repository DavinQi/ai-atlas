Troubleshooting Evidence Chains: Collect Evidence First, Then Infer the Root Cause

Companion to diagram #26 · Chapter 4 "AI Coding Today"

The most common mistake in production troubleshooting is guessing the root cause first and then looking for evidence to prove it. People do it; agents do it even more, because models are naturally good at producing explanations that "sound right". An evidence chain reverses the order: collect factual evidence in a fixed way first, then infer the root cause from the full request chain; when the evidence is insufficient, escalate instead of guessing.

1. A "wrong guess" example

Alert: at 14:05 the error rate of the order API suddenly rises to 5%.

Guessing first. The agent sees the alert and notices a deployment at 13:50, so it infers: "The 13:50 release introduced a bug." It finds that release's diff, sees that it did touch order code, and recommends a rollback. Every step of this reasoning "makes sense".

Evidence first. Take the TraceId of a failed request and follow each hop: gateway fine → order service fine → call to the inventory service times out. Then look at the inventory service: the cache cluster it depends on failed over from primary to replica at 14:04. The recent release has nothing to do with this path.

Rolling back on the first approach would not lower the error rate, and the team would spend more time investigating while the incident continued. As Chapter 1 explained, a model generates the most probable next token, not the true cause. "A release caused the incident" is a statistically common pattern, so the model readily says it, but this time it is not the fact.

2. Why evidence first

ReAct (2022), introduced in Chapter 2, rests on a key observation: interacting with an external environment to gather information mitigates hallucination and error propagation in pure reasoning. The evidence chain applies that principle to operations: anchor every inference to a fact that can be checked, not to the previous inference.

3. How the Qwen user-growth team does it

Per Alibaba's handbook:

  1. A unified TraceId connects logs, upstream and downstream state and code call relationships.
  2. Collect evidence first: troubleshooting does not start from guessing; it starts by gathering facts such as the TraceId, structured logs, upstream and downstream state, code locations and call relationships.
  3. Judge from the complete request chain, not just the hop that reported the error.
  4. Tiered diagnosis: obvious errors are located directly from logs by a diagnosis agent; when evidence is insufficient or contradictory, the gathered evidence goes to an agent with full code context.
  5. Standardise: fix how evidence is collected, when to escalate and the format of conclusions, so troubleshooting moves from personal experience to a reusable, verifiable engineering process.

The tiering in step 4 is worth noticing: most incidents are simple (null pointers, bad config) and a lightweight diagnosis agent can handle them; only a few complex cases need heavier context. It is the same split as first-line on-call and second-line experts in human teams.

4. A minimal evidence chain

symptom (error / alert / user report)
→ TraceId → logs and state at every hop
→ corresponding code locations and recent changes
→ hypothesis → confirm or refute with evidence
→ conclusion (root cause + evidence + fix + regression test)

Note that the hypothesis comes after the evidence and is followed by "confirm or refute". In the example, "the release caused it" was a fine hypothesis, but the evidence (the chain pointing to the inventory service) refuted it directly.

5. Engineering points

  • Observability is a prerequisite. Without unified TraceIds and structured logs, even the strongest agent has nothing to work with. The quality ceiling of the evidence chain is the quality of observability.
  • Give agents read-only access. During troubleshooting an agent should be able to read logs, tables and call chains but should not change production directly. The developer on X mentioned earlier uses a read-only database MCP and a logging Skill.
  • Fix the format of conclusions: root cause, evidence, impact, fix and regression test. Evidence must be checkable by a person, with TraceIds and log excerpts attached, not just "analysis shows the cause is…".
  • Turn evidence into assets. The handbook notes that production evidence chains and diagnostic ability are continually read, validated and updated by later agents. Today's troubleshooting record is tomorrow's context.
  • Include cross-project dependencies in the evidence. Another team in the handbook uses a unified workspace to check contracts across projects, avoiding cases where "a shared capability changed but its consumers weren't rebuilt" leads to a false "fixed" on stale dependencies.

6. Common misconceptions

  • "The model's root cause sounds very plausible, so it must be right." An explanation without supporting evidence is only a hypothesis. The more plausible it sounds, the more it needs checking.
  • "Tests pass after the fix, so we're done." Add a regression test that reproduces the original problem, or it may come back.
  • "Collecting evidence is too slow; just let the agent fix it." A fixed collection procedure can be automated and is faster than repeated trial and error. In the example, guessing looked fast and was in fact much slower.
