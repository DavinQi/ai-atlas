Memory and RAG: Put the Right Knowledge into Context at the Right Time

Companion to diagram #14 · Chapter 2 "Agent Design: Principles & Patterns"

Once deployed, a model's weights are fixed and its context window is finite. To use private knowledge, current information and long-term experience, an agent must keep solving the same problem: what should go into the context right now? Too little and the model can only guess from memory; too much and cost rises, attention is diluted, and the key information gets buried.

Diagram #14 has two halves: the top shows four kinds of memory (context window, session summary, vector store and documents, rule files); the bottom shows RAG's two pipelines (offline indexing, online querying). A sentence at the bottom ties them together: parametric memory lives in the weights, non-parametric memory lives in the retrieval index. This article first explains why layered memory is needed, then takes RAG apart step by step to show where quality is usually lost.

1. Four kinds of memory, like a computer's storage hierarchy

The easiest way to understand an agent's memory is to compare it with a computer's storage hierarchy:

Memory Analogy Capacity Access Examples
Context window (working memory) Registers / RAM Small, billed per token Seen directly by the model The current conversation, a file just read
Session summary (short-term memory) Cache Medium Compressed and put back into context Key points of the previous 50 turns
Vector store · documents (long-term memory) Disk Large Retrieved and put back into context Product docs, past tickets
Rule files (procedural memory) Configuration Small and stable Loaded at the start of each session AGENTS.md, coding conventions

MemGPT turned this analogy into a real system: borrowing hierarchical memory management from operating systems, it lets the agent move data between fast and slow storage itself, getting the effect of "more memory" within a limited context window, for analysing documents far longer than the window and for long multi-session conversations. Generative Agents store a complete record of experiences in natural language, synthesise higher-level reflections over time, and retrieve by relevance, recency and importance when planning.

Core insight: the context window is the only place the model can "see"; all other memory is merely a candidate. A memory system is essentially a policy for deciding what to bring into context, and when.

2. RAG: bring the open-book exam's books into the exam room

The basic idea. Lewis et al. proposed retrieval-augmented generation (RAG) in 2020: generate answers by combining pretrained parametric memory (the weights) with non-parametric memory (a retrievable document index). The paper notes that this helps provide provenance for answers and makes knowledge easier to update: just change the documents, without retraining the model.

The offline pipeline: documents → chunks → embeddings → vector store.

  1. Chunking. Documents are cut into pieces of a few hundred tokens. Too large and a chunk mixes several topics, retrieval is imprecise and context is wasted; too small and context is lost (a table split into several pieces separates headers from data). Cutting at semantic boundaries such as headings and paragraphs, with a little overlap, usually beats cutting at fixed lengths.
  2. Embedding. An embedding model turns each chunk into a vector; semantically similar chunks have similar vectors.
  3. Indexing. Store them in a vector store with metadata (source, date, permissions, product line), so you can filter before retrieving.

The online pipeline: query → retrieve top-k → rerank → insert into the prompt → LLM.

  1. Retrieval. Embed the user's question too and find the k most similar chunks. Pure vector search is good at semantic similarity but insensitive to exact names, version numbers and error codes, so in practice it's often combined with keyword search (BM25).
  2. Reranking (optional, but usually worth it). A finer model rescores the candidates and puts the truly relevant ones first.
  3. Prompt assembly. Put the chunks and their sources into the context, and ask the model to answer from them, cite sources, and say so when the material is insufficient.

Where is quality usually lost? Not in generation but in retrieval. If the model is handed wrong or incomplete material, it can't answer well however strong it is. Gao et al.'s survey divides RAG's evolution into three generations: Naive RAG (retrieval wired straight to generation), Advanced RAG (adding optimisations such as query rewriting and reranking before and after retrieval) and Modular RAG (composable modular pipelines). Chunk granularity, metadata filtering and reranking are often more effective than switching to a bigger model.

What about global questions? For questions like "what are the main themes of this document collection?", the answer is spread across all documents, and the few chunks ordinary retrieval returns can't answer it. Microsoft's GraphRAG first uses an LLM to extract entities and relationships from the documents into a knowledge graph, pre-generates community summaries for groups of related entities, and at answer time aggregates partial answers from each community.

3. Can long context replace RAG?

Context windows keep growing, so a natural thought is: stuff everything in and skip retrieval. Research says no.

Information in the middle gets overlooked. Liu et al.'s "Lost in the Middle" study found that performance is best when relevant information is at the beginning or end of the input and drops markedly when it's in the middle of a long context, even for models built for long contexts.

More context, weaker recall. Anthropic describes the "context rot" revealed by needle-in-a-haystack evaluations: the more tokens in the context, the weaker the model's ability to recall information from it accurately. They liken context to a finite attention budget with diminishing returns.

Cost rises with length. As Chapter 1 explained, prefill attention grows with the square of length and the KV cache grows linearly.

So Anthropic frames the problem as context engineering: find the smallest set of high-signal tokens that maximises the likelihood of the desired outcome.

4. The new approach in the agent era: just-in-time context

Traditional RAG is "retrieve first, then insert everything at once". Anthropic observes that more and more agents use just-in-time context instead: keep only lightweight identifiers (file paths, queries, links) and load content with tools at run time. A coding agent browsing a codebase with grep and glob is the classic case: it doesn't need to embed the whole repository in advance; like a person, it looks at the directory, searches for keywords, then opens the relevant files.

For long tasks spanning hours, they summarise three techniques:

  • Compaction: when the conversation nears the window limit, summarise it and continue in a new window with the summary.
  • Structured notes: the agent writes progress, to-dos and key decisions to files outside the context and reads them back when needed.
  • Multi-agent architectures: subagents explore in their own contexts and return only the essentials to the main agent (next article).

5. Common misconceptions

  • "With a big enough context window, you don't need RAG." Long contexts suffer reduced use of middle information and context rot, and cost rises with length.
  • "RAG eliminates hallucination." It lowers the chance of unsupported generation, but retrieval errors or faulty documents still cause errors. Require citations and allow "I don't know" when material is insufficient.
  • "Memory means a vector store." Memory also includes summaries, structured notes and rule files. What to choose and when to put it in context is what matters.
  • "It doesn't matter where key content goes." Following "Lost in the Middle", put the most important instructions and material at the beginning or end.
