Memory and RAG: Put the Right Knowledge into Context at the Right Time

Companion to diagram #14 · Chapter 2 "Agent Design: Principles & Patterns"

Overview

Model weights are fixed after deployment and the context window is finite. For an agent to use private knowledge, fresh information and long-term experience, it must solve one problem: put the right content into context at the right time. Retrieval-augmented generation (RAG) and layered memory are the two main tools. Anthropic frames this as "context engineering": context is a finite resource with diminishing marginal returns, and good context engineering means finding the smallest set of high-signal tokens that maximizes the likelihood of the desired outcome.

Core Mechanisms

1. Basic RAG. Lewis et al. (2020) combined pre-trained parametric memory (model weights) with non-parametric memory (a retrievable document index) for generation. The paper notes this helps provide provenance for answers and makes knowledge easier to update. Typical flow:

Docs → chunk → embed → index
Query → retrieve Top-K → rerank → insert into prompt → generate

2. Evolution. The survey by Gao et al. divides RAG into three generations: Naive RAG (retrieve-then-generate), Advanced RAG (pre- and post-retrieval optimizations such as query rewriting and reranking) and Modular RAG (composable pipelines). For global questions like "what are the main themes in this corpus?", plain retrieval does poorly; Microsoft's GraphRAG first uses an LLM to build an entity knowledge graph, pre-generates community summaries for groups of related entities, and at query time aggregates partial answers from each community.

3. Layered memory. MemGPT borrows hierarchical memory management from operating systems, moving data between fast and slow tiers to give an agent the effect of "more memory" within a limited window — for analyzing documents far larger than the window and for long multi-session chat. Generative Agents store a complete record of experiences in natural language, synthesize them over time into higher-level reflections, and retrieve them dynamically to plan.

4. Long context does not remove the need for retrieval. The "Lost in the Middle" study found performance is highest when relevant information is at the beginning or end of the input and degrades significantly when it sits in the middle of long contexts — even for explicitly long-context models. Anthropic also notes the "context rot" seen in needle-in-a-haystack style evaluations: as the number of tokens in context grows, the model's ability to accurately recall information from it decreases.

Engineering Practice and Numbers

  • "Just-in-time" context: Anthropic observes that more agents no longer pre-process all relevant data upfront; they keep lightweight identifiers (file paths, stored queries, links) and load data at runtime with tools. Coding agents navigating a codebase with grep and glob are the typical example.
  • Three techniques for long tasks: compaction (summarize a conversation nearing the limit and restart with a new window), structured note-taking (the agent writes progress to files outside the context), and multi-agent architectures (subagents explore in their own contexts and return only the distilled essentials).
  • Retrieval quality sets the ceiling: chunk size, metadata filtering and reranking often matter more than a bigger model.
  • Put key content at the start and end, exploiting the "Lost in the Middle" pattern.

Common Misconceptions

  • "With a big enough window, RAG is unnecessary." Long contexts suffer mid-context degradation and context rot, and cost grows with length.
  • "RAG eliminates hallucination." It reduces ungrounded generation but still fails when retrieval is wrong or the documents themselves are wrong.
  • "Memory means a vector store." Memory also includes summaries, structured notes and rules files; what to select and when to put it in context is what matters.
