MCP: One Protocol to Connect Tools and Data to Any Agent

Companion to diagram #13 · Chapter 2 "Agent Design: Principles & Patterns"

Suppose your team uses three AI tools: an IDE plugin, a chat client and an internal ticketing agent. All three need access to GitHub, the company database and the file system. Without a common standard, each application writes a separate integration for each tool: 3 applications × 3 tools = 9 sets of code, each with slightly different authentication, error handling and data formats, and every new tool means changing every application. That is the "M × N" combinatorial explosion.

The Model Context Protocol (MCP), an open protocol released by Anthropic in November 2024, aims to solve exactly this: an application implements an MCP client once, a tool implements an MCP server once, and any combination works together, turning 9 integrations into 3 + 3 = 6 adapters. Diagram #13 shows its structure from top to bottom: a host containing the LLM and several MCP clients, connected over JSON-RPC 2.0 to their servers, which expose three kinds of capability (tools, resources and prompts), with the three-step flow of a tool call at the bottom.

1. The design reference: LSP did the same thing

The MCP specification says explicitly that it takes inspiration from the Language Server Protocol (LSP). Before LSP, every editor implemented completion, go-to-definition and diagnostics separately for each programming language; LSP pulled "language intelligence" out into separate servers, so each editor needed to implement only one client. As a result, VS Code, Vim, Emacs and others can all use the same TypeScript or Rust language server.

MCP aims to be the LSP of the AI era: just as LSP standardised how programming-language support plugs into development tools, MCP standardises how context and tools plug into AI applications. With that analogy in mind, the design decisions that follow look natural.

2. Three roles

The protocol uses JSON-RPC 2.0 messages between three roles:

  • Host: the LLM application that initiates connections, such as an IDE or chat client. It owns the user interface and the final authorisation decisions.
  • Client: a connector inside the host. Each client corresponds to one server, maintaining one stateful connection one to one, which aids isolation: if one server misbehaves, other connections are unaffected.
  • Server: a service providing context and capabilities, either a local process or a remote service.

Note the relationship between host and LLM: the model itself doesn't "connect" to any server. It only sees descriptions of available tools in its context and decides which to call; it is the host and its clients that actually send requests, execute them and put results back into context.

3. Three kinds of server capability: who decides to use them?

MCP divides what a server can offer into three kinds, and the criterion is interesting: who controls their use.

Primitive What it is Controlled by Examples
Tools Functions for the model to execute The model decides to call them (with user authorisation) Create an issue, run a query
Resources Context and data The application or user chooses to put them in context A file, a table's schema
Prompts Templated messages and workflows The user selects them explicitly A "write release notes" template

The split corresponds to three trust levels: tools have side effects and need the most gatekeeping; resources are read-only data; prompts are shortcuts the user triggers explicitly.

In the other direction, clients can also offer capabilities to servers: sampling lets a server ask the host to call an LLM on its behalf (so the server needs no model or API key of its own); roots let a server ask which URIs or file-system boundaries it may operate within; elicitation lets a server ask the user for more information when needed. This article follows the 2025-06-18 version of the specification, which is the version that added elicitation.

4. The full journey of one tool call

Take "open a GitHub issue for this bug":

  1. Initialisation and capability negotiation. When the connection is set up, client and server exchange the capabilities and protocol versions they support. The connection is stateful, so afterwards each side knows what the other can do.
  2. Tool discovery. The client requests the list of tools, and the server returns each tool's name, description and JSON Schema for parameters. The host puts these descriptions into the model's context.
  3. The model decides to call. Reading the description of create_issue, the model generates a structured tool_call with a title and body as parameters.
  4. The user authorises; the client executes. After the host confirms with the user, the client sends the call to the GitHub server, which actually calls the GitHub API.
  5. The result returns to context. The server returns the new issue's link, the host puts it into context, and the model replies to the user.

If the server's tool list changes (say an administrator enables a new tool), the server can send a notification proactively, so the client doesn't need to poll.

5. Two layers and two transports

MCP has two layers. The data layer defines the JSON-RPC-based protocol itself: lifecycle management, capability negotiation and the primitives above. The transport layer handles how bytes are delivered, commonly in one of two ways:

  • STDIO: the host starts the server as a local subprocess and communicates over standard input and output. Simple, no network needed, usually serving a single client; suited to tools like the file system or local Git.
  • Streamable HTTP: the client sends messages with HTTP POST, and the server can optionally stream responses with server-sent events. Remote servers usually serve many clients at once; suited to shared internal services and easy to connect to unified authentication.

The benefit of separating the layers: the same server implementation can turn from a local tool into a shared team service just by switching transport.

6. Security: the spec itself says "the protocol cannot enforce"

MCP lets models access arbitrary data and execute arbitrary code, so security is a core part of the specification. It lists several principles:

  • Users must explicitly consent to and understand all data access and operations.
  • Hosts must obtain explicit user consent before exposing user data to servers.
  • Tools represent arbitrary code execution and must be treated with caution; tool descriptions (such as annotations) from untrusted servers should be considered untrusted.
  • Hosts must obtain explicit user consent before invoking any tool; users must approve any sampling request.

Most notable is the specification's candour: the protocol itself cannot enforce these principles; implementers must build consent and authorisation flows into their applications. Tool descriptions are placed into the model's context, and a malicious server could hide instructions in them, which is exactly the prompt injection discussed in article 6.

7. Practical advice

  • Read-only first, writes later. Start internal systems with read-only servers (query databases, logs, docs); once the value is proven, open write operations gradually, with human confirmation.
  • Tool descriptions are prompts. Be specific: when to use it, when not to, what parameters mean and their constraints, typical examples. Description quality directly affects whether the model picks the right tool.
  • Few and focused. Tool descriptions take up context, and too many similar tools make the model choose wrongly. Mount only the servers a task needs.
  • Put remote services behind unified authentication. Deploy over Streamable HTTP, connect to the company identity system and keep full call logs.

8. Three common misconceptions

  • "MCP is just function calling." Function calling is a model-level capability; MCP is a protocol between applications and services that also covers resources, prompts, capability negotiation and notifications.
  • "Connecting via MCP makes it secure." The specification says plainly that the protocol cannot enforce its security principles; authorisation and auditing are up to you.
  • "The more tools the better." Tool descriptions take up context, and similar tools interfere with each other.
