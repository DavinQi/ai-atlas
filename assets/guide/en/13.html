MCP: One Protocol to Connect Tools and Data to Any Agent

Companion to diagram #13 · Chapter 2 "Agent Design: Principles & Patterns"

Overview

The Model Context Protocol (MCP) is an open protocol for standardized integration between LLM applications and external data sources and tools. The official specification says MCP takes inspiration from the Language Server Protocol (LSP): just as LSP standardized how programming-language support plugs into development tools, MCP standardizes how context and tools plug into the AI application ecosystem. Before MCP, every AI app needed a custom integration for every tool — an "M apps × N tools" explosion; with a shared protocol it becomes "M + N".

Core Mechanisms

1. Three roles. The protocol uses JSON-RPC 2.0 messages between:

  • Host: the LLM application that initiates connections, such as an IDE or chat client.
  • Client: a connector inside the host; each client maps to one server.
  • Server: a service that provides context and capabilities.

2. Three server features.

  • Resources: context and data for the user or model.
  • Prompts: templated messages and workflows for users.
  • Tools: functions for the model to execute.

3. Client features offered to servers. Sampling (server-initiated LLM calls), Roots (servers asking which URI or filesystem boundaries they may operate in), and Elicitation (servers requesting additional information from users).

4. Two layers. The data layer defines the JSON-RPC protocol, including lifecycle management, capability negotiation and the primitives above; the transport layer handles communication. Two common transports:

  • STDIO: local servers, typically serving a single client.
  • Streamable HTTP: the client sends messages via HTTP POST, optionally receiving streamed responses via Server-Sent Events; remote servers typically serve many clients.

Connections are stateful and both sides negotiate supported capabilities at initialization; when its tool list changes, a server can notify clients without polling.

Engineering Practice and Numbers

Security is a core part of the spec. It states plainly that MCP enables arbitrary data access and code execution, and implementers must take this seriously:

  • Users must explicitly consent to and understand all data access and operations.
  • Hosts must obtain explicit consent before exposing user data to servers.
  • Tools represent arbitrary code execution and must be treated with caution; tool descriptions such as annotations from untrusted servers should be considered untrusted.
  • Hosts must obtain explicit user consent before invoking any tool; users must approve any sampling request.

The spec also admits the protocol itself cannot enforce these principles; implementers must build consent and authorization flows into their applications.

Practical advice:

  • For internal systems, start with read-only servers (query DBs, read logs), then open write operations gradually.
  • Make tool descriptions clear and specific — this directly affects whether the model picks the right tool.
  • Use Streamable HTTP for remote servers and plug them into unified authentication.

Common Misconceptions

  • "MCP is just function calling." Function calling is a model-level capability; MCP is an application-to-service protocol that also covers resources, prompts, capability negotiation and notifications.
  • "Using MCP makes it secure." The spec says the protocol cannot enforce security principles; authorization and auditing are on you.
  • "More tools is better." Tool descriptions consume context, and many similar tools make the model choose wrongly.
