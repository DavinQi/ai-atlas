Traditional CI/CD: Pipelines Run Automatically, Judgement Stays with People

Companion to diagram #34 · Chapter 6 "How AI Reshapes the Dev Lifecycle"

Continuous integration and continuous delivery (CI/CD) turned build, test and deploy into automated pipelines, one of the most important advances in software engineering of the past decade or more. But in traditional CI/CD and operations, execution is automatic while judgement stays with people: when a test fails, who works out why? When an alert fires, who locates the problem? Should the release continue? How do we learn from the incident? All of this depends on engineers' experience.

This chapter looks at what AI changes from the process perspective. Like "The Traditional IDE" in Chapter 3, this article is the baseline: where the pipeline is automated today and where it relies on people.

1. The pipeline: what is already automated

A typical pipeline:

commit → build → unit tests → integration tests → artefact → staging → canary → production

Every arrow is the machine moving things forward. The release engineering chapter of Google's SRE Book stresses two principles that explain why such pipelines are reliable:

  • Self-service: teams release on their own without queueing for dedicated release engineers, removing a "wait for a person" step.
  • Hermetic builds: builds are insensitive to the libraries and software installed on the build machine; the same inputs always give the same output, so builds are repeatable.

Repeatability matters especially in the agent era. Agents rely on environmental feedback to correct themselves (Chapter 3). If the same code builds today and fails tomorrow because a library on the machine was upgraded, the agent will go off to "fix" a problem that doesn't exist. Hermetic builds are a prerequisite for trustworthy feedback.

2. Judgement: what still relies on people

Wherever the pipeline stops is where a person steps in:

  • Analysing test failures and build errors: is the code wrong, the test wrong, or the environment flaky?
  • Alert triage and fault localisation: does this alert matter? Where is the problem?
  • Release decisions: continue, pause or roll back?
  • Postmortems and follow-up actions: why did it happen? How do we prevent it?

Consider a concrete moment. Friday, 4 p.m.: during the canary, the error rate rises from 0.1% to 0.3%. The on-call engineer has minutes to answer: is this the new version or normal noise? Roll back? What would a rollback affect? These calls need experience, context and risk trade-offs; the pipeline itself can't answer them.

3. Toil: where AI moves in first

The SRE Book defines toil as work tied to running a production service that is manual, repetitive, automatable, tactical, devoid of enduring value, and that scales linearly as the service grows.

Google aims to keep each SRE's toil below 50% of their time, with at least half spent on engineering work that reduces future toil or adds service features. The book mentions quarterly surveys showing Google SREs spend about 33% of their time on toil on average.

By this definition much "judgement" work is half toil: digging through logs, finding TraceIds, checking recent changes, pulling up similar past incidents. These steps are manual, repetitive and automatable. Chapter 4's evidence chain hands exactly the evidence-gathering part to agents. AI moves first not into the parts needing deep judgement, but into the toil that precedes judgement.

4. Decide with data, not feelings

Another key SRE idea is to replace subjective calls with objective measures:

Error budgets. An error budget based on a service level objective (SLO) gives an objective measure of how unreliable a service is allowed to be in a quarter. For example, with a 99.9% availability SLO, a 30-day month allows 30×24×60×0.1%=43.2 minutes of downtime. With plenty of budget left you can release faster; when it is nearly spent, slow down and prioritise stability. Arguments about release pace change from "I think" to "how much budget is left".

Blameless postmortems. Postmortems focus on identifying the contributing causes of an incident, not on blaming individuals or teams. That has new meaning in the agent era: when an agent's change causes an outage, the postmortem should ask "which verification layer missed it, and why did permissions allow it?", not simply conclude "AI is unreliable".

DORA metrics are the common language for measuring the pipeline: throughput via change lead time (from commit to production deployment), deployment frequency and failed deployment recovery time; instability via change failure rate and deployment rework rate (Chapter 4).

5. Manual nodes outside the pipeline

Alibaba's practice handbook observes that a requirement coded in an hour can still take weeks from finished code to live after going through several internal platforms, release processes and environment constraints.

Even when the pipeline itself is highly automated, then, there are many manual nodes outside it: requesting resources, waiting for approvals, coordinating release windows, getting cross-team sign-off. By Amdahl's Law, these are the main bottleneck of end-to-end efficiency.

6. Common misconceptions

  • "Having CI/CD means we do DevOps." Automated execution is only the foundation; judgement still relies heavily on people.
  • "Toil means the team isn't working hard enough." The SRE Book treats toil as something to eliminate systematically with engineering, not a personal failing.
  • "AI will replace the pipeline." The opposite: a reliable pipeline is the infrastructure that gives agents their verification signals.
