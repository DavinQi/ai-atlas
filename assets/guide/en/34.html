Traditional CI/CD: Pipelines Run Automatically, Judgment Stays with Humans

Companion to diagram #34 · Chapter 6 "How AI Reshapes the Dev Lifecycle"

Overview

Continuous integration and continuous delivery (CI/CD) turned build, test and deploy into automatically running pipelines — one of the most important advances in software engineering over the past decade and more. But in traditional CI/CD and operations, execution is automatic while judgment stays with humans: who looks into why a test failed? Who locates the fault when an alert fires? Should a release continue? How is an incident reviewed afterwards? All of these depend on engineers' experience.

Core Mechanisms

1. Pipeline automation. A typical flow: commit → build → unit tests → integration tests → artifact → staging → canary → production. The release engineering chapter of Google's SRE Book stresses two principles: teams should be able to release on their own (self-service), and builds should be "hermetic" — insensitive to the libraries and software installed on the build machine — so they are reproducible.

2. Where humans provide judgment:

  • Analyzing test failures and build errors
  • Alert triage and fault localization
  • Deciding to continue, pause or roll back a release
  • Incident retrospectives and improvement actions

3. Toil. The SRE Book defines toil as work tied to running a production service that is manual, repetitive, automatable, tactical, devoid of enduring value, and that scales linearly as the service grows. Google's goal is to keep each SRE's toil below 50% of their time, with at least half spent on engineering work that reduces future toil or adds service features; the book cites quarterly surveys showing Google SREs spend about 33% of their time on toil on average.

4. Decide with data, not gut feeling. SRE uses error budgets based on service level objectives (SLOs) to set release pace: the error budget provides an objective metric of how unreliable the service is allowed to be within a quarter. Postmortems are "blameless": they focus on identifying the contributing causes of an incident rather than blaming individuals or teams.

Key Papers and Milestones

  • Google SRE Book: toil, error budgets, release engineering, blameless postmortems
  • DORA metrics: change lead time, deployment frequency, failed deployment recovery time, change failure rate, deployment rework rate

Engineering Practice and Numbers

  • DORA's five metrics are the common language for measuring this pipeline: throughput is change lead time (from commit to production deployment), deployment frequency and failed deployment recovery time; instability is change failure rate and deployment rework rate.
  • AI enters through toil first: repetitive, automatable work with no enduring value is the ideal target for agents.
  • An observation from Alibaba's handbook: a requirement whose coding takes an hour can still take weeks from code complete to live after passing through multiple internal platforms, release processes and environment constraints. Human nodes outside the pipeline are the main bottleneck of end-to-end efficiency.

Common Misconceptions

  • "Having CI/CD means doing DevOps." Automated execution is only the foundation; judgment still relies heavily on humans.
  • "Toil means the team isn't working hard enough." The SRE Book treats toil as something to eliminate systematically through engineering, not a personal failing.
  • "AI will replace the pipeline." Quite the opposite: a reliable pipeline is the infrastructure from which agents get verification signals.
