Spec-Driven: Clarify Before Building; Write Constraints and Assumptions Separately

Companion to diagram #24 · Chapter 4 "AI Coding Today"

Overview

The faster an agent writes code, the more a misunderstood requirement costs: in the wrong direction, more code means more rework. The spec-driven approach is to clarify the requirement into a verifiable specification first, then let the agent build. Alibaba's handbook offers one key technique: write "constraints" and "assumptions" separately — the Spec draws the boundary of "what counts as correct", not the implementation path.

Core Mechanisms

1. Don't assume the requirement is complete. The handbook notes that people writing requirements often omit default knowledge such as permission boundaries, concurrency handling and idempotency strategy, while AI lacks that organizational memory and can only guess or ignore it. A simple requirement like "generate a public share link" involves decisions on revocation, access control and data consistency. The team has AI actively ask about implicit business and technical decisions and records the answers as traceable Specs and Tasks, exposing risk at the cheapest stage of development.

2. Constraints vs assumptions.

  • Constraints: data must not leave the domain, APIs must stay backward compatible, latency must not exceed a threshold. Keep them long-term and check them automatically where possible.
  • Assumptions: microservices or monolith, which caching strategy. These are hypotheses to be validated, and AI should be allowed to adjust them based on implementation and runtime feedback.

3. What a sufficient Spec contains. Combining the handbook and practitioner experience:

  • The problem to solve and non-goals
  • Scope and priorities
  • Constraints (written as checks where they can be automated)
  • Key decisions and rationale
  • Acceptance criteria (ideally directly convertible to tests)
  • Open questions

4. Know when to stop clarifying. One developer on X shared: use repeated questioning to pin down goals, constraints and trade-offs, and record them in a Spec or CONTEXT.md; once the remaining questions would no longer significantly change the implementation direction or acceptance result, start building — don't require planning every implementation detail upfront, or requirement alignment becomes a heavy process of its own. He also noted that heavy Spec- and TDD-centric Skills such as Superpowers consume a lot of tokens, and as models get stronger some once-useful constraints and processes are turning into noise.

Key Papers and Milestones

  • Plan-and-Solve (2023): planning before executing reduces missing-step errors — the model-level counterpart of "clarify before building"
  • Alibaba's AI Native R&D Paradigm Practice Handbook: Specs that separate constraints from assumptions

Engineering Practice and Numbers

  • The Spec is also shared context for multiple agents: implementing and reviewing agents read the same Spec without rereading the whole previous conversation.
  • Acceptance criteria first: the Qwen user-growth team adopted TDD — fix requirement boundaries with failing tests, make them pass with a minimal implementation, then refactor under test protection.
  • Split complex requirements into independently acceptable issues; only parallelize parts that can proceed independently.

Common Misconceptions

  • "The more detailed the Spec, the better." Hard-coding the implementation path removes the agent's room to adjust from feedback and makes the process heavy.
  • "Clear requirements are the product manager's job." The handbook has AI ask proactively, moving clarification upfront as a team process.
  • "With a Spec you don't need tests." The Spec defines what is correct; tests prove it was done correctly.
