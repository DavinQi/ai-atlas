Spec-Driven Development: Clarify Before Building, and Separate Constraints from Assumptions

Companion to diagram #24 · Chapter 4 "AI Coding Today"

The faster an agent writes code, the more a misunderstood requirement costs: in the wrong direction, the more it writes, the more must be redone. Spec-driven development means first clarifying the requirement into a verifiable specification, then letting the agent build. Alibaba's practice handbook gives one key technique: write constraints and assumptions separately. The spec defines the boundaries of "correct"; it does not prescribe the implementation path.

1. Start with a one-line requirement

A product manager asks: "Let documents generate public share links."

It sounds complete. Hand it straight to an agent and it will quickly build something that works: a random URL that anyone can open to read the document. But a string of unspoken questions hides behind it:

  • Can a link be revoked? What happens to pages already open?
  • Does it expire?
  • If the document is deleted or the sharer leaves the company, does the link still work?
  • Can viewers see version history and comments?
  • May sensitive documents be shared publicly? Who controls that switch?
  • If "generate" is clicked twice on the same document, do you return the same link or a new one?

The handbook notes that people writing requirements tend to omit default knowledge such as permission boundaries, concurrency handling and idempotency, while AI lacks this organisational memory and can only guess or ignore it. "Generate a public share link" involves several decisions about revocation, access control and data consistency. Answered before coding, these questions cost minutes of discussion; discovered after launch, they may cost a data leak.

2. Let the AI ask

The handbook team's practice is not to assume the requirement is complete. The AI first reads the requirement and the relevant code and actively asks about implicit business and technical decisions; a person confirms each one, and the results are captured as a traceable spec and task list, exposing risk at the stage where development is cheapest.

This turns a model "weakness" into a strength: precisely because it has no organisational memory, it asks the questions veterans consider "obvious" and therefore never write down.

3. Constraints vs assumptions: the crucial cut

A spec contains two kinds of content, which must be written separately:

Constraint Assumption
Meaning Must hold, or the result is wrong What currently seems reasonable
Examples Data must not leave the region; the API stays backward compatible; revoked links stop working within 1 minute Cache links in Redis; use random tokens rather than signed URLs
Lifetime Kept long-term May change with feedback
How it is checked Turned into automated checks where possible Validated by implementation and runtime data
May the agent change it? No Yes, with a stated reason

Why separate them? If "use Redis" and "revoked within 1 minute" sit at the same level, the agent treats them as equally hard requirements. When Redis turns out to be a poor fit, it either forces it through or gets "flexible" with the constraint that actually matters. Written separately, the agent knows which lines are red and which can adapt to circumstances.

4. A spec that is good enough

Combining the handbook and practitioners' experience, a good-enough spec usually contains:

  1. The problem to solve and the non-goals ("no password protection in this release")
  2. Scope and priorities
  3. Constraints (as automated checks where possible)
  4. Key decisions and their rationale
  5. Acceptance criteria (ideally convertible straight into tests)
  6. Open questions

Non-goals are often neglected but matter: agents tend to over-engineer, and saying what not to do prevents scope creep better than saying what to do. Acceptance criteria bridge spec and tests: "accessing a revoked link returns 404" becomes a test directly.

5. Know when to stop clarifying

Spec-driven work can also go too far. A developer on X shares this experience: use repeated questioning to pin down goals, constraints and trade-offs, captured in a Spec or CONTEXT.md; once the remaining questions would no longer significantly change the implementation direction or acceptance outcome, start building. There is no need to plan every implementation detail in advance, or requirement alignment itself becomes a heavyweight process. He also notes that heavyweight Skills built around specs and TDD, such as Superpowers, consume a lot of tokens; as models get stronger, some once-useful constraints and processes are turning into noise.

A practical stopping rule: ask whether the answer to the next question would change the architecture or the acceptance criteria. If not, start writing code.

6. Where the spec sits in the process

  • Plan, then execute. Plan-and-Solve (2023) showed that planning before executing reduces missing-step errors, the model-level counterpart of "clarify first".
  • The spec is shared context for multiple agents. The implementing and reviewing agents read the same spec, without rereading the whole earlier conversation.
  • Acceptance criteria first. The Qwen user-growth team adopted TDD: fix the requirement's boundaries with failing tests, make them pass with a minimal implementation, then refactor under the protection of the tests.
  • Split complex requirements into independently verifiable issues, and parallelise only the parts that can progress independently (Chapter 5).

7. Common misconceptions

  • "The more detailed the spec, the better." Hard-coding the implementation path removes the agent's room to adjust from feedback and makes the process heavy.
  • "Clear requirements are the product manager's job." The handbook's approach is to have the AI ask, making clarification a team process.
  • "With a spec, we don't need tests." The spec defines what is correct; tests prove it was done correctly.
