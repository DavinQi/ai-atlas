The Orchestration Layer: One Agent as Project Manager, Humans Guard the Gates

Companion to diagram #32 · Chapter 5 "Multi-Agent Programming"

When more agents run at once than a person can track, you need an orchestration layer: one agent acts as "project manager", breaking down the task, dispatching work to worker agents, tracking progress and consolidating results, while humans step in only at key decision gates. This is what Anthropic calls the orchestrator–workers pattern: a central LLM dynamically breaks down tasks, delegates them to worker LLMs and synthesises the results, well suited to coding tasks whose subtasks can't be predicted in advance.

1. Why an orchestration layer?

In the previous two articles a human did the orchestrating: deciding how many worktrees to open, what to give each agent, when to check, how to merge. That is manageable with three agents; with ten, a person's whole day fills up with switching windows, checking status and copy-pasting errors.

The orchestration layer hands scheduling itself to an agent, turning the person from dispatcher back into decision-maker. It continues the thread of Chapter 3: each generation of tools hands one more layer of detail to the machine.

2. Subagents: the basic unit

Mainstream tools all have subagents built in:

  • Claude Code: subagents are Markdown files with YAML front matter; each runs in its own context window with a custom system prompt, specific tool access and independent permissions.
  • Codex: can spawn specialised agents in parallel and collect their results into one response; current versions enable subagent workflows by default.
  • Cursor: subagents are specialised assistants the main agent can delegate to; each works in its own context and returns results to the parent, used to break down complex tasks, work in parallel and keep the main conversation's context clean.

These subagents usually live within one session. Larger, longer-running orchestration needs a more structured coordination mechanism.

3. An example of structured orchestration: Orca

Orca's docs describe orchestration as a structured multi-agent layer (experimental), built on five concepts:

  • Run: a durable namespace and coordinator inbox.
  • Task: a work item with a spec, dependencies and status; tasks can form a DAG (directed acyclic graph).
  • Dispatch: one attempt to execute a task on a particular terminal.
  • Message: worker_done, escalation, question, heartbeat and so on.
  • Decision gate: a question created by the coordinator that blocks the relevant tasks until a decision is recorded.

A pre-release review shows how they fit. The developer on X who shared how they use Orca gives this example: before launch, one agent acts as project manager and leads two agents reviewing front end and back end separately, and the person reads only the final summary; the database migration step has a gate that a human must approve. Mapped onto the model:

Run: pre-release review
├─ Task A: review front end → Dispatch to terminal 1 → worker_done
├─ Task B: review back end  → Dispatch to terminal 2 → worker_done
├─ Task C: run migration    (depends on A, B)
│    └─ Decision gate: "May the migration script run?" ← human
└─ Coordinator summarises → hands to the human

Task C depends on A and B, forming a DAG; the decision gate stops C from running until the human answers.

The worker contract. Orca sets explicit requirements for workers: send worker_done exactly once, whether successful or not, stating the outcome; include a summary of what was done, what was found and what remains; send heartbeats during long work; and ask blocking questions through the coordinator rather than waiting locally.

These rules may look fussy, but each addresses a classic distributed-systems problem:

  • Exactly once: prevents a task being marked done twice, or never receiving a completion signal.
  • Completion messages carry both the task ID and the dispatch ID: Orca requires this so a stale retry cannot complete the wrong task. If a dispatch timed out and was re-dispatched, and the old attempt reported completion later, a task ID alone could overwrite the new attempt's result.
  • Heartbeats: let the coordinator tell "still working" from "stuck".
  • Questions via the coordinator: workers don't wait forever locally, and all blockers gather where a person can see them.

4. Humans guard the gates

Gates belong on irreversible or high-risk steps: merging shared components, database migrations, releases. That matches the guardrail principle from Chapter 2: let reversible operations go, require confirmation for irreversible ones.

Gates also concentrate decisions. Without an orchestration layer, ten agents ask for confirmation at ten different times in ten windows; with one, requests collect at the coordinator and a person can handle them in one sitting.

5. Engineering points

  • The orchestrator is itself an agent. The developer notes that Orca is built for agents as well as people: an agent can open new workspaces itself and read errors from other windows, and the "project manager" uses exactly these abilities to assign tasks and collect results.
  • Start small. Anthropic cautions that LLM agents are not yet good at coordinating and delegating in real time. Pilot with two or three workers and well-bounded tasks.
  • Verification decides. A worker reporting "done" is a signal; whether the task is really done depends on tests and checks.

6. Common misconceptions

  • "With an orchestrator, humans can step out entirely." High-risk decisions still need a responsible person; gates are part of the design.
  • "The more elaborate the orchestration, the stronger." Every layer adds tokens and failure points; add them as needed.
  • "If a worker says it's done, it's done." Completion is judged by verification results, not the agent's self-report.
