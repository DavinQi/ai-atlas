The Orchestration Layer: One Agent as Project Manager, Humans Guard the Gates

Companion to diagram #32 · Chapter 5 "Multi-Agent Programming"

Overview

When more agents run at once than a human can track, you need an orchestration layer: one agent acts as "project manager", breaking down tasks, dispatching them to worker agents, tracking progress and aggregating results; humans step in only at key decision gates. This is Anthropic's "orchestrator-workers" pattern: a central LLM dynamically breaks down tasks, delegates them to worker LLMs and synthesizes the results, suited to coding tasks whose subtasks can't be predicted.

Core Mechanisms

1. Subagents: the basic unit of orchestration. Mainstream tools have them built in:

  • Claude Code: subagents are Markdown files with YAML frontmatter; each runs in its own context window with a custom system prompt, specific tool access and independent permissions.
  • Codex: can spawn specialized agents in parallel and collect their results into one response; current releases enable subagent workflows by default.
  • Cursor: subagents are specialized assistants the main agent can delegate to; each works in its own context and returns results to the parent, used to break down complex tasks, work in parallel and keep the main conversation's context clean.

2. Orca's orchestration layer. Orca's docs describe orchestration as a structured multi-agent layer (experimental) whose core model includes:

  • Run: a durable namespace and coordinator inbox
  • Task: a work item with a spec, dependencies and status, composable into a DAG
  • Dispatch: one execution attempt of a task on a terminal
  • Message: messages such as worker_done, escalation, question, heartbeat
  • Decision gate: a question created by the coordinator that blocks the related task until a decision is recorded

The worker contract includes: send exactly one worker_done with the outcome, success or failure; attach a summary of what was done, what was found and what remains; send heartbeats during long work; ask blocking questions through the coordinator instead of waiting locally.

3. Humans guard the gates. Put gates on irreversible or high-risk steps: merging shared components, database migrations, releases. The X developer sharing Orca usage gives an example: before release, one agent acts as project manager leading two agents reviewing frontend and backend separately, and the human only reads the final summary; the database migration step has a gate where a human must decide.

Engineering Practice and Numbers

  • Make completion signals structured: Orca requires completion messages to carry both the task ID and the dispatch ID, so a stale retry can't wrongly complete another task.
  • The orchestrator is itself an agent: the developer above notes Orca serves agents as well as humans — agents can open new workspaces and read errors from other panes, and the "project manager" uses exactly these capabilities to assign work and collect results.
  • Start small: Anthropic warns LLM agents are not yet great at real-time coordination and delegation; pilot with two or three workers on well-bounded tasks.

Common Misconceptions

  • "With an orchestrator, humans can step out entirely." High-risk decisions still need a responsible human; gates are part of the design.
  • "The more complex the orchestration, the stronger." Every layer adds tokens and failure points; add them as needed.
  • "If a worker says it's done, it's done." Completion is determined by verification results, not the agent's self-report.
