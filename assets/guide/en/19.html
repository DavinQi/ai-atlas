From Completion to AI IDEs: Models Entered the Cursor, Then the Editor

Companion to diagram #19 · Chapter 3 "The Evolution of Programming"

AI entered development tools in two steps. The first was completion at the cursor: predict the next line or block from the current file and cursor position. The second was the AI IDE: the model stops staring at the cursor and can understand the whole project, edit across files, and explain and refactor code in chat. Both share one thing: the human still leads every change inside the editor, and AI is the co-pilot.

Rather than retelling the history, this article works through three questions. What is a completion model actually doing? What does an AI IDE add on top of completion? And does it really make people faster?

Question 1: what is a completion model doing?

Completion is the next-token prediction from Chapter 1, with code as the corpus. OpenAI's 2021 Codex paper introduced GPT models fine-tuned on public GitHub code and stated that a production version powers GitHub Copilot. It also released HumanEval: 164 hand-written programming problems, each giving a function signature and docstring; the model writes the body, and unit tests decide whether it is correct.

Here is what that looks like. The editor sends the text before the cursor to the model as the prompt:

def is_palindrome(s: str) -> bool:
    """Return whether s is a palindrome, ignoring case and non-alphanumeric characters."""

The model continues with the function body. The signature, type hints, docstring and even variable names are all clues. Clear comments and names are themselves prompts. That is why the same completion tool does noticeably better in a well-kept codebase.

Why do completion tools often offer several candidates? The Codex paper found that with a single sample the model solved 28.8% of HumanEval problems; with 100 samples per problem, counting a problem as solved if any sample passed, the figure rose to 70.2%. In other words, the right answer is often "in" the model's distribution but not necessarily the first one sampled. Offering several candidates for a human to choose from exploits exactly this; later agents use tests to choose automatically, replacing "the human picks" with "the machine picks".

One easily overlooked detail: completion context goes far beyond the current file. Real completion systems put code before and after the cursor, other open tabs and relevant snippets from neighbouring files into the prompt. As Chapter 1 explained, the model only knows what is in its context, so choosing what goes in is the key engineering problem for completion quality.

On 29 June 2021 GitHub launched the Copilot technical preview, saying it worked especially well for Python, JavaScript, TypeScript, Ruby and Go — languages with a great deal of public code, consistent with "model ability comes from training data".

Question 2: what does an AI IDE add?

Completion answers "what do I write next?"; an AI IDE answers "how should this be changed?" It adds three things:

  1. Chat: ask about, explain or generate code for a selection or the whole project — "why does this function throw on an empty list?" rather than only "continue".
  2. Multi-file edits: one change can span several files and is shown as a diff. Adding a field to an API means changing the data model, serialisation, API docs and tests together.
  3. Project-level context: index the codebase and retrieve relevant files on demand, so the model can find every caller when it changes an interface.

From completion to AI IDE, the unit of human review grows from a line to a diff. Whether one line is right you can tell at a glance; whether a five-file diff is right requires actually understanding it. Review cost rises, which foreshadows why the next generation had to bring in automated verification.

Rule files keep the model following team conventions. Every session starts from scratch; the model will not remember that you told it last week "this project uses pnpm, not npm". The fix is to write conventions into repository files that load automatically. Cursor's docs explain that rules provide persistent, reusable context at the prompt level; project rules live in .cursor/rules under version control, and AGENTS.md is supported as a simpler alternative. AGENTS.md describes itself as "a README for agents", and its website says more than 60,000 open-source projects use it. Claude Code reads CLAUDE.md.

A good rule file covers the stack and versions, build and test commands, the parts of the style models tend to get wrong, and things never to do. More rules are not better: they take up context and dilute the important points. Add a rule when the model keeps making the same mistake.

The boundaries are blurring. GitHub Copilot's docs now cover agent mode in the IDE, a CLI, and a coding agent that works asynchronously in the cloud and can open or update PRs for review. "Completion tools" and "agent tools" are increasingly modes of one product.

Question 3: does it really make people faster?

This is where intuition misleads most. Two rigorous randomised controlled trials reached seemingly opposite conclusions.

Trial A: 55.8% faster. In a 2023 Copilot RCT, developers implemented an HTTP server in JavaScript; the Copilot group finished 55.8% faster than the control group.

Trial B: 19% slower. METR's 2025 RCT had 16 experienced open-source developers complete 246 real tasks in mature projects they had maintained for years. Each task was randomly assigned to "AI allowed" (mainly Cursor Pro with Claude 3.5/3.7 Sonnet) or "AI not allowed". With AI allowed, completion time rose by 19%. Developers had expected a 24% reduction beforehand and still believed afterwards that they had been 20% faster.

The studies do not contradict each other; the settings differ:

Trial A Trial B
Task Well-bounded greenfield task Maintenance tasks in real projects
Codebase From scratch Large codebase the developer knows intimately
Quality bar Passing the tests The project's long-standing implicit standards

On a bounded task from scratch, the model's "average code" is good enough. In a large project full of implicit conventions that the developer knows by heart, the time spent understanding, prompting, waiting for, reviewing and fixing AI output can exceed the time to just write it. Gains depend heavily on task type, codebase familiarity and the quality bar.

The bigger lesson: subjective impressions are unreliable. Developers in Trial B felt faster while actually being slower. Judge AI tools by objective delivery metrics, not surveys (see "Metrics" in Chapter 4).

Practical points

  • Review AI-generated diffs as you would a colleague's PR; do not accept them blindly.
  • Commit rule files to Git so the team shares, reviews and evolves them.
  • Give the model good clues: clear names, types and comments are the cheapest prompt engineering.
  • Measure in your own setting instead of borrowing someone else's speed-up percentage.
