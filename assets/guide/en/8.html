Inference and Serving: Prefill Once, Decode Token by Token

Companion to diagram #8 · Chapter 1 "How LLMs Are Trained"

Overview

LLM inference has two phases:

  • Prefill: the whole prompt goes through the model in parallel, computing K/V for every position and producing the first token. This phase is compute-bound and sets time-to-first-token (TTFT).
  • Decode: each step feeds only the previously generated token, reads the cached K/V, and produces the next token until done. Every step reads all weights and the KV cache, so it is memory-bandwidth-bound and sets per-token latency.

As Leviathan et al. put it, decoding K tokens takes K serial runs of the model. Nearly every inference optimization pursues two goals: make memory access cheaper, and make each access serve more requests or produce more tokens.

Core Mechanisms

1. KV cache. In causal attention, past K/V never change, so they can be cached instead of recomputing the whole prefix each step. Cache size per token:

bytes/token=2×L×nkv​×dhead​×b

(2 for K and V; L layers; nkv​ KV heads; dhead​ dimension per head; b bytes per value.) For Llama 3 70B (80 layers, 8 KV heads, hidden size 8192 / 64 heads = 128 per head), FP16 gives 2×80×8×128×2=327,680 bytes ≈ 320 KB per token; a 128K-token context needs about 40 GB for the KV cache alone.

2. Compressing KV. GQA lets several query heads share KV heads; Llama 3 pairs 8 KV heads with 64 query heads, cutting KV to 1/8. DeepSeek-V2's Multi-head Latent Attention (MLA) compresses KV into a latent vector, reducing the KV cache by 93.3% and raising maximum generation throughput 5.76× relative to DeepSeek 67B.

3. PagedAttention and continuous batching. The vLLM paper measured that in existing systems only 20.4%–38.2% of KV-cache memory actually stores token states; the rest is lost to reservation and fragmentation. PagedAttention borrows OS-style paging: KV cache is split into fixed-size blocks allocated on demand, nearly eliminating waste and allowing blocks to be shared across sequences. Throughput improves 2–4× at the same level of latency.

4. Mixture of Experts (MoE). Replace the FFN with many "experts" and let a router choose a few per token. The idea traces to Shazeer et al.'s 2017 sparsely-gated MoE layer; Switch Transformer simplified routing to a single expert per token and reported up to 7× faster pretraining at equal compute.

  • Mixtral 8x7B: 8 experts per layer, 2 selected per token; 47B total, 13B active parameters.
  • DeepSeek-V3: 671B total, 37B activated per token.

MoE reduces compute per token, not memory: all expert weights must be loaded.

5. Other techniques.

  • Quantization: GPTQ quantizes the weights of a 175B model to 3–4 bits in about four GPU hours with negligible accuracy loss; AWQ protects a small set of salient weights based on activation statistics.
  • Speculative decoding: a small model drafts several tokens and the large model verifies them in one parallel pass, leaving the output distribution unchanged; the paper reports 2–3× speedups on T5-XXL.
  • FlashAttention: the standard kernel for prefill and long contexts.

Engineering Practice and Numbers

  • Memory = weights + KV cache + activations. A 70B model's FP16 weights are about 140 GB (70B × 2 bytes), plus a KV cache that grows linearly with concurrency and context length.
  • Throughput vs. latency. Bigger batches let each weight read serve more requests, raising throughput but increasing per-request latency.
  • Reusing long prompts: KV blocks for shared prefixes (system prompts, RAG documents) can be reused; PagedAttention's block sharing is designed for exactly this.
  • Framework choice: open-source engines such as vLLM already integrate PagedAttention, continuous batching, quantization and speculative decoding — build on them for self-hosted serving.

Common Misconceptions

  • "A 671B MoE model deploys with the memory of a 37B model." Compute follows active parameters; memory must still hold all parameters.
  • "Longer context only costs linearly more." The KV cache grows linearly, but prefill attention compute grows quadratically with length.
  • "Quantization always hurts badly." 4-bit weight quantization usually costs little on large models, but evaluate on your own tasks.
