Inference and Serving: Prefill Once, Decode Token by Token

Companion to diagram #8 · Chapter 1 "How LLMs Are Trained"

Training happens once; inference happens hundreds of millions of times a day. Whether a model is pleasant and affordable to use is decided largely at inference. Diagram #8 splits inference into three parts: at the top, the prefill and decode phases and the KV cache that connects them; in the middle, three serving techniques (quantisation, continuous batching, PagedAttention); at the bottom, MoE routing. This article first explains "why is generating text so slow?", then shows which bottleneck each technique attacks.

1. Two phases, two bottlenecks

When you press Enter in a chat box, the model does two very different things.

Prefill: the whole prompt goes into the model in parallel, computing K/V for every position and producing the first token. Thousands of tokens are multiplied in matrices at once, using the GPU's compute fully, so this phase is compute-bound and determines time to first token (TTFT).

Decode: from then on each step inputs only the single token generated in the previous step, reads the cached K/V, and generates the next token, until done. Leviathan et al. put it bluntly: generating K tokens requires running the model serially K times. Each step computes little but must read all the weights and the KV cache from memory once. The GPU spends most of its time waiting for data, so this phase is memory-bandwidth-bound and determines per-token generation speed.

For scale: a 70B model's FP16 weights are about 140 GB (70B × 2 bytes). Serving one request at a time, every generated token means reading those 140 GB once. That's why almost every inference optimisation revolves around two things: make each memory read cheaper, and make each memory read serve more requests or produce more tokens.

2. The KV cache: trade memory for compute

In causal attention, the K/V of past positions never change once computed. Rather than recompute the whole preceding text for every new token, cache them. The cost is memory; the cache size per token is:

bytes/token=2×L×nkv​×dhead​×b

The 2 is for K and V, L is the number of layers, nkv​ the number of KV heads, dhead​ the dimension per head, b bytes per number. For Llama 3 70B (80 layers, 8 KV heads, 128 dimensions per head, FP16): 2×80×8×128×2=327,680 bytes, about 320 KB per token. A 128K-token context needs about 40 GB for the KV cache alone; serving 10 such requests at once takes 400 GB, far more than the weights.

The real bottleneck of long context is often the KV cache, not the weights. So compressing KV has been a main thread of recent architectural evolution:

  • GQA: several query heads share one set of KV heads. Llama 3 70B pairs 8 KV heads with 64 query heads, cutting KV to 1/8. With standard multi-head attention, the 320 KB above would be about 2.5 MB.
  • MLA: DeepSeek-V2's multi-head latent attention compresses KV into a low-dimensional latent vector, reducing the KV cache by 93.3% compared with DeepSeek 67B and raising maximum generation throughput to 5.76×.

3. The serving trio: make one read serve more requests

Continuous batching. Put several requests in one batch, and one read of the weights computes a token for each, multiplying throughput. Traditional static batching waits for the longest request in a batch to finish before admitting new ones; continuous batching lets finished requests leave and new ones join at every step, so the GPU never idles. The cost: bigger batches mean higher latency per request, so throughput and latency must be balanced to the use case.

PagedAttention. The batch ceiling depends on how much KV cache fits in memory. The vLLM paper measured that in existing systems only 20.4%–38.2% of KV cache memory actually stored token state; the rest was wasted on "reserve for maximum length" and fragmentation, because nobody knows in advance how long an answer will be. PagedAttention borrows virtual-memory paging from operating systems: split the KV cache into fixed-size blocks allocated on demand, logically contiguous but physically scattered, almost eliminating waste. It also supports sharing blocks between sequences: when many requests share the same system prompt or RAG document, the prefix's KV is stored once. At the same latency, throughput improves 2–4×.

Quantisation. Compressing weights from 16 bits to 8 or 4 cuts memory use and bytes read per step proportionally, striking right at decode's memory bottleneck. GPTQ can quantise a 175B model's weights to 3–4 bits in about 4 GPU-hours with negligible accuracy loss; AWQ observes that a small fraction of weight channels are especially sensitive to activations and protects those key weights based on the activation distribution. 4-bit weight quantisation usually costs little on large models, but evaluate on your own tasks.

4. Speculative decoding: verify several tokens at once

If decode's bottleneck is "every token needs one serial run of the big model", can we produce several at a time? Speculative decoding has a small model quickly draft k tokens, then the big model verifies all k positions in one parallel forward pass, accepting the prefix consistent with its own distribution and replacing the first inconsistent token with its own. It is mathematically guaranteed that the output distribution is identical to using the big model alone, not an approximation. The better the small model guesses, the more tokens are accepted per pass; the paper reports 2–3× speed-ups on T5-XXL.

5. MoE: many parameters, only a few used each time

Mixture of experts (MoE) replaces the Transformer's FFN with several "experts", and a router chooses a few experts per token to compute. The idea comes from Shazeer et al.'s 2017 sparsely gated MoE layer; Switch Transformer simplified it to routing each token to just 1 expert, speeding up pretraining by up to 7× at the same compute.

  • Mixtral 8x7B: 8 experts per layer, 2 chosen per token; 47B total parameters, 13B active per token.
  • DeepSeek-V3: 671B total parameters, 37B active per token.

In the diagram the router picks E2 and E5 (a top-2 illustration). Keep MoE's benefits and costs apart: it reduces compute per token, so training and inference FLOPs follow the active parameters; but it does not save memory: all expert weights must be loaded, so a 671B model still needs memory for 671B. There are also engineering problems such as expert load imbalance and cross-GPU communication.

6. The last step of generation: pick one from the probability table

At each step the model outputs a probability table, and how you pick a token from it affects output quality. Suppose after "He was thirsty, so he drank a glass of" the model gives water 69%, tea 25%, book 6%:

  • Greedy always picks the top one, "water": stable but prone to monotony and repetition.
  • Temperature divides the scores by the temperature before softmax: at 0.5 the distribution becomes about 88% / 12% / 0.7%, more concentrated and conservative; at 2 it is about 53% / 32% / 16%, more varied and more error-prone.
  • Top-p (nucleus sampling) accumulates probability from highest to lowest and stops at p: with p=0.9, water + tea = 94% already exceeds 90%, so it samples only between those two at 73% / 27%, excluding "book". Unlike top-k, which always keeps k candidates, the number kept adapts to the situation.

Holtzman et al. found that in open-ended writing, always chasing the most likely text often produces bland, repetitive text that can fall into loops, which is why nucleus sampling was proposed. Use low temperature for code and information extraction, higher for writing and brainstorming. But remember: sampling only picks among the probabilities the model gives; it can't change the model's ability.

7. A checklist for deployment arithmetic

  • Memory = weights + KV cache + activations. The KV cache grows linearly with concurrency and context length and is often the real ceiling.
  • Long context costs more than linearly. The KV cache grows linearly, but prefill attention grows with the square of length.
  • Reuse shared prefixes. Put system prompts and RAG documents in fixed positions so prefix caching hits.
  • Prefer mature engines. Open-source engines such as vLLM already integrate PagedAttention, continuous batching, quantisation and speculative decoding.
  • Don't be misled by MoE's active parameters. For a model with 671B total and 37B active, estimate compute at 37B and memory at 671B.
