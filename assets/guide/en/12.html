Three Paradigms: Think While Acting, Plan Then Execute, Self-Correct Afterwards

Companion to diagram #12 · Chapter 2 "Agent Design: Principles & Patterns"

Same model, same tools, organised differently, and an agent's reliability, cost and explainability can be completely different. Diagram #12 shows the three most common paradigms side by side: ReAct, a small loop of thought, action and observation; Plan-and-Execute, where a planner breaks out the steps and an executor completes them one by one; and Reflection, which evaluates the result afterwards and carries the feedback into the next attempt. They don't replace one another; they answer three different questions: what should I do next? How should the whole job be split? How do I improve after a mistake?

To see the differences, one task runs through the whole article: "Fix issue #123: the service returns 500 when users upload avatars larger than 10 MB."

1. ReAct: one step at a time

Mechanism. Yao et al. proposed ReAct in 2022, having the LLM generate reasoning traces and concrete actions in an interleaved way. Reasoning helps the model induce, track and update plans and handle exceptions; actions let it interact with a knowledge base or environment to get new information. The loop looks like this:

Thought → Action(tool, args) → Observation → Thought → … → Final Answer

Applied to our task:

  • Thought: a 500 means the server threw an exception; look at the upload endpoint first.
  • Action: grep -r "avatar" src/api/
  • Observation: found upload_avatar(), which calls resize_image().
  • Thought: maybe large images run out of memory when resized; check the logs to confirm.
  • Action: read the recent error logs.
  • Observation: PayloadTooLarge is not caught…

Every thought builds on the previous real observation; that's its value.

Why does it work? Pure chain of thought reasons only "in the model's head", so if one intermediate fact is wrong, everything after it goes wrong. On HotpotQA question answering and Fever fact verification, ReAct, calling only a simple Wikipedia API, mitigated the hallucination and error propagation common in pure chain-of-thought reasoning, and produced solution trajectories that people find easier to interpret. Observations from the environment keep pulling the model back to reality.

Costs. Many rounds, and each round re-feeds an ever-longer history; without a global plan it easily circles locally, for example grepping the same keyword again and again. Today's mainstream coding agents are still essentially this loop, just with stronger models, more tools, context compaction and a cap on rounds.

2. Plan-and-Execute: think it through, then act

Mechanism. Wang et al.'s 2023 Plan-and-Solve targets the "missing steps" problem of zero-shot chain of thought: have the model draw up a plan, split the task into subtasks, then carry out the plan step by step; the extended PS+ adds more detailed instructions to reduce calculation errors. In experiments on ten datasets with GPT-3 it consistently beat Zero-shot-CoT. Engineering-style Plan-and-Execute follows the same idea: a planner produces a list of steps, an executor completes them one by one, and returns to the planner to replan when needed.

For the same task, the planner might produce:

  1. Reproduce: call the upload endpoint with an 11 MB image.
  2. Locate the source of the exception and add a test.
  3. Unify the size limit at the gateway and application layers, returning 413 instead of 500.
  4. Run all tests and commit.

The executor gets small, well-bounded tasks; each step can use a cheaper model, or even run in parallel (the seed of the orchestrator–workers pattern in article 5).

Advantages. A clear global structure; people can review the plan before execution; more controllable cost; dependencies between steps are obvious.

Costs. The plan is based on information available before execution. If step 2 reveals the problem is actually in the CDN configuration, step 3 of the original plan is out of date. So Plan-and-Execute must support replanning, or you get "faithfully executing a wrong plan". Nor is a more detailed plan always better: the more uncertain the environment, the more easily a detailed plan breaks.

3. Reflection: look back afterwards, with language as the gradient

Mechanism. Shinn et al.'s 2023 Reflexion doesn't update model weights; it reinforces the agent through "verbal feedback". After each attempt the agent writes a reflection based on the task's feedback signal and stores it in episodic memory; in the next attempt those reflections go into the context to improve decisions. The paper reports 91% pass@1 on the HumanEval coding benchmark, above GPT-4's 80% at the time.

Applied to our task: after the first fix, the tests still fail, and the reflection reads: "I only added a check at the application layer, but nginx's client_max_body_size rejected the request first and returned the gateway's error page. Next time, check the limits at every layer along the request path first." The second attempt carries that lesson and starts straight from the gateway configuration.

The related Self-Refine has the same LLM act in turn as generator, critic and reviser to refine output iteratively, with an average absolute improvement of about 20% across 7 kinds of task.

Key precondition: the feedback signal must be reliable. Reflexion works well on coding tasks largely because test results give objective feedback: a pass is a pass, and a failure comes with an error message. Without an external signal, just asking the model to "check itself" can be unreliable and may even reinforce the original wrong judgement. That is what the diagram means by "suited to: tasks with clear checking criteria".

4. How to choose, and how to combine

Paradigm Suited to Main cost Typical failure
ReAct Unpredictable steps, explore and decide along the way Many rounds, prone to circling Repeated local probing
Plan-and-Execute Long tasks with clear structure that can be split in advance Plans can go stale Sticking to a wrong plan
Reflection Clear checking criteria, multiple attempts allowed Extra calls each round Reinforcing errors without a signal

Real systems almost always combine them. A typical coding agent first splits an issue into steps with planning (Plan-and-Execute); within each step it uses a ReAct loop to read code, edit code and run commands; when tests fail it carries the error and a reflection into the next round (Reflection); and the whole process has caps on rounds and budget.

These paradigms also map onto Anthropic's pattern catalogue: Plan-and-Execute resembles "orchestrator–workers"; Reflection resembles "evaluator–optimiser", which works best when there are clear evaluation criteria and iteration brings measurable improvement.

5. Three common misconceptions

  • "ReAct is outdated." The core of mainstream coding agents is still the "think — call a tool — observe" loop.
  • "The more detailed the plan, the better." Detailed plans break easily when the environment changes; the key is being able to replan.
  • "Self-reflection always improves things." Without external verification, reflection may just restate the error in other words. Connect reflection to tests, type checks or real execution results and it actually works.
