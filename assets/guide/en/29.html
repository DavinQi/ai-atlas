Maintaining Code with AI Agents: A Seven-Step Loop That Is Small, Verifiable and Traceable

Companion to diagram #29 · Chapter 4 "AI Coding Today"

The previous diagram was about laying the foundation in one week. This one goes a step further: once the foundation exists, how do you actually work with an agent while maintaining a real repository day to day? It is written for two kinds of readers: people just starting with Claude Code, Codex, Cursor or Copilot, and experienced engineers who already use them but find the results hit-and-miss.

The short version: the difference between people who get a lot out of agents and people who don't is not how many commands they know. It is whether they have a closed loop. Anthropic's own best-practice guide puts it first: give the agent a check it can run itself (tests, a build, a screenshot to compare). That is the difference between a session you have to watch and one you can walk away from. Karpathy said it even more directly in his widely shared notes from early 2026: don't tell it what to do, give it success criteria and watch it go; get it to write tests first and then pass them. The seven steps below are built around that loop.

1. The seven-step loop

Step 0: a project map. Put a guide for the agent at the repository root: AGENTS.md (read by Codex, Cursor and Copilot) or CLAUDE.md (Claude Code; recent versions also read AGENTS.md when there is no CLAUDE.md). You don't have to write it from scratch. Both Claude Code and Codex have /init, which scans the repository and drafts one. Your job is to cut and add: how to install dependencies, how to run tests, directory conventions, what must never be touched.

Keep it short. The official docs name a failure pattern called "the over-specified CLAUDE.md": when the file is too long, the important rules get lost in the noise. The test is simple: if the agent would not make a mistake without a given line, delete the line. Boris Cherny, who created Claude Code, has described how his team does it: after every correction, end with "update CLAUDE.md so you don't make that mistake again", and keep pruning until the mistake rate measurably drops. The file grows out of real mistakes rather than being written as a rulebook in one go.

Step 1: read-only exploration. When you pick up unfamiliar code, the first move is not to have the agent change it but to have it explain it. Ask directly: "Where does the login request come in, and which files does it pass through?" "Who calls this function?" "Why is there a lock here?" These are the questions a new hire would normally ask a senior colleague. Ask the agent first, then check the files and line numbers it gives you with your own eyes.

Step 2: plan first. Whenever a change touches several files, you are unsure of the approach, or you don't know the code well, start in plan mode. In both Claude Code and Cursor you press Shift+Tab in the input box to switch. In plan mode the agent reads but does not write, and ends with a plan. A good plan answers three questions: which files change, in what order, and how we will prove it is right. Conversely, if you can describe the whole diff in one sentence (fix a typo, add a log line), skip the plan; the official docs say plainly that planning has overhead.

The Claude Code team's experience is to pour effort into the plan so the implementation lands in one shot, and the moment the implementation goes sideways, don't keep pushing: switch back to plan mode and re-plan. Some open a second session and have it review the plan as a staff engineer.

Step 3: small steps. Have the agent do one thing at a time. Not because it can't do big things, but because you can't review big diffs. You can read a 50-line diff line by line; with a 2,000-line diff you will just click accept. The typical mistakes Karpathy describes live exactly there: making wrong assumptions on your behalf and running with them, overcomplicating code, changing comments and code it doesn't understand as a side effect. With small steps, each of these surfaces at the step where it happens.

Step 4: run the checks. This is the heart of the loop, marked in orange on the diagram. Put "run the tests, the build and the linter" into the task itself, and let the agent read the results and fix things until they pass. Then ask it for evidence: the command it ran and what it returned, not just "done". Reviewing evidence is much faster than re-running everything yourself.

Step 5: review the diff. Only after the machine's gates pass is it a person's turn. You are not reading for syntax. You are looking for changes outside the task, deletions that shouldn't have happened, and simpler ways to do the same thing. A favourite move on Boris's team is to make the agent quiz you: "Grill me on these changes and don't make a PR until I pass." Or, after a mediocre fix: "Knowing everything you know now, scrap this and implement the elegant solution." Another option is to open a clean session or a subagent whose only job is to find faults. The context that wrote the code should not be the one judging it.

Step 6: commit and open a PR. Have the agent write a clear commit message and open the PR, then let CI guard the gate once more. At Anthropic, the first round of review on every PR is done by Claude, running non-interactively as claude -p inside a GitHub Action; the Codex equivalent is codex exec. By the time a person opens the PR, the low-level issues have already been filtered once.

2. Applying it to four common jobs

Fixing a bug. Have the agent write a test that reproduces the problem, confirm that the test fails, then fix until it passes. "Fails first" matters: a test that has never failed proves nothing. Paste logs, stack traces and CI output in directly; they are more accurate than your paraphrase. Boris's team sometimes just says "go fix the failing CI tests" and doesn't prescribe how.

Refactoring. First add tests that pin the current behaviour, then change things in batches. Run the tests and commit after each batch so you can roll back precisely. Remind the agent explicitly that behaviour must not change, and watch in review for any "improvements" it slipped into the business logic.

Upgrading dependencies. Have it read the changelog of the target version and list the call sites that might be affected, then bump one dependency at a time and run the full suite after each. Bundling several major upgrades into one PR is the hardest thing to review and the hardest to roll back.

Writing docs. Let the agent read the code and draft the README, API notes or architecture notes, and check the facts yourself. Agents write docs fast, but they will also state plausible-sounding things as fact, so anything involving version numbers, commands or defaults should actually be run.

3. The few moves worth memorising

Every tool has many commands, and they change quickly. In day-to-day maintenance only a handful are used constantly, and the ideas carry across tools:

Move What it does Where
/init Scan the repo and draft the project guide Claude Code (CLAUDE.md), Codex (AGENTS.md)
/clear Empty the context when you switch tasks Claude Code
/compact Summarise a long session and keep going Claude Code, Codex
Shift+Tab Switch to plan mode: read and plan only Claude Code, Cursor
@file Put a specific file into context Claude Code, Cursor and others
/review Review the current uncommitted changes Codex (Claude Code's equivalent is /code-review)
claude -p / codex exec Run non-interactively, for scripts and CI Claude Code, Codex

Two more keys worth knowing in Claude Code: Esc interrupts at any time so you can redirect, and pressing Esc twice (or /rewind) takes you back to an earlier checkpoint.

The most underrated of these is /clear. Two of the most common failure patterns in the official docs come down to it. One is the "kitchen sink session": you do A, ask about B, then go back to A, and the context fills with irrelevant material. The other is "correcting over and over": wrong, corrected, still wrong, and the context fills with failed attempts. The fix is the same: if it is still wrong after two corrections, /clear, fold what you learned into a better first prompt, and start again.

4. Conventions that let a whole team trust it

  • Rule files live in the repo. AGENTS.md, CLAUDE.md, .cursor/rules/ and .github/copilot-instructions.md are reviewed and evolved together with the code. Personal preferences go in a local file (for example CLAUDE.local.md), not in the team's rules.
  • One task, one branch. The agent's changes always live on a branch and arrive through a PR; never let it push to main.
  • Tests first. A bug fix starts with a failing test; a refactor starts with tests that pin behaviour.
  • Small diffs. One PR solves one problem. If you can't review it, don't merge it.
  • Keep secrets out of context. Don't paste .env files, tokens or production credentials into the conversation. Keep high-risk commands (deleting data, changing permissions, pushing to production) behind human confirmation; don't open everything up just to save clicks. Codex's --sandbox and --ask-for-approval and Claude Code's /permissions exist to draw that line.
  • Review evidence. "Done" without test output or a screenshot is not done.

5. Prompt templates you can copy

Understanding code:

Don't modify any files yet. Read src/auth/ and tell me where the login
request enters, which functions it passes through, and where the session
is stored. Give a file and line number for every claim.

Fixing a bug:

Problem: <paste the error / logs>.
First write a test that reproduces it, run it and confirm it fails. Then
fix the root cause; don't make the error go away by swallowing exceptions.
Finally run the full test suite and paste the commands and output.

Refactoring:

Goal: extract the price calculation in OrderService into its own module,
with behaviour exactly unchanged. First check that existing tests cover
price calculation and add tests if they don't. Then change it step by step,
running the tests after each step. Don't touch unrelated code.

Reviewing:

Review the changes on this branch against main as a senior reviewer: list
behaviour changes, missing tests, and places that could be simpler. Only
list issues; don't edit anything.

6. Two tracks for getting better

Beginner track: one session, one task, read every diff. For the first two weeks, aim for understanding, not speed. Always go explore → plan → small step → run checks → read the diff → commit. Every time the agent trips you up, add the lesson to the rule file. Treat the agent as a capable new colleague who tends to assume things: it does the work, you sign it off. The Claude Code team also suggests switching the output style to "Explanatory" or "Learning" so it explains why it makes each change, which is one of the fastest ways to learn an unfamiliar repository.

Intermediate and advanced track: parallelise, reuse, automate.

  1. Parallelise. The Claude Code team's single biggest productivity tip is to run 3–5 git worktrees at once, each with its own session on an unrelated task (Claude Code's claude -w <name> starts a session directly in a worktree). It only pays off if the tasks really are independent and you can keep up with the reviews; Chapter 5 covers the costs.
  2. Reuse. Anything you do more than once a day becomes a custom command or skill, committed to the repo for the whole team (in Claude Code, under .claude/skills/ or .claude/commands/). When you need a dedicated role, define a subagent (.claude/agents/), such as a read-only code reviewer. Subagents have their own context, which also keeps the main session clean.
  3. Connect. Use MCP to wire in your issue tracker, logs and a browser, so the agent gathers evidence itself instead of you copying and pasting.
  4. Deterministic gates. A rule in a prompt can be forgotten; a rule in a hook runs every time, for example formatting and linting after every edit.
  5. Agents in CI. Use claude -p or codex exec in the pipeline for a first round of review, or assign an issue directly to Copilot's coding agent and have it come back with a PR for you to review.

Both tracks end in the same place: less of your time goes into writing, more into defining the problem and accepting the result. Karpathy's warning is worth keeping in mind: these models' mistakes are no longer syntax errors but the conceptual errors of a slightly sloppy, hasty junior developer. Hold the verification gate and you have a helper that never gets tired. Let go of it and the agent will confidently amplify the mistakes.
