Hands-on Playbook: How Senior Engineers Use AI Agents on Real Full-Stack Maintenance

Companion to diagram #29 · Chapter 4 "AI Coding Today"

This is written for people who already own a system. Your question is no longer "how do I get it to write a function?" but, facing a legacy codebase that spans frontend, backend, data and deployment, "how do I plug an agent into my existing engineering discipline" — letting it do the legwork and the exploring without letting it bypass your architectural constraints, test contracts and review process. The examples are full-stack throughout: one requirement usually touches the API, the database, frontend state and CI at the same time, and the seams between those layers are exactly where agents fail.

0. Five-minute alignment: the minimal loop

If you have no habits yet, memorise one chain; everything below is an elaboration of it: rule file first → read-only exploration → spec/plan → small steps → machine verification → human diff review → PR and CI. One branch and one session per task; if it is still wrong after two corrections, clear the context and start over; "done" without test output is not done. Beginners should keep asking why; senior engineers put their effort at the two ends — constraints and acceptance criteria up front, evidence and review at the back. The rest of this article assumes you can do this and focuses on scale, automation, and staying in control in a large codebase.

1. Context engineering: the right information, not the most information

Anthropic's Effective context engineering for AI agents states the problem clearly: context is a finite resource with an "attention budget", and the more tokens you add, the worse the model's recall of what is in there — context rot. So the senior move is not to stuff the whole repository in; it is to layer it, fetch on demand, and keep it disposable.

Layer 1: the root rule file holds only invariants. AGENTS.md / CLAUDE.md contains what is true everywhere: how to install dependencies, how to run tests and builds, directory and layering conventions, and prohibitions (never edit migration files, never bypass the auth middleware, and so on). Rule of thumb: if deleting a line would not cause a mistake, delete the line. Anthropic's own best-practice guide names "the over-specified CLAUDE.md" as a classic failure mode — the longer the file, the more the critical constraints drown.

Layer 2: shard by directory. A large repo should not be governed by one giant file. Put local conventions in per-directory rule files (idempotency rules for the payments module, component conventions for the frontend) so the agent loads them only when it enters that code. Claude Code loads CLAUDE.md files from subdirectories on demand, Cursor scopes .cursor/rules/ by file pattern, Copilot reads .github/copilot-instructions.md plus the nearest AGENTS.md. The mechanisms differ; the idea is the same: global rules state invariants, local rules stay local.

Layer 3: personal preferences and secrets never enter committed rules. Local overrides (e.g. CLAUDE.local.md) hold personal habits; tokens, internal addresses and production details are never written anywhere the model will read and git will keep.

Let rules grow out of corrections. The practice the Claude Code team is most often quoted for: after every correction, add "write this into the rule file so it doesn't happen again", then prune regularly. Rules then carry the scars of real incidents instead of reading like a constitution written in one sitting. Pair this with periodic audits: delete rules that have not fired in a month, and promote anything you keep reminding it about into a hook or a test (next section). Whatever a machine can enforce should not live in a prompt.

Concrete budget moves:

  • Just-in-time retrieval, not pre-loading. Let the agent search for files and read only the fragments it needs; read big files by range; look at log tails and filtered output. Anthropic calls this just-in-time context: keep identifiers (paths, queries, links) in context and fetch the content when needed.
  • Isolate dirty work in subagents. Wide searches, reading forty files to find a call chain, an independent review pass — these burn large amounts of intermediate tokens. Delegate them to a subagent (Claude Code's .claude/agents/, or simply instructing "use a subagent to investigate") so the main session receives only a one-to-two-thousand-token conclusion. On Boris Cherny's team this is the main technique for keeping the primary context clean.
  • Compact long sessions deliberately. Near the limit, use /compact with a focus ("keep architectural decisions, unresolved failures, and the list of files changed; drop tool outputs"). More robust than compaction is externalised notes: keep the plan, decisions and progress in PLAN.md / NOTES.md inside the repo. Context can be thrown away; the file survives, and a fresh session reads it and continues.
  • /clear when you switch tasks. Two of the most common failure patterns in the official docs — the "kitchen sink session" and "correcting over and over" — both come from not clearing. Two failed corrections mean your first prompt was missing information; rewriting it with the lesson included is cheaper than coaxing a polluted context.

2. Parallel agents and long-running tasks: worktrees, orchestration, checkpoints

Parallelism is the most-cited productivity unlock, and also the fastest way to multiply your review debt. The Claude Code team's published practice is 3–5 git worktrees at once, each with its own session; Claude Code's claude -w <name> starts a session directly in a worktree. Three things matter in practice:

  1. Tasks must be genuinely independent. Good candidates: bugs in different modules, competing design explorations, writing tests separately from fixing the implementation. Bad candidate: a refactor where one person must make sequential decisions along a single call chain — splitting it only manufactures merge conflicts.
  2. Worktrees isolate files, not runtime. Ports, databases, caches and secrets are still shared. When running full-stack services in parallel, give each worktree its own port range and test database (or schema), and write it in the rule file. Otherwise you will spend an afternoon chasing a "ghost bug" that is actually another agent's server answering your requests.
  3. Pick the orchestration pattern per task. Four common shapes: fan-out exploration (several subagents investigate, one summary), racing (two or three attempts at the same task, keep the cleanest diff), pipeline (explore → implement → review as separate roles), and lead-and-workers (the main session holds the plan, subagents do the work). The senior consensus: the number of parallel agents is set by your review bandwidth, not by your quota. If you can't review it, drop to two.

For long tasks (hours, multiple sessions), keep state in files, not in the conversation:

  • SPEC.md: goal, explicit non-goals, the interface contract, acceptance criteria as an executable checklist.
  • PLAN.md: steps with status; tick each off and commit when done. Git commits are your checkpoints — rolling back to the last green commit is far more reliable than asking the conversation to "undo that".
  • Resume protocol: a new session's first instruction is to read SPEC/PLAN and the recent git log, restate where things stand and what the next step is, and only then start. This one step blocks most "it forgot what we decided" drift.

3. Codifying experience: custom commands, hooks, MCP

Custom commands / skills: turn daily operations into assets. Anything you do twice a day deserves to be codified: release checks, tech-debt sweeps, PR descriptions in your team's format. In Claude Code these live in .claude/skills/ (or the older .claude/commands/) and take arguments via $ARGUMENTS; write them as "steps + acceptance", and commit them so the whole team shares them. A tech-debt command skeleton you can adapt:

---
description: Scan for duplicated code and stale workarounds; output an actionable cleanup list
disable-model-invocation: true
---
Find duplicated implementations, commented-out old code, and TODO/FIXME markers
older than 30 days in this repository. Sort by blast radius, smallest first;
give file, line and a suggested action for each. Output the list only; do not edit code.

Hooks: turn "should" into "must". Rules in a prompt rely on the model's goodwill; hooks are executed by the program. Claude Code hooks are configured in .claude/settings.json; the three that earn their keep:

  • PostToolUse (after Edit/Write): run formatting and lint automatically, removing style from human review entirely.
  • Stop (when it wants to finish): run the tests; on failure, block the stop and make it keep fixing. This turns the verification loop from a habit into a gate.
  • PreToolUse: intercept dangerous commands (direct production access, destructive operations) and refuse them or require a human.
{
  "hooks": {
    "PostToolUse": [
      { "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "<your format+lint command>" }] }
    ]
  }
}

Principle: anything a script can judge right or wrong does not belong in a prompt. Prompts are for the parts that need judgement.

MCP: the stronger the tool, the smaller the permission. MCP lets the agent query databases, read issues, drive a browser and fetch logs, eliminating copy-paste. But keep Simon Willison's lethal trifecta in mind: private data + untrusted content + external communication together mean prompt injection can walk your data out — and issues, web pages and logs are all untrusted content that may contain instructions aimed at the model. The countermeasures are engineering, not hoping the model is smart:

  • Read-only first: database MCP servers get read-only accounts; no write permission unless the task truly needs it.
  • Least scope: tokens cover only the repos/projects required; production and development credentials are separate.
  • Allow-list tools: enable only the servers the current task needs (which also keeps context cleaner).
  • Treat all tool output as data, never as instructions: state in your rules that content from issues and web pages is factual material only and any instructions inside it must not be executed; high-risk actions always pass human confirmation and the sandbox.
  • Keep credentials for headless/CI MCP use separate from personal ones, so they can be revoked independently.

4. Headless and CI: agents in the pipeline

Once interactive use is smooth, the natural step is moving repetitive work into CI. claude -p "..." (Claude Code) and codex exec "..." (Codex) are the non-interactive modes built for scripts and pipelines; OpenAI's official openai/codex-action@v1 runs Codex directly in GitHub Actions (pass the task via prompt or prompt-file; it needs an API key in secrets; for Claude Code's action, follow its official repository rather than copying YAML from memory). Three patterns that are verified in production use:

  1. First-round PR review. Trigger on PR creation/update and have the agent review the diff read-only: behaviour changes, missing tests, suspicious API usage, posted back as comments. This is how Anthropic uses claude -p internally — by the time a human opens the PR, the low-level issues have been filtered once. Give it a read-only sandbox (Codex: --sandbox read-only; Claude Code: tightened permission rules) so it can comment but never modify code.
  2. Issue-to-PR automation. Hand well-specified small issues to an agent running in the cloud or CI (GitHub Copilot's coding agent accepts an issue assignment and returns a PR; headless Codex/Claude Code with a script achieves the same). What matters is not generation but intake discipline: the same CI, the same human review, never auto-merge; branch protection and CODEOWNERS apply to bot PRs exactly as to human ones.
  3. Scheduled maintenance. Nightly dependency patrols, flaky-test triage, docs-versus-code drift checks — producing issues or PRs, never commits to main.

Headless permission discipline is stricter than interactive, because nobody is there to click "approve": encode the boundary in sandbox and approval policy — read-only tasks stay read-only, write access is confined to the workspace, and bypass flags such as --dangerously-skip-permissions belong only in disposable, isolated environments holding no real secrets. Set cost guardrails too: maximum turns/budget per task with automatic stop, so a runaway loop cannot burn a night's quota.

5. Verification strategy: the line between senior and amateur

Tests are the contract, not theatre. Specify acceptance in executable form when you assign work: which existing tests must stay green, which new tests the new behaviour needs, what the edge cases are. The standard bug-fix motion is a failing reproduction test first (red), then fix to green; before a refactor, pin current behaviour with characterization tests. For pure functions and protocol layers, property-based tests (tools such as Hypothesis or fast-check) pay off: the machine generates masses of inputs against invariants, which catches "looks right" implementations far better than three hand-written examples. One level up, keep a small evals set for the agent itself: a dozen real historical tasks with acceptance scripts; run it whenever you change models, rules or tooling, and judge by pass rate rather than vibes.

A senior diff-review checklist, in order:

  1. Start with git diff --stat: is the blast radius proportional to the task? Extra files are extra risk.
  2. Read the test diff separately. The most common form of agent cheating is editing tests to fit the implementation — deleted assertions, loosened expectations, skipped failing cases. Rule: every test change needs a stated reason, or it goes back.
  3. Look at what it did not change: callers, docs, type definitions, migrations that should have moved in sync.
  4. Be suspicious of every new API, config key and field name: make it cite where it is defined (in the repo or official docs). Anything unverifiable is a hallucination until proven otherwise.
  5. Hunt over-engineering: new abstractions, new config layers, extension points for futures that may never come. Karpathy's observation is exact: models will write 1,000 lines where 100 would do. In review, ask "what can be cut?" — usually half.
  6. Check failure paths: error handling, idempotency, concurrency, permission checks — and whether a "drive-by optimisation" quietly weakened any of them.

Frequent AI failure modes are cheaper to forbid in rules than to fix in review: silently editing tests, inventing APIs from memory, refactoring unrelated code while passing by, deleting comments and validation it didn't understand, "fixing" errors by swallowing exceptions, and copy-pasting boilerplate three times instead of reusing the existing helper. Boris's team checks specifically for duplicated implementations in review and makes the agent look for reusable functions during planning — moving that step earlier beats catching it later.

6. Large and legacy systems: migrations, upgrades, cross-layer refactors

In a big codebase, the right shape is the strangler pattern: new logic takes the new path, old logic is replaced incrementally, every step reversible.

  • Pin behaviour before touching structure. For any legacy module you are about to change, first have the agent add characterization tests (even if that just snapshots current output); only when those are green may refactoring begin.
  • Mechanical transforms belong to codemods; judgement belongs to the agent. Repo-wide renames of APIs or component props should be done by AST tooling (every language ecosystem has mature codemod/jscodeshift-style tools) deterministically, with the agent handling the long tail the tool cannot parse. Asking an agent to hand-edit hundreds of files with a regex mindset is how incidents happen.
  • Databases and APIs go expand–contract. Add the new column/endpoint and dual-write (expand), migrate the data and shift reads, verify, then delete the old one (contract). A single PR that changes frontend, backend and schema together is especially dangerous with an agent: you cannot review it, and it does not know which layer it skipped.
  • Upgrade one step at a time. Have the agent read the target version's changelog and migration guide first and list affected call sites; then bump one dependency, one major version, per PR, with the full test suite and build each time. On failure, bisect which dependency and version introduced it instead of reverting everything at once. Validate the CI version matrix (runtimes, databases) in the same PR, not after it lands on main.

7. Full-stack in practice: three complete walkthroughs

Each example gives you a prompt you can paste, the verification to run, and the review points. Replace placeholders like <test> with the actual scripts your repo defines (in package.json, a Makefile or your task runner).

Example A: end-to-end feature — filter the order list by status (frontend + API + database)

Step 1: contract first, no implementation.

Do not write implementation code yet. Draft the API contract for "filter the
order list by status" into SPEC.md: request parameters, the status enum,
pagination semantics, the response for invalid parameters, and the
backward-compatibility story. Then list every layer it touches: the database
query, the API, frontend state and URL parameter sync, tests.
Put anything you are unsure about in a list of questions for me; do not guess.

Step 2: backend first, tests red first.

Implement the backend per SPEC.md. First write failing tests: every status
value, the empty result, invalid status returning 400, pagination edges.
Run them and confirm they fail before writing the implementation.
Justify any index decision on the query; do not change the response shape
of the existing order endpoints.

Verify: <test> <typecheck> <lint>, then one real request against the local service to confirm the response matches the contract.

Step 3: frontend, synced with the URL.

Build the filter UI: status lives in the URL query parameters so refreshes
and shared links restore it; loading and empty states reuse the existing
components. Add component tests for parameter parsing and request building.
Do not introduce a new state-management library.

Verify: <test> <build>, then click through it in a real browser and keep before/after screenshots as evidence.

Step 4: end-to-end and regression.

Add one e2e test: selecting a status in the UI returns the same result as
calling the API directly. Run the full test suite and build, paste a summary
of the commands and output, and finish with one sentence listing what you
did not verify.

Review points: contract versus implementation, word for word; are invalid parameters being silently swallowed by the frontend "to help"; N+1 queries or a missing index; URL parameters and component state fighting each other; any old assertion edited just to make it pass.

Example B: production-style debugging — intermittent 500s on checkout

The checkout endpoint returns intermittent 500s. Here is the last hour of
error logs and one traceId (below). Build the evidence chain only: follow
the traceId across gateway, service and database, lay out the timeline and
the first failing hop. Then list 2–3 root-cause hypotheses ranked by
likelihood, each with what would confirm or refute it.
Do not change any code until there is evidence.
<paste logs>

Once a hypothesis leads, have it reproduce locally with constructed data, turn that into a failing regression test, and only then fix. Verify: regression test goes red → green, full suite passes, and it explains why the fix does not mask the same error on other paths (for example by merely swallowing the exception). Review points: is the fix at the source or at the symptom; does the new logging/alerting make the next occurrence a five-minute diagnosis; were any unrelated configs touched on the way through.

Example C: cross-layer refactor — renaming status to state

Never let it do this in one shot. Use expand–contract across three PRs:

  1. PR1 (expand): add the new column with dual writes; the API returns both fields; the frontend still reads the old one. Write "this PR deletes nothing" into the prompt, verbatim.
  2. PR2 (switch): frontend reads the new field; the API marks the old one deprecated; a codemod rewrites in-repo references in bulk and the agent handles only the files the tool failed on.
  3. PR3 (contract): once metrics show the old field has no traffic, drop the column and the compatibility code, with rollback notes on the migration.

Verification is the same each step: characterization tests stay green, <typecheck> catches missed references, and a dual-run comparison confirms old and new fields agree. Review points: do dual writes cover every write path (including cron jobs and the other service); is there actual evidence of zero traffic before the contract PR.

8. Team governance, cost, and measurement

Review policy comes first. Add two fields to the PR template: whether an agent generated or assisted the change, and the verification evidence (which checks ran, where the output is). Accountability is explicit: the submitter owns the code; the tool takes no blame — "the AI wrote it" is never a merge argument. Changes to rule files, custom commands and hooks go through the same review as code, because they change how the whole team produces software. Tier the permissions: newcomers and bots default to read-only plus PRs; senior engineers may run parallel and headless tasks, but production sandboxes and approvals do not relax with seniority.

Cost and latency are engineering trade-offs, not mysticism. N parallel sessions cost roughly N× the tokens and N× the review. Long contexts and bloated tool sets bill continuously. Use cheap, fast models for exploration and boilerplate; reserve strong models for design and review; cap headless tasks by budget and turns; and count your own waiting time in the ledger — if you could write it in twenty minutes and the agent takes forty plus twenty of review, that is a negative-return task.

Measure outcomes, never vibes. One study every senior engineer should know: METR's 2025 randomised controlled trial (16 experienced open-source developers, 246 real tasks, in mature repositories they had maintained for an average of five years) found that allowing the then-current AI tools made completion 19% slower on average — while the developers had predicted a 24% speedup beforehand and still believed afterwards that they had been 20% faster. Know its limits: small sample, tools as of early 2025, and experts working in their most familiar code; it does not prove "AI is useless", but it decisively proves that perceived speed is not evidence. So measure at team level with delivery metrics: lead time, PR open-to-merge time, change failure rate, rollback rate, review round-trips — one cycle before and after adoption — and never with vanity metrics like "percentage of AI-written code", which only rewards bloat.

9. Failure-mode playbook

Symptom Likely cause Fix
Drifting further off with every correction Context polluted by failed attempts /clear; rewrite the prompt with the lessons as constraints and acceptance criteria
A 2,000-line diff lands at once Task never decomposed, no plan Send it back; split by layer/step into separately green commits
Tests all green, feature wrong It edited the tests to fit the implementation Review the test diff separately; forbid unexplained test changes in the rules
APIs/fields that don't exist Generated from memory, never searched the repo Require a citation of the definition; verify with typecheck and search
Works, but grotesquely over-built Default bias toward over-engineering Demand the minimal implementation first; in review, ask what can be deleted
Parallel sessions stepping on each other Tasks not independent, or shared ports/DB Split by file boundary; separate ports and test databases per worktree
Long task "forgets" earlier decisions State lives only in the conversation Externalise SPEC/PLAN as files; on resume, make it restate progress first
MCP-connected agent behaving strangely Instructions smuggled in via tool output (prompt injection) Audit against the lethal trifecta: cut permissions, disable external-communication tools, require human confirmation for high-risk actions
The CI agent occasionally causes damage Headless permissions too broad Start read-only, confine writes to the workspace, cap budget and turns, never auto-merge bot PRs

A closing note for senior engineers: an agent amplifies the engineering capability you already have. With contracts, tests and review in place, it is a tireless execution layer; without them, it will amplify the chaos with the same tirelessness. The real skill shift is moving your effort from writing to setting standards and accepting work — that is what these tools are actually for.

10. The relay baton for long tasks: Initializer + Coding Agent

The hard part of work that spans hours or days is not model intelligence; it is that every new session starts amnesiac. Anthropic's engineering post Effective harnesses for long-running agents names two failure modes: trying to do too much and leaving a half-finished mess when context runs out, and a later session glancing around and declaring victory too early. Their harness maps cleanly onto day-to-day maintenance:

Session one is the Initializer (scaffold only, no product code):

  • Write init.sh (or equivalent): one command to start local services and run a basic health check.
  • Write a structured feature list (they used JSON, every item with passes: false and executable verification steps). Explicitly forbid later sessions from deleting test entries — editing tests to go green is the most dangerous cheat on long tasks.
  • Create claude-progress.txt (or PROGRESS.md) as a running log.
  • Make an initial git commit so later sessions can recover history from git log.

Every later session is a Coding Agent (one small step):

  1. pwd → read the progress file → read the feature list → check git log.
  2. Run init.sh and do one end-to-end smoke test (open the page, send a request, confirm the core path still works). Confirm the last session did not break it before starting anything new.
  3. Pick exactly one highest-priority item with passes: false.
  4. When done: verify → flip passes → write progress → commit with a descriptive message.

This is the same idea as multi-agent work in Chapter 5 and AIOps in Chapter 6: state lives in the repo, not in the chat. On full-stack work the feature list is especially valuable — "user clicks a filter → URL updates → list matches that status" written as steps blocks half-finished cross-layer work far better than "finish the filter".

11. Rule files in practice: one contract, thin adapters

The most common friction on the ground: Codex / Cursor / Copilot read AGENTS.md, Claude Code historically read CLAUDE.md, and the two files drift until two agents disagree about ground truth. As of September 2026 Claude Code falls back to AGENTS.md when there is no CLAUDE.md in a folder (toggleable in /config). The stable senior pattern:

  • One canonical contract: root AGENTS.md holds invariants (build, test, forbidden zones, layering).
  • Thin adapters: if Claude needs extras, keep a short CLAUDE.md with only the deltas, or @-import AGENTS.md; do not maintain two full copies.
  • Directory-local rules for local concerns: payment idempotency, frontend component rules live next to that code.
  • Stay extremely lean. An Anthropic engineer publicly noted they removed ~80% of the Claude Code system prompt for newer models. Treat your rule files the same way: stronger models want heuristics and acceptance criteria, not hardcoded procedures. If the root file is longer than a screen or two, split it.

Cat Wu (Claude Code product) also draws a useful line: CLAUDE.md is your instructions to Claude; auto-memory (Memory.md) is its own scratchpad. Team conventions go in the former; personal temporary preferences go in the latter or CLAUDE.local.md.

One operable habit: after every correction, make it write the rule back (in Claude Code a line starting with # can append straight into CLAUDE.md). Then spend ten minutes a week pruning — delete rules that never fire, promote anything you keep saying out loud into a hook or a test.

12. Context and spend: the daily economising moves

Moves that show up again and again in high-engagement practitioner posts and line up with official docs:

  • One task, one session. Do not chain three unrelated requests in one long thread; /clear when you switch. This is the cheapest cost cut.
  • /compact around 60%, with a focus. Waiting until the window is full produces worse summaries. Example focus: "keep architectural decisions, unresolved failures, files changed; drop raw tool output."
  • Cheap models for exploration, strong models for decisions. Switch with /model; formatting and call-site hunting do not need the top tier the whole time.
  • Plan first. Shift+Tab into Plan, lock the approach, then implement. The Claude Code team's experience: a thorough plan often one-shots the implementation; if it drifts, switch back to Plan instead of pushing.
  • Dirty work goes to subagents. "Use a subagent to investigate X / do a security review" runs in a separate context and returns a summary — this is an explicit recommendation in Anthropic's best-practices guide.
  • Keep tool returns short. Prefer search_* over list_* for MCP and internal tools; paginate large results and offer concise|detailed. Anthropic's Writing effective tools for agents finds that too many overlapping tools and UUID-heavy payloads make agents pick the wrong tool and burn tokens.

13. Designing tools the agent will actually use

If your team is wiring databases, tickets, logs or browsers into the agent, the tools themselves are product surface. Principles that held up under Anthropic's own evals:

  • Few and sharp; do not wrap every REST endpoint. schedule_event beats list_users + list_events + create_event; search_logs beats dumping whole files through read_logs.
  • Namespace. Prefixes like jira_search / asana_search reduce collisions when ten tools are all named "search".
  • Return natural-language identifiers; minimise cryptic UUIDs. When downstream calls need IDs, expose response_format: concise|detailed.
  • When truncating, say what to do next. "Results truncated — add a filter or page" beats a stack trace.
  • Iterate with evals. Write a few dozen real tasks, run the agent loop, see which tools it mis-picks, then have the agent help rewrite descriptions — that is how Anthropic tuned their internal Slack and Asana tools.

14. Team-level evals: from "it feels worse" to actionable signal

Demystifying evals for AI agents makes a point worth tattooing on the sprint board: 20–50 real failure tasks are enough to start. You do not need a perfect suite. For a full-stack maintenance team:

  1. Mine failures from production and review. Every "agent loosened the tests", "invented an API", "skipped a migration" becomes an eval task with executable acceptance.
  2. Separate capability and regression suites. Capability suites may start with a low pass rate (a hill to climb); regression suites should sit near 100% (a tripwire). Graduate capability tasks into regression once they pass reliably.
  3. Combine graders. Deterministic checks for code (tests, types, static analysis); rubric-based model graders for behaviour; humans only at critical points. Do not overfit to exact tool-call sequences — agents often find valid alternate paths; grade outcome state.
  4. Read the transcripts. When scores stall, suspect the task or grader before you suspect the model. Several Anthropic case studies show grader fixes moving scores more than model swaps.
  5. Run evals when models arrive. Teams with a suite retune in days; teams without spend weeks clicking around.

Wire evals into CI: every change to rule files, hooks, custom commands, or model bumps runs the suite. That beats "we all feel this version is smarter".

15. Two more full-stack walkthroughs: contract drift and CI matrix upgrades

Example D: frontend/backend contract drift (OpenAPI / generated types)

Symptom: frontend TypeScript types disagree with actual backend responses; intermittent undefined in production.

Do not change business logic. First compare:
1) the OpenAPI (or proto) definition in the repo;
2) what the backend handlers actually construct;
3) the generated frontend types and their call sites.
Produce a diff table: field, which side is wrong, which pages break.
Then open one minimal PR: either fix the generation pipeline or add
contract tests (schema-validate every public endpoint's response).
Do not hand-edit generated type files.

Verify: contract tests in CI; deliberately break one field locally and confirm CI goes red. Review: was the schema loosened "to go green"; is the generate command documented in AGENTS.md.

Example E: runtime / framework major upgrade (Node, Django, Next…)

Goal: upgrade <runtime or framework> from X to Y. Constraints:
- Read the official migration guide first; list breaking changes and
  every hit in our repo;
- One major version per PR; companion dependency bumps in separate PRs;
- Run the CI matrix on both old and new (or a temporary dual matrix)
  and only switch the default when both are green;
- If database migrations are needed, use expand–contract; do not bind
  them into the same PR as the framework bump.
One commit per compatibility fix so we can bisect.

Verify: dual matrix green; smoke script on the core paths; rollback notes in the PR. Review: any any / disabled checks used as a shortcut; lockfile contains only necessary changes.

16. A senior full-stack day you can copy

A concrete daily shape that wires the mechanisms above together:

  1. Start (10 minutes): triage overnight CI and agent automation PRs; merge only what has evidence; send back anything that loosened tests.
  2. Triage: independent small tickets → headless/cloud agent opens a PR; cross-layer work → local Plan mode and a SPEC; production incidents → evidence chain first, code second.
  3. Implementation block (25–45 minutes a round): one worktree, one thing; subagents investigate; main session implements; hooks auto-lint; tests gate every stop.
  4. Review block: run your own diff through the §5 checklist; then open a clean session or subagent for adversarial review ("name the three most likely holes in this PR").
  5. Close-out: write corrections back into AGENTS.md; update progress/SPEC; for long tasks tick one feature-list item and commit; /compact if the budget is tight, or /clear when you are done.
  6. Weekly (30 minutes): prune rule files; glance at eval trends; drop unused MCP servers; stay sceptical of "feels faster" stories like the METR result — watch lead time and change-failure rate instead.

Treat the agent as a tireless execution layer and keep three things for yourself: the contract (SPEC/rules), the evidence (tests/logs), and the merge button. With those three, full-stack maintenance scales; missing one, it scales the mess at the same speed.

17. Parallel work on the ground: three work-station tickets + one read-only review ticket

The principles are above; here is a schedulable version you can rename and reuse. Still full-stack: add a create-order endpoint to an orders module (backend + DTO validation + frontend wiring + docs). What matters is not the example but how the tickets are written.

You personally write a one-page contract and put it on disk first (never leave it in chat): docs/contracts/order-create.md — path, fields, error codes, forbidden zones, acceptance signals. All three stations @-reference the same file.

Station Task Parallel? Acceptance signal
A Contract landing POST /api/orders + DTO validation Starts once the contract is pinned Target test class + manual curl
B Test backfill Boundary cases for the existing OrderService Parallel with A, but no production signature changes Touches only src/test/**
C Docs Error codes and integration examples Parallel with A/B Touches only docs/
R Read-only review Review the combined diff after merging Last Edits nothing

Senior teams add three hard constraints on top:

  • Shared contracts queue first. DTOs, migrations, public interfaces and generated code (OpenAPI types, ORM models) are serial items: merge them first, then start downstream work. Only pure tests, docs, independent modules and read-only research are truly parallel.
  • Every ticket states five things: goal, allowed paths, prohibitions, acceptance command, delivery format (file list + raw command output + one sentence on uncovered edges). Miss one and the agent invents it — rarely the way you wanted.
  • Concurrency is capped by review bandwidth. 2–4 editable agents + 1 read-only reviewer is the common sweet spot; beyond that the bottleneck is instantly you, not the model.

A root AGENTS.md can start from this skeleton (swap the build command for your stack; Spring Boot is only the example):

# AGENTS.md (excerpt)
- Build: ./mvnw -q -DskipITs test        # replace with your test/build/lint
- Never modify: **/application-prod.yml, **/prod/**, secrets and .env
- Never: upgrade dependencies unless tasked; no empty assertions; never edit generated files
- merge / rebase / force-push are human-only; agents only commit
- Style reference: the existing Controller / Service in-repo

18.1 Create the isolation

cd ~/code/shop-api

git switch main && git pull --ff-only origin main

git worktree add ../shop-agent-a -b feat/order-create origin/main

18.2 Open and prove identity

  • Cursor: File → Open Folder… — one window per worktree (a/b/c), one fresh Agent chat each; confirm the working directory is not the main repo.
  • Claude Code: one terminal per station, cd ../shop-agent-a && claude (or start with its built-in worktree mode, e.g. claude -w <name>).
  • First job is not coding; it is identity proof. Have each agent report back:
pwd
git rev-parse --show-toplevel
git branch --show-current

If directory or branch does not match the ticket, stop immediately. Label windows/terminal tabs with the station name — the cheapest anti-cross-talk device there is.

18.3 A schedule with decision points (90-minute example)

Time Action / decision point
T+0 Contract finalised and committed → create three worktrees → verify directories in all three windows

T+70 Merge by dependency: A → B rebased and re-tested → C → R read-only review of the total diff
T+85 Clean up worktrees (§18.5)

20. Green/red signals: without them the agent stops at "looks right"

A dividing line between senior and amateur practice is whether executable green/red signals are written into the ticket. Spring Boot as the example (translate to your stack):

Test side (MockMvc) — assert status and error code, never empty assertions:

mockMvc.perform(post("/api/orders")
        .contentType(MediaType.APPLICATION_JSON)
        .content("{\"skuId\":\"SKU-1\",\"quantity\":0}"))
    .andExpect(status().isBadRequest())
    .andExpect(jsonPath("$.code").value("INVALID_QUANTITY"));

mockMvc.perform(post("/api/orders")
        .contentType(MediaType.APPLICATION_JSON)
        .content("{\"skuId\":\"SKU-1\",\"quantity\":2}"))
    .andExpect(status().isCreated())
    .andExpect(jsonPath("$.status").value("CREATED"))
    .andExpect(jsonPath("$.orderId").isNotEmpty());

Service layer — assert the business code, not just "threw something":

assertThatThrownBy(() -> orderService.create(new CreateOrderRequest("SKU-1", 0)))
    .isInstanceOf(InvalidOrderException.class)
    .extracting(ex -> ((InvalidOrderException) ex).getCode())
    .isEqualTo("INVALID_QUANTITY");

Manual curl — write both colours into the ticket and require the status line + JSON back:

# Green: 201 + CREATED
curl -sS -D - -X POST http://localhost:8080/api/orders \
  -H 'Content-Type: application/json' -d '{"skuId":"SKU-1","quantity":2}'
# Red: 400 + INVALID_QUANTITY
curl -sS -D - -X POST http://localhost:8080/api/orders \
  -H 'Content-Type: application/json' -d '{"skuId":"SKU-1","quantity":0}'

When spot-checking you only look at three things: status code, the code/status fields, and whether forbidden paths were touched. The frontend equivalent: "after clicking the filter, URL and list must agree" as an e2e assertion, not a screenshot and a promise.

21. Field failures: four recurring wrecks (senior edition)

Wreck 1: three windows, one directory. Worktrees exist, but the second session is still opened on the main checkout; both sides edit the same OrderService and the diffs overwrite each other. The fix is §18.2's identity proof: pwd + show-toplevel + branch name, matched before any work. What is shared is not just files — one local database, one Redis, one port cross-talks just as well, which is why senior teams isolate test data per station too.

Wreck 2: B merges first, A changes the signature, tests go fake-green. Tests written against the old signature land first; A changes create(...); CI stays green because the tests were skipped or never compiled against the new signature. Fix: freeze the order A→B; B must re-run after rebasing; in review, specifically scan for @Disabled and loosened assertions. Contract-level signature changes get their own ticket, merged first, before downstream parallelism starts.

Wreck 3: the agent "helpfully" merges. Inside its own worktree it runs git merge main, resolves conflicts, and drags another station's code in; history is instantly dirty. Fix: agents only commit; merge/rebase/force are human-only. This belongs in the ticket itself, not only in AGENTS.md — in a long session the ticket's prohibitions are closest to hand.

Wreck 4: the contract lives only in chat. A implements field names from conversation v1; C documents the v2 you mentioned verbally later; integration day discovers the mismatch. Fix: contract lands on disk and is committed before dispatch; every ticket @-references the same file; when the contract changes, stop the affected stations, update the file, then resume — and make running stations re-read it.

One level up, senior teams also guard two variants: generated-artifact collisions (two stations each regenerate and edit a generated file — generation is owned by the contract station and merges first) and shared-environment fake green (testing B's code against A's running service). The former is solved by single-ownership of generation; the latter by port/database isolation and tickets that state which running service acceptance applies to.

22. Wrap-up checklist (tape it next to the screen)

Before dispatch: ☐ one-page contract on disk (ideally committed) ☐ serial vs parallel items marked ☐ git worktree list checked ☐ every ticket has its five parts ☐ AGENTS.md states build commands and forbidden paths

During: ☐ ≤4 editable agents ☐ every window's directory verified ☐ agent going in circles → fresh session ☐ A red/out-of-bounds → send back into a fresh session ☐ B/C early → pre-review only, merge in dependency order by default

Before wrapping: ☐ file list checked against the red-line table first ☐ acceptance commands run by your own hand ☐ merged A → rebased-and-retested B → C ☐ read-only review over the total diff ☐ git worktree remove done

One line to remember: you are dispatch and the gate; agents are parallel workers. Isolate the workspaces, share one on-disk contract, let dependencies decide merge order, and let green/red you ran yourself decide acceptance.

23. Case library (1): OpenAI's Harness Engineering — humans write no code, only the environment

OpenAI's February 2026 engineering post documents an extreme experiment: an internal product with zero lines of human-written code, ~1M lines (code, tests, CI, docs, tooling), ~1,500 merged PRs in five months, starting with 3 engineers (growing to 7), ~3.5 PRs per engineer per day. The transferable lessons for senior teams are not the scale but the counter-intuitive decisions:

  • AGENTS.md is a map, not an encyclopedia. They tried the giant single file; it failed predictably: crowding out context, making everything "important" so nothing is, rotting instantly, impossible to verify mechanically. Instead ~100 lines of map plus structured docs/ as the system of record, linters/CI checking doc freshness and cross-links, and a recurring "doc-gardening" agent that opens PRs fixing stale documentation.
  • Observability is fed straight to the agent. Each worktree boots an isolated app instance with queryable logs/metrics/traces (LogQL / PromQL), so "startup must complete in under 800ms" becomes an executable prompt. Single runs of 6+ hours are routine.
  • Entropy needs garbage collection. Agents replicate existing bad patterns. After Friday manual clean-ups failed to scale, they encoded "golden principles" and run background agents that scan for drift, update quality grades, and open small refactoring PRs — most reviewable and mergeable in under a minute.

Steal three things first: a short AGENTS.md plus structured docs; a per-worktree app you can boot standalone with its own logs; and turning repeated taste issues into lints whose error messages contain the fix, so the agent repairs its own violations.

24. Case library (2): OpenAI Agents SDK — maintaining OSS with Skills

OpenAI's Agents SDK repos (Python / TypeScript) run day-to-day maintenance on AGENTS.md + repo-local Skills + GitHub Action; merged PRs rose from 316 to 457 quarter over quarter. Copyable patterns:

  • Make Skills mandatory with if/then in AGENTS.md. E.g. call $implementation-strategy before touching runtime/API, run $code-change-verification whenever code changes, check $changeset-validation for JS package changes, finish with $pr-draft-summary.
  • Verification stacks live inside the Skill. Python: make format / lint / typecheck / tests. TypeScript: pnpm i / build / -r build-check / lint / test. One definition, changed in one place.
  • Routing is governed by description, not code. Their sharpest lesson: a vague description ("run the verification stack") routes badly; a specific one ("run when changes affect runtime code, tests, or build behaviour…") routes reliably. Fix metadata before adding machinery.
  • Deterministic work sinks into scripts/. The model judges and reports; scripts run the repetitive shell. Only after a Skill is stable locally does it move into CI.

25. Case library (3): 16 agents write a C compiler — the ceiling test for parallelism and verification

Anthropic's Nicholas Carlini ran 16 agents through ~2,000 Claude Code sessions at ~$20k API cost over two weeks to produce a 100k-line Rust C compiler that builds Linux 6.9. The engineering is the lesson:

  • Task locks prevent collisions. Each agent claims work by writing a file under current_tasks/; git sync naturally rejects duplicate claims. Finish: merge, push, release the lock.
  • The verifier must be near-perfect. Most effort went into test suites and checker scripts, extended whenever a new failure mode appeared. When new features kept breaking old ones, CI gained a hard rule: no new commit may break existing tests.
  • Split mega-tasks until they parallelise. Compiling the whole Linux kernel is one giant task — 16 agents converged on the same bug. Using GCC as a known-good oracle and randomly mixing GCC-compiled and agent-compiled files to bisect made 16 lines actually parallel.
  • Design around model blindness. Test output prints only a few lines, detail goes to files (error lines prefixed ERROR for grep); against "time blindness", default runs sample 1%/10% (--fast) so an agent does not spend hours running the full suite.

The blunt summary: how far autonomy goes is set by how hard the verifier is, how small the tasks are, and how clean the context is — not by how moving the prompt is.

26. Case library (4): Anthropic's multi-agent research — when parallelism actually pays

Anthropic's multi-agent Research system carries the cleanest numbers available: a Lead (Opus 4) + Sonnet 4 subagents beat a single Opus 4 agent by 90.2% on their internal eval, while multi-agent use costs ~15× the tokens of chat. On BrowseComp, token usage alone explained ~80% of performance variance.

The failures and counters are equally copyable:

  • Early versions spawned 50 subagents for simple questions. Counter: effort rules tied to difficulty written into the prompt — one agent and a few tool calls for simple facts; 10+ divided subagents only for complex research.
  • Subagent briefs must carry objective, output format, allowed tools and boundaries, or they duplicate work and leave gaps.
  • Parallel tool calls cut complex-query time by up to ~90%.
  • Evaluate end state, not a fixed path — multiple agents legitimately take different routes.

Translated to code maintenance: parallelism pays for work that is broad and independent (investigation, multi-solution search) and disappoints on narrow and coupled work (one call chain). And price it honestly — 15× tokens is not rhetoric.

27. Case library (5): dotnet/runtime, ten months — the real merge rate in an elite codebase

Microsoft's .NET team ran GitHub Copilot's coding agent in dotnet/runtime for ten months with unusually complete data: 878 agent PRs, 535 merged (67.9% success) vs 87.1% for Microsoft humans and 79.7% for community humans; ~95k lines added, ~31k removed. In a GitHub-internal case, the Secret Protection team expanded validated token types from 32 to nearly 90 in a few weeks, with interns directing the agent.

How senior teams should read this:

  • 67.9% is a good number, not a failure. In the hardest kind of repo two-thirds of agent PRs merge — but a third need human rework, so staff your review/rework capacity accordingly; never plan on "fully automatic".
  • Framework-shaped, repeatable work pays most. Token validation, test backfill, debt burn-down — clear patterns, clear acceptance. Taste and cross-team coordination remain human work.
  • Scope issues to what a human can review. The GitHub Billing team's lesson: don't file "improve test coverage"; file "add tests for file X / folder Y" as separate issues — not because the agent can't do bigger, but because you can't review a 100+-file PR.

28. Case library (6): Cursor's official workflow — plan files, the TDD five-step, model racing

From Cursor's official January 2026 best-practices guide, the moves most validated across teams:

  • Plans land on disk. Plan Mode (Shift+Tab) output saved into the workspace (e.g. .cursor/plans/) survives interruptions and briefs the next agent. When a build goes wrong, reverting to the plan and re-running is usually faster and cleaner than patching via follow-ups.
  • The TDD five-step, frozen: ① agent writes tests from I/O pairs, explicitly told it is TDD and must not fake implementations; ② run tests, confirm all red, tests-only edits allowed; ③ commit the tests; ④ implement with tests frozen, iterate to green; ⑤ commit the implementation.
  • Sediment the daily commands. /pr (diff → message → gh pr create), /fix-issue [number], /review, /update-deps (one at a time, tests after each) as repo-checked command files.
  • Same-prompt multi-model racing for hard problems, keeping the cleanest diff; native worktrees as the isolation mechanism.
  • Debug Mode for stubborn bugs: enumerate hypotheses, instrument with logging, have the human reproduce, locate from runtime data — evidence over guessing.
