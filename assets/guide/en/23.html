Context Engineering: 0→1 Runs on Generation, 1→N Runs on Context

Companion to diagram #23 · Chapter 4 "AI Coding Today"

In a new project, AI generates code at astonishing speed. In an existing codebase, the problem shifts from "can it write this?" to "does it understand this?" Alibaba's practice handbook sums it up: 0→1 runs on generation ability; 1→N runs on context engineering.

1. A puzzling contrast

Give the same model two tasks:

  • Task A: "Write a to-do list CRUD service in FastAPI."
  • Task B: "In our order system, add 'partial refund' to the refund API."

The model gets Task A right almost first time, because thousands of similar examples exist online and everything it needs is in its training data. Task B often goes badly. It does not know what your order state machine looks like, which internal service refunds go through, whether amounts are stored in cents or yuan, or that someone changing this code last time caused a financial loss.

This knowledge is not in the model's weights. It lives only in your codebase, your documents and people's heads. The only way the model can use it is for it to be put into context. That is the problem context engineering solves.

2. Definition: put the most useful things into limited attention

Anthropic defines context engineering as the set of strategies for curating and maintaining the optimal set of tokens during LLM inference. Because the attention budget is finite, good context engineering means finding the smallest set of high-signal tokens that maximises the likelihood of the desired outcome.

Note the word "smallest". If the model lacks information, why not just stuff in the whole codebase? Two reasons this fails:

  • Context rot. Anthropic notes that needle-in-a-haystack evaluations reveal that as the number of tokens in context grows, the model's ability to recall information accurately declines. Context is a finite resource with diminishing returns.
  • Lost in the Middle. A 2023 study found that when key information sits in the middle of a long context, models use it markedly worse than when it is at the beginning or end.

So the question is not how much to give but what to give and when.

3. What makes up context?

For a coding agent, context usually falls into five kinds:

Kind Content Typical carrier
Project map Architecture, module responsibilities, entry points Architecture docs, README
Rules Stack constraints, conventions, prohibitions CLAUDE.md, AGENTS.md, .cursor/rules
Requirements Goals, scope, acceptance criteria Spec (next article)
Tools What can be done and how to call it Skills, MCP, CLI
Runtime facts Logs, test results, database state Test output, traces, read-only queries

Back to Task B: the state machine and refund service are the project map; "amounts in cents" is a rule; the edge cases of partial refunds are requirements; querying order data is a tool; the logs of the last incident are runtime facts. Missing any one, the model has to guess.

4. Three key techniques

1. Load just in time instead of pre-filling. Rather than loading every file up front, keep lightweight identifiers (file paths, queries, links) and load content with tools at run time. Claude Code browsing a codebase with glob and grep is an example: it searches for and opens the refund logic only when it needs it. That is how people work too: you do not memorise the codebase, you know where to look.

2. Three ways to sustain long tasks.

  • Compaction: summarise the conversation when it nears the limit and start a fresh window with the summary.
  • Structured notes: write progress, decisions and to-dos to files outside the context and read them back when needed.
  • Subagents: each explores separately and returns only the essentials to the main session (Chapter 3, article 4).

3. Turn tacit knowledge into explicit assets. Teams in the handbook use three kinds of asset to help AI understand a project: code documentation explains why things are designed as they are; a code graph precisely answers questions about definitions, call relationships and blast radius; rules turn team experience into enforceable constraints. The handbook also treats context as an organisational asset: Skills, MCP, specs, READMEs / runbooks, templates and checklists. Without building these up, a team stays stuck at "everyone asks the AI ad hoc", explaining from scratch every time.

5. A case from the field: the three stages of Qwen's user-growth agent team

Alibaba's handbook records one team's experience, which is typical:

  • Stage one: about 15 back-end engineers explored AI coding individually; in some scenarios code generation was several times, even about 10 times, faster than before.
  • Stage two: once the 0-to-1 build-out was done, the marginal gain from code generation alone fell. The real problem became getting AI to understand project structure, business requirements and engineering constraints accurately inside an existing codebase.
  • Stage three: engineering effort shifted to organising context, defining boundaries and building verification.

Almost every team hits this turning point on the way from Task A to Task B.

6. Practical advice

  • Commit rule files to Git. Rules that exist only locally are invisible to a new worktree (the developer on X who shared how they use Orca stressed this).
  • Add rules one at a time; do not write dozens at once. Add one when the agent keeps making the same mistake. Too many rules dilute attention themselves.
  • The rule of three. Once a workflow has been repeated more than three times, turn it into a reusable Skill.
  • Write "why", not just "what". "Amounts are in cents" is weaker than "amounts are in cents, because floating-point errors once broke reconciliation". Knowing the reason lets the model make the right call in cases the rule does not cover.

7. Common misconceptions

  • "More context is better." Context rot shows that extra tokens dilute attention.
  • "A stronger model will understand old code." The handbook's experience is that steadily building high-quality context, clear constraints and verifiable feedback usually improves output stability more than chasing a stronger model. Even a stronger model does not know your company's state machine.
  • "Write the rules once and you're done." Context assets need updating and validating alongside the code; outdated docs are more dangerous than none.
