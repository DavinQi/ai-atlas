Context Engineering: 0→1 Runs on Generation, 1→N Runs on Context

Companion to diagram #23 · Chapter 4 "AI Coding Today"

Overview

In a new project, AI's code generation speed is stunning; in an existing codebase, the question shifts from "can it write" to "can it understand". Alibaba's handbook sums it up: 0→1 runs on generation ability, 1→N runs on context engineering. Anthropic defines context engineering as the set of strategies for curating and maintaining the optimal set of tokens during LLM inference; because the attention budget is finite, good context engineering means finding the smallest set of high-signal tokens that maximizes the likelihood of the desired outcome.

Core Mechanisms

1. Why context is finite. Anthropic notes that needle-in-a-haystack style evaluations reveal "context rot": as the number of tokens grows, the model's ability to accurately recall information decreases, so context is a finite resource with diminishing returns. The "Lost in the Middle" study likewise found that models use information in the middle of long contexts significantly worse.

2. What context consists of. For a coding agent, context typically includes:

  • Project map: architecture, module responsibilities, code entry points
  • Rules: stack constraints, coding conventions, prohibitions (CLAUDE.md, AGENTS.md, .cursor/rules)
  • Requirements: Spec, acceptance criteria
  • Tools: Skills, MCP, CLI
  • Runtime facts: logs, test results, database state

3. "Just-in-time" loading. Rather than stuffing context upfront, keep lightweight identifiers (file paths, queries, links) and load on demand with tools at runtime. Claude Code navigating a codebase with glob and grep is an example.

4. Managing long tasks. Compaction (summarize a conversation nearing the limit and start a new window), structured notes (write progress outside the context), and subagents (each explores and returns only the essentials).

Engineering Practice and Numbers

The Qwen user-growth agent team's three stages (Alibaba handbook):

  • Stage 1: about 15 server-side engineers explored AI coding individually; in some scenarios code generation reached several times — even about 10× — the traditional speed.
  • Stage 2: once the 0-to-1 build was done, the marginal return of relying on code generation alone fell; the real challenge became getting AI to accurately understand project structure, business requirements and engineering constraints in an existing codebase.
  • Stage 3: engineering focus shifted to organizing context, defining boundaries and building verification mechanisms.

The team used three kinds of assets to solve "how AI understands the project": code documentation explains "why it is designed this way", a code graph precisely queries definitions, call relationships and impact scope, and Rules turn team experience into executable constraints.

The handbook treats context as an organizational asset: Skills, MCP, Specs, README / runbooks, templates and checklists. Without accumulating these, a team stays at the "everyone asks AI ad hoc" stage.

Practical tips:

  • Commit rules files to Git so new worktrees can read them (the X developer sharing Orca usage stressed this).
  • Don't write dozens of rules at once; add one when the agent repeatedly makes the same mistake.
  • Once a process has been repeated more than three times, turn it into a reusable Skill.

Common Misconceptions

  • "More context is better." Context rot shows extra tokens dilute attention.
  • "A stronger model will fix not understanding legacy code." The handbook's experience is that continually building high-quality context, explicit constraints and verifiable feedback often improves output stability more than simply chasing a stronger model.
  • "Write the rules once and you're done." Context assets need continual updating and verification.
