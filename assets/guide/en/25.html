Layered Verification: Let the Agent Pass the Machines Before It Reaches a Human

Companion to diagram #25 · Chapter 4 "AI Coding Today"

When agents produce far faster than people can review, people become the bottleneck. The answer is not to make people read faster but to let machines decide everything they can, leaving people only what machines cannot reliably judge. Alibaba's practice handbook calls this a layered verification system and says "our main battlefield is verification and environments".

1. First, an attention budget

Suppose one engineer directs three agents, each producing 5 MRs a day averaging 300 changed lines. That is 4,500 lines a day. Seriously reviewing 4,500 lines is more than one person can do in a day, let alone with other work.

That leaves two options: review becomes a formality (glance and approve), or the person becomes the bottleneck (agent output piles up in a queue). In the language of Amdahl's Law, review is the new part that cannot be sped up. Layered verification removes the part of review that machines can do, so people look only at what genuinely needs human judgement.

2. Three layers of feedback

Per Alibaba's handbook:

Layer Content Purpose
Seconds Compilation, type checks, unit tests High-frequency autonomous iteration
Minutes Integration tests, contract tests, browser automation Cover more realistic behaviour
Human Business value, user experience, ethical boundaries What machines cannot reliably judge

It is a pyramid: the lower, the faster, cheaper and more frequent; the higher, the slower, costlier and rarer. The agent corrects itself in the lower loops and moves up only after passing the layer below.

One change passing through all three layers. An agent changes a function signature:

  1. Seconds: the type checker immediately flags three callers with mismatched arguments. The agent fixes them and reruns, all within seconds. No human ever knows it happened.
  2. Minutes: an integration test finds a downstream service's contract test failing because a returned field was renamed. The agent adds a compatibility field and reruns; green.
  3. Human: the person opening the MR sees a change that compiles, passes all tests and keeps the contract compatible. They only need to judge whether its business meaning is right and how long the compatibility field should stay.

Without the first two layers, every one of those problems would land on the third, to be found by a person one at a time.

3. Why executable checks matter so much

Anthropic notes that an agent needs "ground truth" from its environment at every step to assess progress. DeepSeek-R1's training explicitly used only rule-based rewards (answer checking, compilation and tests), because neural reward models are prone to being gamed. The same holds in use: executable checks are objective signals; a model's self-assessment is not. When the model says "I checked and it's fine", that sentence was generated too.

4. What you test matters more than how much

Chasing coverage is a common trap. Ask AI to "raise coverage to 90%" and it will happily oblige with many tests that call functions and assert the result is not null. Coverage goes up; almost nothing is protected.

The Qwen team in the handbook focuses tests on requirement boundaries, key branches and known failure modes, rather than coverage for its own sake. They also found reliability is rarely a single-point issue. Under concurrency, for example, agent sandboxes were created twice. Preventing that requires not just idempotency at the API layer but "end-to-end idempotency" across the request entry point, database transactions, message publishing and consumer execution. Unit tests that only exercise the API cannot catch such cross-stage problems.

5. Build an end-to-end test environment for the agent

A developer on X shared four things:

  1. Make the environment familiar to the agent: start the test environment and create test data with one command, state versions, test accounts and permissions, and provide cleanup and reset.
  2. Let the agent operate the business system: run real business flows through a browser, API or CLI.
  3. Let the agent query tables and logs easily: a read-only database MCP to confirm what was written, a logging Skill and traces to check the state of the call chain.
  4. Turn tedious but stable procedures into scripts and Skills.

His conclusion: AI is very good at writing test cases, but without an end-to-end environment you still hit unexpected errors after launch. He no longer reads every generated line; he mainly checks test results and core business logic, on condition that each MR stays small, verifying complete business paths step by step.

6. Results

The Qwen user-growth team's comparison from May to August 2026: average delivery cycle halved, defects per thousand lines down 70%, change failure rate down more than 90%. The handbook's interpretation: quality metrics improved more than speed metrics, showing the main gains came from verification rather than generation speed. That matches Amdahl's Law: delivery time halved rather than shrinking several-fold like code generation, while the quality gains came directly from the verification system.

7. Common misconceptions

  • "High coverage means safety." Chasing coverage makes AI generate meaningless assertions; covering failure modes is what counts.
  • "Having another model review it counts as verification." Model review is a useful complement but cannot replace executable checks.
  • "More human review is safer." Attention is limited and should go to what machines cannot judge. Review too much and nothing is read carefully.
