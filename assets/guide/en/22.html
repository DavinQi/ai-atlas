Amdahl's Law: Speeding Up Only Coding Caps the Overall Gain

Companion to diagram #22 · Chapter 4 "AI Coding Today"

Chapter 3 concluded that AI is rapidly taking over coding. This chapter starts with a question that puzzles many teams: why do engineers say they "write code several times faster" while features ship barely faster at all? The answer is a law from 1967.

1. The law

In 1967 Gene Amdahl proposed, in a paper on parallel computing titled Validity of the single processor approach to achieving large scale computing capabilities, the law that now bears his name: the overall speed-up of a system is limited by the part that cannot be sped up. Back then the question was how much faster a program gets with more processors. Applied to software delivery, the conclusion is just as direct: if coding is a small share of the delivery cycle, then even if AI shrinks coding time to zero, delivery will not get much faster.

Let coding be a share p of the delivery cycle and let AI speed coding up by a factor s. With total time normalised to 1, the non-accelerated part stays 1−p and coding becomes p/s, so the overall speed-up is:

S=(1−p)+sp​1​

As s→∞ (coding time goes to zero), only 1−p remains in the denominator, giving the cap:

Smax​=1−p1​

2. Work through it

Suppose a feature takes 10 days from request to release, of which 3 days are actual coding (p=0.3). The other 7 are clarification, reviews, integration, testing, waiting for environments and release approvals.

  • AI makes coding 10× faster: coding drops from 3 days to 0.3, total 7.3 days, speed-up 10/7.3≈1.37.
  • AI makes coding instant: total 7 days, speed-up 10/7≈1.43.

Coding got 10× faster, yet the whole thing is only 37% faster; even with coding taking no time at all, it is only 43% faster. More combinations (computed from the formula):

Coding share p Coding 10× faster Coding time → 0
20% 1.22× 1.25×
30% 1.37× 1.43×
50% 1.82× 2×

Now flip it: halve the waiting and manual work in those 7 days (to 3.5) while also making coding 10× faster. Total time is 3.5+0.3=3.8 days, a speed-up of about 2.6×. Optimising the non-coding parts pays off far more than squeezing coding further.

3. Data from the front line

Alibaba's AI Native R&D Paradigm Practice Handbook (annotated edition) records what the formula predicts:

  • Coding is a small share. Rough internal estimates put code generation at only 20–30% of the development pipeline, or even less. For one consumer-facing user-journey change, coding and local verification could be done in an hour, but after several internal platforms, release processes and environment constraints, plus a possible change freeze, it could still take weeks from finished code to live.
  • A "paradoxical" figure. More than 60% of bugs were fixed automatically, yet the share of bugs closed the same day rose only from 53% to at most 63%. The reason: triggering depends on people and verification depends on people. However fast the agent fixes, it waits for someone to notice the problem, start the task and confirm the result. The handbook calls this Amdahl's Law in real life: high automation at a single point, unchanged end-to-end throughput, because manual nodes remain in the chain.

The example shows that "the part that cannot be sped up" includes not just slow steps but waiting for people. If a task sits in a queue for two days before anyone looks at it, those two days have nothing to do with how fast the agent is.

4. What to do about it

  1. Measure before optimising. Map the value stream from request to release and mark each step's processing time and waiting time. Waiting is often longer than processing and easiest to overlook.
  2. Point AI at the bottleneck. Clarifying requirements, testing, preparing environments, release approvals and troubleshooting are often more worth optimising than coding. The rest of this chapter follows that logic: context engineering and specs target understanding requirements, layered verification targets testing, and evidence chains target troubleshooting.
  3. Remove the "a human must trigger it" choke points. The handbook team's next step was to let execution nodes discover pending work themselves, routed by a scheduling layer, instead of waiting for someone to start them (more in Chapter 5).

5. Common misconceptions

  • "AI writes code 10× faster, so the team is 10× faster." The cap is set by the part that cannot be sped up.
  • "Everything outside coding is someone else's problem." Value is end-to-end delivery; a local optimum is not a global one.
  • "The law is outdated." It describes system structure and does not expire with technology. On the contrary, the more thoroughly coding is solved, the more the other stages become the new bottleneck, so the law only grows more relevant.
