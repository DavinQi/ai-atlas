AIOps Self-Healing Loops: Low Risk Runs Automatically, High Risk Goes Through People

Companion to diagram #36 · Chapter 6 "How AI Reshapes the Dev Lifecycle"

Connecting agents to operations makes a self-healing loop possible: detect → collect evidence → diagnose → generate a fix → verify → release → observe. The key design question is not how much the agent can fix but how to tier by risk: low-risk operations that can be rolled back quickly may run automatically; high-risk, irreversible ones must go through a person.

1. Follow one incident around the loop

2 a.m.: a service's error rate starts climbing.

  1. Detect. The alert fires. Traditionally, the first thing is to wake the on-call engineer; in a self-healing loop the alert creates a task for a diagnosis agent directly.
  2. Evidence. Following Chapter 4's evidence chain, the agent gathers facts first: take the TraceIds of a few failed requests, check logs and upstream/downstream state along the chain, and compare against code locations and recent changes. It finds that every failure happens after a newly released config value is read, and that value is malformed.
  3. Diagnose. The evidence is clear, an "obvious error", so the diagnosis agent locates it directly. If evidence were insufficient or contradictory, it would escalate to an agent with full code context or to a person.
  4. Fix. Two options: roll the config back to the previous version (low risk), or change the parsing code to accept the new format (medium risk). The agent does the former to stop the bleeding and prepares a patch for the latter, plus a regression test that reproduces the problem.
  5. Verify. The patch goes through layered verification: compile, unit tests, integration tests.
  6. Release and observe. After the config rollback, the error rate returns to normal. The code patch does not go live automatically at 2 a.m.; it becomes a change awaiting approval, which a person approves with one click in the morning before a gradual rollout.

At 9 a.m. the engineer sees a structured report: symptom, evidence, root cause, the mitigation already taken, and the fix awaiting approval. Nobody was woken, but the key decision was still made by a person.

2. Risk tiers: the heart of the loop

The crucial move in the example is step 4, treating "roll back the config" and "change the code" differently. Behind that sits a risk tiering:

Risk Examples Handling
Low Restart stateless instances, scale out, roll back to the previous version Run automatically and notify
Medium Config changes, small code fixes Generate automatically; one-click human approval
High DB migrations, permission changes, anything involving money A person must decide

Tiering rests on two dimensions: reversibility (can a mistake be recovered quickly?) and blast radius (how many users and how much data does a mistake affect?). Rolling back to the previous version "returns to a known good state": reversible and low risk. A database migration may be irreversible and touch all the data.

This matches security guidance. OWASP's mitigations call explicitly for human-in-the-loop control of privileged operations and human approval for high-risk ones, with separate tokens and least privilege for applications. The MCP specification likewise requires explicit user consent before invoking tools.

3. Gradual release: fixes face the test too

Even an agent-generated fix that passes every test can fail in production; test-environment data and traffic never fully match production. So fixes also go canary, observe, then widen.

Anthropic uses "rainbow deployments" in its multi-agent system: old and new versions run side by side and traffic shifts gradually from old to new, so updates don't break agents mid-run. The same idea applies to agent-generated fixes.

4. Manual nodes swallow automation gains

Chapter 4 cited the handbook's "paradoxical" figure: more than 60% of bugs fixed automatically, yet the same-day bug closure rate rose only from 53% to at most 63%, because triggering depends on people and verification depends on people.

Against the loop above, the problem is plain: if step 1 waits for a person to notice and create the task, and step 5 waits for a person to check each fix, then however fast steps 2–4 are, throughput won't rise. For the loop to really close, triggering and low-risk verification must be automated too, leaving to people only what genuinely needs judgement.

5. The hardest last mile

The handbook is also sober about this: build, integration testing, canary release, production verification and recovery involve real environments, real data and real users; the tolerance for error is tiny, and the demands on sandbox isolation, credential management, guardrails and observability far exceed what exists today.

So build trust step by step:

  • Start with read-only access and earn trust in diagnosis. How accurate are the agent's diagnostic reports? Let people "shadow" it for a while.
  • Then open up low-risk write operations gradually, such as restart, scale-out and rollback.
  • Leave a trace for every automatic action: who (which agent), on whose behalf, for which task, did what (Chapter 5, "digital employees").

6. Common misconceptions

  • "Self-healing means fully automatic." Risk tiers and human gates are core parts of a self-healing system.
  • "Tests pass after the fix, so release it everywhere." Production verification needs gradual rollout and observation.
  • "Agents make too many mistakes for operations." The key is to limit their scope so errors can be rolled back and audited. People make mistakes too; operations systems were always designed for mistakes.
