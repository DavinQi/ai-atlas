Agent Components: LLM + Planning + Memory + Tools, Looping on Environment Feedback

Companion to diagram #11 · Chapter 2 "Agent Design: Principles & Patterns"

The previous chapter ended with the point that a model only predicts the next token. So how does it "check the weather", "edit code" or "book a meeting room"? The answer is surprisingly plain: the model only writes down "what to do"; an external program does it, and the result is turned back into text for the model. Run this loop automatically for many rounds and you have what we call an agent.

Diagram #11 shows the parts of that loop: the LLM in the centre (the core of reasoning and decisions), surrounded by planning, tools, memory and environmental feedback, with a reminder at the bottom: the difference between a workflow and an agent is whether the path is predefined or decided by the model. This article starts from one concrete tool call, takes the components apart one by one, then returns to the most important design question: when do you actually need an agent?

1. Start from one tool call

A user asks: "What's the weather in Beijing today?" The model can't go online by itself. Training taught it to output text in a particular format when needed, roughly like this (illustrative):

<|assistant|><|tool_call|>search(query="Beijing weather today")<|end|>

The model stops after writing this line. An external program recognises the format, actually runs the search, and appends the result to the context as new text:

<|tool_result|>Beijing today: sunny, high of 22°C…
<|assistant|>It's sunny in Beijing today with a high of 22°C, a good day to go out.

The model reads the result, continues predicting, and writes the answer. Toolformer showed that a model can even learn in a self-supervised way when and how to call APIs. Arithmetic, running code, querying databases and reading files all follow the same pattern. An agent just runs this loop automatically for many rounds: decide the next step → call a tool → read the result → decide the next step, until the task is done or a stop condition triggers.

Anthropic's summary in Building effective agents is blunt: agents are usually simple to implement; they are essentially LLMs using tools based on environmental feedback in a loop. The complexity lies not in the loop itself but in each component inside it.

2. Four components, each with one job

Lilian Weng's 2023 survey gave the widely cited framework: the LLM acts as the agent's "brain", working with three components: planning, memory and tool use. Anthropic especially stresses a fourth: real feedback from the environment.

Planning: break a big task into doable steps. "Switch the login module from sessions to JWT" isn't one step. Planning does two things. One is decomposition into sub-goals such as "find every use of sessions → design the token structure → change each place → run the tests". The other is reflection: learning from steps already taken and correcting mistakes. ReAct, Plan-and-Execute and Reflexion, covered in the next article, are three typical ways of organising planning.

Tools: get what the weights don't have. The weights don't contain today's weather, your company's database or the latest code in your repository, and the model can't reliably do exact calculation. Tools fill these gaps: APIs, code execution, search, file I/O. The form of the tools matters too. CodeAct proposes executable Python code as a unified action space and reports up to 20% higher success than JSON or text actions on its benchmarks: code naturally supports loops, conditions and combining several tools, so one action can do more.

Memory: inside and outside the context. Weng's split: short-term memory is everything in the context, limited by the window size; long-term memory uses external storage and retrieval to keep and recall information over long spans. Generative Agents store a complete record of experiences in natural language, periodically synthesise higher-level reflections, and retrieve dynamically when planning. Article 4 covers memory and RAG in depth.

Environmental feedback: the agent's "eyes". This is the most underrated component. The diagram draws it in orange and lists it separately: observations, errors, test output. Anthropic stresses that during execution an agent must get ground truth from the environment at every step (tool call results, code execution results) to assess progress, and pause for human feedback at checkpoints or when blocked. An agent without feedback is just generating with its eyes closed. However elegant the code, you only know it's right after running the tests; however confident the SQL, you only know the table exists after querying it.

The CoALA framework gives a more formal description from cognitive science: modular memory components, a structured action space for interacting with internal memory and the external environment, and a general decision process for choosing actions. Different names, same skeleton.

3. Workflow or agent: who decides the next step?

"Agent" has no single definition. Anthropic calls every LLM-based automated system an agentic system and draws one key distinction:

  • Workflow: LLMs and tools are orchestrated through predefined code paths. For example, "first have the model classify the ticket, then call a different handling prompt per category".
  • Agent: the LLM dynamically directs its own process and tool usage, keeping control over how it accomplishes the task.

The difference isn't whether there are tools but who holds the control flow. That determines almost every property of the system:

Workflow Agent
Predictability High; paths can be enumerated Low; paths are chosen by the model
Suited to Fixed steps that can be broken down in advance Unpredictable steps, decided along the way
Cost and latency Controllable Uncertain number of rounds, usually higher
How it fails One step fails Errors accumulate over rounds
Debugging Easy Hard; needs full trajectory logs

Anthropic's advice is to start with the simplest solution: many applications only need a single, well-optimised LLM call with retrieval and examples. Agentic systems usually trade latency and cost for better task performance; add complexity only when that trade is worth it.

4. Three principles for building agents well

Keep it simple. Don't use an agent where a workflow will do; don't use multiple agents where one will do (see the decision tree in article 6).

Make planning visible. Show the agent's planning steps explicitly, so people can spot it going off course in time and review afterwards.

Design the agent–computer interface (ACI) carefully. Tool names, parameters, documentation and error messages are the model's only window onto the world. Anthropic suggests investing as much effort as in a human interface: say clearly when to use a tool and when not to, give examples, and make common mistakes hard to make. SWE-agent's research shows that an interface designed for agents (such as file viewing with line numbers and edit commands with syntax checks) markedly improves performance on software engineering tasks.

Also, be careful with frameworks. They add layers of abstraction that hide the underlying prompts and responses and make debugging harder. Anthropic suggests starting with the LLM API directly; many patterns take only a few lines of code.

5. Three common misconceptions

  • "An agent is a chatbot with tools." The key is who decides the control flow: code in a workflow, the model in an agent.
  • "More autonomy is better." Autonomy means higher cost and the risk of compounding errors. Set stop conditions (such as a maximum number of iterations), test thoroughly in a sandbox and add guardrails.
  • "Memory means stuffing all history into the context." Context is short-term memory and a scarce resource; long-term memory needs external storage and retrieval.
