Orca: One Task per Worktree, One Agent per Worktree

Companion to diagram #31 · Chapter 5 "Multi-Agent Programming"

When several agents edit the same code at once, the first problem is trampling on each other. Git worktrees are the infrastructure that solves this, and Orca is a multi-agent development workbench built around them. Orca's docs describe it as a desktop IDE for running multiple AI coding agents side by side, where each task gets its own git worktree, its own agent terminal and its own browser tab.

1. The problem: three agents in one directory

Suppose you open three terminals in the same project directory and give three agents three jobs: A fixes a payments bug, B adds avatars, C refactors logging. Trouble starts quickly:

  • Files overwrite each other: A and C both edit utils/logger.py, and whoever saves last wins.
  • Test results contaminate each other: while A runs tests, B's half-written code is in the tree; A sees failures B caused and goes off to "fix" a problem that doesn't exist.
  • Branch conflicts: A wants to switch to fix-payment while B is working on feature-avatar. There is only one working directory; switching interrupts B.

The root cause: a working directory can have only one branch checked out and one state of its files at a time.

2. The fix: git worktree

Git's documentation explains that a repository can support multiple working trees, so several branches can be checked out at once; a newly added working tree is called a "linked worktree", as opposed to the main working tree created by git init or git clone.

git worktree add ../fix-payment -b fix-payment
git worktree add ../feature-avatar -b feature-avatar
git worktree list
git worktree remove ../fix-payment

After the first two commands there are three directories on disk: the original project, ../fix-payment and ../feature-avatar, each with a different branch checked out and files that don't interfere.

The key point: all worktrees share the repository's objects and history, each with its own working directory and checked-out branch. That differs from cloning three times: a clone copies the full history three times, while a worktree adds only the working directory. A commit made in one worktree is immediately visible from another (for example via git log fix-payment).

3. What Orca adds on top of worktrees

Worktrees solve file isolation, but the other multi-agent problems remain. Orca's docs compress the workflow into: add a repo → open a workspace (worktree) → choose an agent → split panes → review changes → commit. Some design points:

  • No bundled model: it runs the Claude Code, Codex, Cursor CLI, OpenCode and so on that you already have, on your own subscriptions. This also addresses "locked into one vendor's quota" from the previous article: different worktrees can run different vendors' agents.
  • Every worktree is a real git worktree, so you can step into the directory and use plain git at any time without being locked into the tool.
  • Runs on your local desktop by default; remote compute uses machines you control (SSH, self-hosted servers or cloud VMs).

Make new worktrees ready to work immediately. This answers "they won't run". A new worktree is clean code checked out from Git; untracked .env files and dependency directories aren't there, so the agent errors on start. The developer on X mentioned earlier explains that Orca can be configured to copy some files into each copy (such as .env) and to share some directories (such as dependency packages).

Notifications and review. This answers "can't keep track, can't keep up". According to the same developer, Orca pops a notification when an agent goes from working to idle; its change view supports line-by-line comments sent back to the agent in one go, and can mark which lines AI wrote.

Shared rules. Project rules rely on files the agents read themselves: Claude Code reads CLAUDE.md, Codex reads AGENTS.md. They must be committed to Git, or agents in new worktrees won't see them. This is an easy trap: rules written in the main directory but not committed leave the agent in a new worktree like a new hire who never read the handbook.

4. What worktrees don't isolate

Worktrees isolate files, not the runtime:

Resource Isolated? Risk
Working-directory files Yes —
Checked-out branch Yes —
Repository history, object store No (shared) Usually harmless
Ports No Two agents both start dev servers on port 3000
Local database No A's tests wipe test data B is using
External services No Both call the same test environment's APIs

So when running tests in parallel, give each worktree its own ports and its own database or container.

5. Engineering points

  • Name tasks: one worktree per clear task and branch, which makes cleanup easy.
  • Delete when done: clean up losing or finished worktrees and their branches promptly, or the disk and branch list get messy.
  • Know the limits: the developer admits that if you use one vendor's agent and do one thing at a time, Orca adds little and the official client is enough; its value scales with the number of agents running at once and the volume of changes to accept.

Orca is made by Stably and open-sourced under the MIT licence; its GitHub repository was created on 17 March 2026 and had about 94,000 stars when this was checked.

6. Common misconceptions

  • "Opening a few terminals is the same." It can be, but you have to solve missing dependencies, losing track and review overload yourself.
  • "Worktrees are fully isolated." They share history and the object store; ports, databases and external services can still collide.
  • "Orca is a model or a hosted service." Its docs say explicitly that it is neither a model nor a hosted VPS product.
