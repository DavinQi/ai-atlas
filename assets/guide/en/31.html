Two Plays: Race for the Best Result, or Pipeline the Work

Companion to diagram #31 · Chapter 5 "Multi-Agent Programming"

Multi-agent programming has two basic plays:

  • Race: give the same task to several agents at once and pick the best result.
  • Pipeline: split one task into stages or parts handled by different agents.

They correspond to the two variants of "parallelisation" in Anthropic's pattern catalogue: voting, running the same task several times for diverse outputs, and sectioning, splitting a task into independent subtasks run in parallel. They solve different problems: racing tackles what is hard, pipelines tackle what is big.

1. Racing: lower risk through diversity

Scenario. Payments occasionally charge customers twice in production, cause unknown. A classic "hard" problem: the change may be small, but getting it wrong is expensive.

How. Orca's docs list "have three agents fix the same bug at once and pick the winner" as a typical use. The three agents analyse and fix independently, each in its own worktree, and a person compares the results.

Why it works. The developer on X who shared how they use Orca relays the official explanation: different agents make different mistakes. Where all three change the same thing, it is probably right; where each changes something different, that is the genuinely hard part of the problem. For one wait you get three answers plus a map of where they disagree.

That disagreement map is often worth more than any single answer. Say all three agents add an idempotency check to the payment callback (agreement) but choose differently between the order ID and the payment transaction ID as the idempotency key (disagreement). You can safely adopt the agreed part; the disagreement is exactly where human attention should go.

The research counterpart. The Codex paper found repeated sampling an effective strategy for reaching correct solutions: 28.8% solved with one sample, 70.2% with 100 samples per problem. Multi-agent debate research showed that several model instances proposing and debating answers improves reasoning and factual accuracy. Racing combines the two: more samples raise the chance of hitting a right answer, and comparing disagreements helps identify which one it is.

Different vendors help. If all three agents run the same model, their errors are often correlated and they may share a blind spot. Agents from different vendors (one reason Orca doesn't bind you to a model) make errors more independent, so agreement means more.

Races don't merge themselves. When each result is half right, let the winning agent revise once more with reference to another's changes, or pick the good parts by hand.

2. Pipelines: handle complexity through division of labour

Scenario. Building a new "loyalty points" feature spanning requirements, design, back end, front end and tests. A "big" problem: no single step need be hard, but the total exceeds what one context holds comfortably.

How. MetaGPT encodes standard operating procedures (SOPs) into prompt sequences and uses an assembly-line paradigm to assign roles to different agents, breaking complex tasks into subtasks handled collaboratively, with agents that have domain expertise verifying intermediate results to reduce errors. A common coding pipeline:

clarify requirements → design → code → test → cross-review → integrate

Hand-offs go through files, not conversations. The biggest risk in a pipeline is information lost at hand-off. The remedy is for each stage to produce explicit shared artefacts: a spec, CONTEXT.md, interface definitions, test results. Downstream agents read these rather than rereading the whole upstream conversation. That is another value of Chapter 4's spec-driven approach: the spec is the pipeline's interface.

Cross-review. Another developer has a coding agent finish, then brings in another vendor's agent for adversarial review, with all issues fed back to the main coding agent to fix and re-verify. It is a concrete form of "verifying intermediate results", again relying on different agents making different mistakes.

3. Which one?

Dimension Race Pipeline
Problem it tackles Hard: single-point problems where mistakes are costly Big: large tasks that can be split
Cost N× tokens Sum of the stages
Human work Compare, choose, merge Define interfaces and acceptance
Main risk Review burden multiplies Information lost at hand-off

They combine, too: inside a pipeline, race just the riskiest step (say, the change to the payment callback).

Race only where it counts. The developer's advice: race only where mistakes are painful, such as payments, permissions and data migrations; don't do it for copy edits.

4. Common misconceptions

  • "The more racers, the better." Returns diminish while cost grows linearly and review multiplies. Going from 1 to 3 buys a valuable disagreement map; going from 3 to 10 mostly buys review work.
  • "The finer the pipeline roles, the better." Every hand-off can lose information, and Anthropic warns that tasks with heavy inter-agent dependencies are not currently a good fit.
  • "If three agents agree, it must be right." Agreement raises confidence, but tests are still needed, especially when they run the same model.
