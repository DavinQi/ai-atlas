Two Approaches: Race for the Best, or Pipeline the Work

Companion to diagram #31 · Chapter 5 "Multi-Agent Programming"

Overview

Multi-agent programming has two basic approaches:

  • Race: give the same task to several agents at once and pick the best result.
  • Pipeline: split a task into stages or parts handled by different agents.

They correspond to the two variants of "parallelization" in Anthropic's pattern catalogue: voting — running the same task multiple times for diverse outputs; and sectioning — breaking a task into independent subtasks run in parallel.

Core Mechanisms

1. Race: reduce risk with diversity. Orca's docs list "have three agents fix the same bug and pick the winner" as a typical use. The X developer sharing Orca usage relays the official rationale: different agents make different mistakes. Where all three make the same change, it's probably right; where each changes something different, that's the genuinely hard part of the problem. You spend one wait and get three answers plus a map of "where they disagree".

There is academic evidence too: the Codex paper found repeated sampling on the same problem an effective strategy for getting a correct solution (28.8% solved with one sample, 70.2% with 100 samples per problem); the multiagent debate study showed that multiple model instances proposing and debating their answers improves reasoning and factual accuracy.

2. Pipeline: handle complex tasks through division of labor. MetaGPT encodes standardized operating procedures (SOPs) into prompt sequences, using an assembly-line paradigm to assign roles to different agents, break complex tasks into subtasks handled collaboratively, and have agents with domain expertise verify intermediate results to reduce errors. A common coding pipeline:

Clarify → design → code → test → cross-review → integrate

  • Race only where it matters: the developer above advises racing only where mistakes are painful, such as payments, permissions and data migrations — not for copy changes.
  • Races don't merge automatically: when each of three results is half right, have the winning agent revise once more with reference to another's changes, or pick the good parts by hand.
  • Pipeline handoffs go through files: shared artifacts like the Spec, CONTEXT.md and test results spare downstream agents from rereading the whole upstream conversation.
  • Cross-review: another developer has agents from other vendors do adversarial review after the coding agent finishes, with all issues fed back to the main coding agent for fixing and re-verification.

Common Misconceptions

  • "The more racers, the better." Returns diminish while cost grows linearly and review burden multiplies.
  • "The finer the pipeline roles, the better." Every handoff can lose information; Anthropic also warns that tasks with many inter-agent dependencies are not a good fit today.
  • "If three agents agree, it must be right." Agreement raises confidence, but tests are still needed.
