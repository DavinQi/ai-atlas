Multi-Agent and Harness: Iterate in a Controlled Loop Until Verification Passes

Companion to diagram #15 · Chapter 2 "Agent Design: Principles & Patterns"

When one agent's context can't hold everything and time is short, the natural idea is to bring in more agents and divide the work. The top half of diagram #15 shows three common divisions of labour: orchestrator–workers, pipeline, and generator–reviewer. The bottom half shows something more important: a harness loop. A task goes into planning, the plan goes to tool execution, the results must pass verification (tests, lint, type checks); if they fail, the errors and test output go back into context for a retry, and only when they pass is a PR submitted. The whole execution and verification process is framed inside a sandbox.

The core message of the diagram: the value of multiple agents can only be realised reliably inside a controlled loop. "Harness" here means the layer of engineering wrapped around the model: tools, permissions, context management, verification rules and stop conditions. We first look at the three divisions of labour, then at why the harness matters more than the division itself.

1. Three divisions of labour

Orchestrator–workers. In Anthropic's pattern catalogue, a central LLM dynamically breaks down the task, delegates to worker LLMs and synthesises the results. It differs from simple parallelisation in that the subtasks aren't hard-coded in advance; the orchestrator decides after seeing the input. That suits coding tasks where "you don't know in advance which files need changing": after reading the issue and the code structure, the orchestrator decides to send one worker to the API layer, one to the data layer and one to write tests.

Pipeline. The task flows in a fixed order through several specialised agents, such as requirements analysis → coding → testing. MetaGPT encodes a software company's standard operating procedures (SOPs) into multi-agent collaboration, with roles such as product manager, architect and engineer handing off artefacts according to the process; ChatDev advances each phase through conversation. A pipeline's advantage is that each stage has a single responsibility and checkable output; the risk is that upstream errors propagate all the way downstream.

Generator–reviewer (debate / review). One agent generates, another reviews and gives feedback, iterating to improve, corresponding to Anthropic's "evaluator–optimiser" pattern. Research on multi-agent debate also found that having several model instances debate the same question over multiple rounds improves reasoning and factual accuracy. Frameworks such as AutoGen turn this kind of conversational collaboration into a general programming interface.

2. A real, public case

Anthropic published the design and data of its multi-agent research system, one of the few first-hand sources available:

  • Structure: a lead agent plans the research process, then creates several parallel subagents to search simultaneously; each subagent explores one aspect of the problem in its own context window and returns the most important information, compressed, to the lead agent.
  • Results: a system with Claude Opus 4 as lead and Claude Sonnet 4 as subagents outperformed single-agent Claude Opus 4 by 90.2% on its internal research evaluation.
  • Why: in their analysis, token usage alone explained 80% of the variance in performance, with the number of tool calls and model choice as the other two factors. In other words, multiple agents mainly let the system "spend more tokens": each subagent has a clean context and can read more material in parallel.
  • Cost: agents use about 4× the tokens of ordinary chat, and multi-agent systems about 15×.

These numbers give a clear criterion: multiple agents suit tasks that are highly parallelisable, involve more information than one context can hold, and need many tool calls, and the task must be valuable enough to cover roughly 15× the cost.

3. Why be especially careful with coding tasks?

The same article names two limitations: domains where all agents need to share the same context, or where agents have many dependencies on each other, are not currently a good fit for multiple agents; and most coding tasks involve fewer truly parallelisable parts than research tasks, while LLM agents are not yet good at real-time coordination and delegation.

The reason is easy to see. In research, "look up company A's financials" and "look up company B's" don't affect each other; in coding, change an interface signature and every caller must change too, and if two agents each change half, merging produces conflicts. Chapter 5 explains how engineering practice often gives each agent an isolated working copy with git worktrees, precisely to make such dependencies explicit.

4. The harness: turning "probably right" into "verified right"

Whether one agent or many, the model's output is essentially "probably right". The harness turns it into "verified right". Each step of the loop in the diagram matters:

Task / spec. The entry point needs a clear goal and acceptance criteria. "Fix the login bug" isn't a good task; "return 401 when a user logs in with an expired token, add the corresponding unit tests, and keep all existing tests passing" is. The acceptance criteria are the basis for verification later.

Sandbox / controlled environment. Tool execution and verification happen in an isolated environment: a separate container or working directory, with network and file-system access opened only as needed. The cost of an agent's mistakes is confined to the sandbox.

Verification: objective signals, not subjective judgement. Anthropic stresses that agents need ground truth from the environment at every step. In coding, the most reliable "evaluators" are tests, type checks, lint and build results, not another model's opinion. Model review can supplement (for readability, say) but can't replace executable checks.

Failures go back in. When verification fails, put the error messages and test output back into the context verbatim and let the model correct accordingly. This is the engineered version of the previous article's Reflection paradigm: the more specific the external signal, the more accurate the next round's correction.

Stop conditions. Set a maximum number of iterations and a budget cap. After several consecutive failures, escalate to a person instead of looping forever.

State and compounding errors. Anthropic also warns that agents are stateful and errors compound: one early bad decision affects every later step. When updating their system they use "rainbow deployments" to shift traffic gradually so long-running tasks aren't interrupted, and in evaluation they focus on whether the end state is correct rather than analysing every turn.

5. A minimal harness checklist

Component Purpose Coding example
Task description and acceptance criteria Define "done" Issue + tests that must pass
Isolated execution environment Limit the blast radius of mistakes Containers, separate worktrees
Automated verification Provide objective feedback Unit tests, type checks, lint, build
Feedback loop Turn failures into information Put the raw error text back into context
Stop and escalation rules Prevent runaway behaviour At most N rounds, then hand to a person
Complete logs Enable audit and review Inputs and outputs of every tool call

6. Three common misconceptions

  • "More agents are faster." Parallel gains depend on whether the task splits into independent parts; coordination has its own cost, and token usage multiplies.
  • "Having another model review it is enough." Model review can supplement, but executable tests and checks provide objective signals.
  • "Multi-agent is the default architecture." It's an upgrade for when a single agent isn't enough. Getting a single agent's harness solid first usually pays off more; see the decision tree in the next article.
