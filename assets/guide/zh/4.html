数据与分词：文本先切成 token，再映射成向量

对应图 #4 · 第一章「大模型如何训练」

模型从不直接「看」文字。一句 public class UserService 在进入 Transformer 之前，要先后经过三道工序：数据管线决定哪些文本有资格被读；分词器把文本切成一串离散的 token，并换成整数 id；嵌入矩阵再把每个 id 查表变成一个向量。图 #4 的左半边画的是第一道工序，右半边画的是后两道。三者看似是「预处理」，却直接决定了模型能力的上限、训练算力的效率，以及不同语言用户付出的成本是否公平。

一、数据管线：从网页到训练语料

预训练语料的主体来自网页抓取，最常用的源头是 Common Crawl。原始网页里充满导航栏、广告、乱码、重复页面和机器生成的垃圾，直接拿来训练既浪费算力，也会教坏模型。所以典型的管线是一串过滤器：

  1. 文本抽取：从 HTML 中取出正文，丢掉模板和脚本。
  2. 语言识别：按语言分流，方便后续按比例配比。
  3. 质量过滤：先用启发式规则（太短、符号比例异常、重复行过多）剔除明显的垃圾，再用小模型给文本打分。
  4. 去重：用 MinHash 等近似去重方法删除大量重复或近似重复的页面。
  5. 安全过滤：去掉个人隐私信息和有害内容。

这条管线到底值多少？FineWeb 给出了少见的系统证据。团队从 96 个 Common Crawl 快照构建出 15T token 的数据集，并对每一步去重和过滤策略做了消融实验：用相同规模的小模型分别在不同版本的数据上训练，比较下游表现。更有意思的是它的子集 FineWeb-Edu：用一个分类器挑出「有教育价值」的网页，得到 1.3T token，在 MMLU、ARC 等知识与推理基准上带来了显著提升。结论很反直觉：经过筛选的较小子集，可以明显优于更大的未筛选数据。

去重还有一层容易被忽略的作用：评测的可信度。如果训练数据里混入了评测题，分数就会虚高，而模型并没有真的学会。另外，下一篇会讲到，被重复很多次的文本更容易被模型逐字记住，这同时带来隐私和版权风险。

二、分词：为什么不是按字，也不是按词？

假设我们直接按字符喂给模型。英文只有几十个字符，词表很小，但一句话会变成很长的序列：模型每生成一个 token 都要完整算一遍，序列越长，计算越多，能看到的上下文也越短。反过来按完整单词切，序列短了，但词表会爆炸，而且总会遇到没见过的词（新名词、拼写错误、代码里的变量名），只能标成「未知」。

子词（subword）分词是两者的折中：常见的词是一个 token，罕见的词拆成几个常见片段。Sennrich 等人 2015 年把字节对编码（BPE）引入神经机器翻译，算法简单到可以手算：

  1. 从单个字符（或字节）开始，每个字符都是一个符号。
  2. 统计语料中所有相邻符号对的出现次数。
  3. 把出现最多的一对合并成一个新符号，加入词表。
  4. 重复第 2、3 步，直到词表达到预定大小。

举个手算的例子。语料里有 low 出现 5 次、lower 2 次、newest 6 次、widest 3 次。第一轮统计，e s 和 s t 都出现了 6+3=9 次，并列最多（假设按顺序先合并 e s，得到 es）；下一轮 es t 同样出现 9 次，合并成 est。（这里为了演示省略了论文中的词尾标记。）几轮之后，est 成了一个 token，newest 就能切成 new + est。合并规则完全由语料频率决定：常一起出现的片段被「焊」成整体，模型就不必反复去猜这种显而易见的搭配，同样长度的上下文也能装下更多内容。

BPE 也天然没有「未登录词」：最坏情况下，任何字符串都能退回到单个字节表示。SentencePiece 则把原始文本连同空格一起当作序列处理，不需要先按空格切词，所以对中文、日文这类不用空格分词的语言更友好。

Karpathy 在讲解分词器时强调一个工程事实：分词器是 LLM 流水线中完全独立的一个阶段。它有自己的训练集和训练算法（BPE），训练完提供 encode() 和 decode() 两个函数；之后才训练语言模型。这意味着分词器的选择一旦定下，就和嵌入矩阵绑死了：换分词器通常等于重训模型，或者至少要大量继续训练。

三、分词的连锁反应

分词粒度看似是个技术细节，却会一路影响到用户体验和账单。

压缩率决定「读」多少。 Llama 3 把词表扩到 128K（100K 来自 tiktoken，另加 28K 非英语 token）。相比 Llama 2 的分词器，英文样本上每个 token 平均对应的字符数从 3.17 提高到 3.94。作者指出，这让模型在同样的训练算力下能「读」更多文本。新增的 28K 非英语 token 改善了这些语言的压缩率和下游表现，对英文分词没有影响。

token 数就是成本。 API 按 token 计费，上下文窗口也按 token 计算。同样一段中文，在不同模型的分词器下 token 数可能差很多。估算成本或判断「这份文档能不能放进上下文」时，应该用对应模型的分词器实测，而不是按字数估算。

词表大小是一个权衡。 词表越大，序列越短，注意力计算和 KV Cache 都更省；但嵌入层和输出层的参数随词表线性增长，罕见 token 得到的训练也更少。

一些「低级错误」源自分词。 让模型数 strawberry 里有几个 r、把一个长数字倒过来写、做精确的多位数运算，常常出错。原因之一是模型看到的不是一个个字符，而是几个子词 id：它要从「这些片段由哪些字母组成」的间接知识里推出答案。实践中的应对很简单：让模型写一段代码来数，或者调用计算工具。

四、嵌入：从 id 到向量

分词之后，public class UserService 变成了一串整数，比如 [1212, 1888, 2938, 1860]（图中数字为示意）。整数本身没有「意思」：1888 和 1889 并不比 1888 和 50000 更相近。模型需要的是能表达相似性的表示，这就是嵌入（embedding）。

设词表大小为 V、隐藏维度为 d，嵌入矩阵 E∈RV×d，token id 为 i 的向量就是 E 的第 i 行。这一步只是查表，但表里的数字是和模型其余部分一起训练出来的。训练会把在相似上下文中出现的 token 推到相近的位置，向量之间的点积可以用来衡量「有多像」。

位置也要编码进去。 注意力本身只看相关程度，不知道顺序：把「狗咬人」的「狗」和「人」交换位置，如果不加位置信息，注意力的计算结果完全一样。原始 Transformer 把正弦、余弦函数生成的位置向量加到 token 向量上；现代模型多用旋转位置编码（RoPE）。RoPE 不改 token 向量本身，而是在计算注意力时把 query 和 key 按「与位置成正比的角度」旋转。两个向量的点积只取决于长度和夹角，旋转后多出的夹角只和两者的位置差有关，所以注意力分数只依赖相对距离，而不是绝对位置。Llama 3 还把 RoPE 的基频提高到 500,000，以支持更长的上下文。

五、几个值得记住的判断

  • 数据质量比数据数量更值钱。 在算力固定时，把预算花在过滤和去重上，往往比单纯加数据更有效，FineWeb-Edu 就是例证。
  • 分词器决定了「同样的钱能读多少」。 对中文等非英语场景，先实测 token 数再谈成本和上下文容量。
  • 拼写、计数、精确计算类错误，先怀疑分词，再怀疑模型。 工具调用通常比提示技巧更可靠。
  • 分词器不能随便换。 它和嵌入矩阵一一对应，是模型的一部分，而不是一个可插拔的预处理脚本。
