7 天落地路线图：个人 / 小团队这周就能开始

对应图 #28 · 第四章「当前如何做 AI 编程」

前几篇讲了原则，本篇把它们压缩成一份个人或小团队一周内可以执行的清单。路线图本身是讲者基于阿里巴巴实践手册整理的建议，不是某家公司的官方流程。手册给刚起步团队的核心建议是：不需要一次建设完整体系，先建立项目地图、规范复杂需求、提供可验证反馈，并打通线上事实链，形成基本闭环。

和前几篇不同，这一篇按天写，每一天都说明「做什么、为什么、做完的标志是什么」。

第 1 天：选一个真实小任务，跑通一次

做什么。 选一个边界清晰、有测试的缺陷或小需求，让 Coding Agent 从头做完。全程记录：耗时多少？它在哪里卡住？你介入了几次？

为什么。 先体验，再设计流程。很多团队一上来就写规范，结果规范针对的是想象中的问题，而不是真实的问题。今天记下的每一个「卡住」，都是后面几天的原材料。

完成标志。 一个合并的 MR，外加一份问题清单。

第 2 天：写项目规则文件

做什么。 在仓库根目录写 AGENTS.md 或 CLAUDE.md，包括：技术栈、目录结构、构建与测试命令、禁止事项，以及需要停下来请示的操作（数据库迁移、密钥、生产环境）。提交到 Git。

为什么。 第 1 天的问题清单里，很可能有「它用了错误的包管理器」「它不知道测试命令」这类问题。这些都是规则文件该解决的。

注意。 别一次写成几十条。X 上分享 Orca 用法的开发者建议，Agent 在同一件事上反复犯错时再补一条。他的示例规则包括「已有测试只许新增，不许改、不许删」和「碰到数据库迁移、支付密钥、生产环境先停下来问我」。前一条正对应第三章提到的风险：Agent 可能为了让测试通过而修改测试。

第 3 天：补项目地图

做什么。 写清关键模块的职责、入口和依赖关系。可以让 Agent 先读代码起草，人来校对。

为什么。 这是上下文工程（第 2 篇）中的「项目地图」。人校对的过程本身就很有价值：Agent 起草时理解错的地方，恰好暴露了代码中不够清晰的部分。

第 4 天：把验证命令一键化

做什么。 让编译、类型检查、lint、单元测试可以用一条命令跑完，并把这条命令写进规则文件，要求 Agent 每次改完都执行。

为什么。 这是分层验证（第 4 篇）的秒级层。没有这一层，Agent 的每一次修改都只能靠你来检查。这一天的投入，回报可能是整周最高的。

第 5 天：用 Spec 做一个中等需求

做什么。 选一个比第 1 天更复杂的需求。先让 Agent 读需求和代码，主动追问；把约束、验收标准和非目标写进 Spec；再让它实现。

为什么。 练习第 3 篇的「先澄清再动手」，体会约束与假设分开写的效果。可以对比第 1 天：返工次数少了吗？

第 6 天：建立审阅习惯

做什么。 保持 MR 小；审阅时先看测试结果和核心逻辑，特别留意对测试的修改；把意见一次性反馈给 Agent 返工，而不是自己动手改。

为什么。 自己改，Agent 学不到，下次还会犯；把意见反馈给它，必要时补进规则文件，问题才会真正收敛。

第 7 天：复盘并沉淀

做什么。 回答三个问题：

  1. Agent 在哪些地方反复犯错？→ 补一条规则。
  2. 哪个流程重复了三次以上？→ 整理成 Skill（另一位开发者的「三次原则」）。
  3. 这周的交付周期和返工次数是多少？→ 记为基线。

为什么。 没有第 1 天和第 7 天的对比数据，就无法判断是否真的提效。第 6 篇介绍的 METR 研究说明，感觉不可靠。

一周之后

这七天对应着四个基本闭环：项目地图（第 2、3 天）、规范需求（第 5 天）、可验证反馈（第 4、6 天）、度量与沉淀（第 7 天）。线上事实链（第 5 篇）通常需要基础设施支持，可以作为下一阶段的目标。

Anthropic 在《Building effective agents》中的建议同样适用：从最简单的方案开始，只在能证明效果时增加复杂度。 手册也提到，早期方法尚不成熟时，允许不同成员分头探索并定期交流，比过早统一规范更有利于找到有效路径；实践稳定后再收敛为统一工作流。

常见误区

  • 「先买最贵的工具、上多 Agent。」 在单 Agent + 规则 + 验证闭环跑通之前，多 Agent 只会放大混乱。
  • 「一周就能看到 10 倍提效。」 一周的目标是建立闭环和基线，不是出成绩。
  • 「规则文件写完就不用管。」 它应该随项目和团队经验持续演进。
