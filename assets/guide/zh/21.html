四代工具对比：自主度越高，越依赖自动验证

对应图 #21 · 第三章「编程的进化」

把前几篇放在一起，可以得到四代开发工具：传统 IDE → AI 补全 → AI IDE → Coding Agent。从左到右，AI 承担的工作越来越多，人的介入越来越少。但这张对比图真正想说的不是「越新越好」，而是一条约束：每多一分自主度，就要多一分自动化验证来兜底。 这是本章最重要的结论。

一、四代工具一览

代际 AI 做什么 人做什么 人审阅的单位
传统 IDE 无（静态分析） 全部 自己写的每一行
AI 补全 预测下一段代码 逐条接受或拒绝 一行 / 一段
AI IDE 对话、多文件修改 审每个 diff 一个 diff
Coding Agent 读、改、跑、修的闭环 定任务、审 PR 一个 PR

最后一列是理解这张表的钥匙。人审阅的单位越来越大，审阅的细致程度必然越来越低。 看一行补全，人几乎不会漏掉错误；看一个改了二十个文件的 PR，人很可能只看核心逻辑和测试结果。那么，那些人没看的地方，由谁保证正确？

二、为什么自主度越高越依赖验证？

理由一：人工审查的粒度变粗了。 上面已经说明。

理由二：错误会累积。 Anthropic 指出 Agent 是有状态的，错误会累积；自主性意味着更高的成本和错误累积的风险。用一个粗略的算术来体会：假设每一步独立地有 95% 的概率做对，那么连续 10 步全对的概率是 0.95¹⁰ ≈ 60%，连续 20 步是 0.95²⁰ ≈ 36%。真实情况下各步并不独立，这只是示意；但趋势很清楚：步骤越多，没有中途检查的长链条越容易出错。 中途的验证就像在链条上加检查点，每一步错了都能被及时发现、纠正，不会传下去。

理由三：验证是 Agent 自我纠错的唯一可靠信号。 Anthropic 强调 Agent 每一步都要从环境中获得「真实反馈」。模型自己说「我改好了」不算数，测试通过才算数。

阿里巴巴《AI Native 研发范式实践手册》（解读版）提出了一个更宏观的规律：AI 总是优先解决那些反馈公开、验证可以规模化的问题，这也是编码最先被解决的原因。代码可以编译、可以跑测试，对错有客观标准；相比之下，「这个产品需求合不合理」就很难自动验证。

三、一条贯穿始终的线：可自动验证

把本书前后的里程碑串起来看，会发现「可自动验证」贯穿了评测、训练和使用三个环节：

  • 评测：2021 年的 HumanEval 用单元测试衡量功能正确性；2023 年的 SWE-bench 用仓库原有的测试判断 issue 是否被修复。
  • 使用：2023 年的 Reflexion 让 Agent 读取测试反馈，在下一次尝试中改进。
  • 训练：2025 年的 DeepSeek-R1 在可验证奖励上做强化学习，代码题用编译器和测试判分（见第一章「后训练」）。

上一篇 Codex 的 28.8% → 70.2% 也是同一个道理：采样 100 次，正确答案大概率在里面，难的是挑出来。有了测试，机器就能自己挑。验证能力，就是把模型的「潜在能力」变成「可交付结果」的那个转换器。

四、怎么选：按风险而不是按新旧

既然自主度和验证必须匹配，选工具就变成了一个问题：这个任务的验证条件和出错代价是什么？

场景 验证条件 出错代价 合适的方式
探索性原型、内部脚本 跑一下就知道 低 Agent 高度自主
有完善测试的业务模块 测试覆盖好 中 Agent 闭环 + 人审 PR
缺少测试的遗留代码 弱 中到高 先让 Agent 补测试，再改功能
支付、权限、数据迁移 难以完全自动化 高 降低自主度，AI IDE 逐个 diff 审，加人工关卡

第三行值得单独说一句：先补验证，再提自主度。 对没有测试的模块，最划算的第一个任务往往不是「改功能」，而是「为现有行为补测试」：这样既给后续修改建立了安全网，也让人有机会检查 Agent 对代码的理解对不对。

验证还要覆盖真实路径。 前述 X 上那位开发者的经验是：单元测试写得再多，上线仍可能出错；关键是为 Agent 提供端到端的测试环境，让它能从真实入口执行到用户需要的结果，并能查库表和日志。单元测试验证的是「零件」，端到端测试验证的是「整机」。

五、常见误区

  • 「最新一代工具一定最好。」 合适的代际取决于任务和验证条件。同一个团队同一天里，可能在原型上用 Agent，在支付模块上逐个 diff 审阅。
  • 「有 Code Review 就够了。」 人的审阅速度难以跟上 Agent 的产出速度，需要机器先把关，人再看机器看不了的部分（见第四章「分层验证」）。
  • 「测试通过就万事大吉。」 测试只能证明它覆盖到的部分。Agent 甚至可能为了让测试通过而修改测试本身，所以审阅时要特别留意对测试的改动。

小结

本章的时间轴、基线图、补全、Agent 和这张对比表，讲的是同一件事：机器接管的越多，人越要把精力放在「定义什么是对的」上。 下一章，将从单个开发者扩展到整个团队：当编码不再是瓶颈，研发流程该如何重新组织。
