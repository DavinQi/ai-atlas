未解问题，和明天就能做的 5 件事

对应图 #38 · 第六章「AI 改变研发流程」

概述

本手册的最后一篇，回到两个问题：哪些事情还没有答案？明天能做什么？ 未解问题部分主要依据阿里巴巴实践手册的总结；「5 件事」是讲者基于全书内容给出的建议。

核心机制

四个尚未解决的问题（据阿里巴巴实践手册）：

  1. 从写代码到可靠交付，仍有较多技术问题。 软件交付的最后一公里——构建、集成测试、灰度发布、生产验证、故障恢复——容错空间极小，对 Sandbox 隔离、凭证管理、Guardrail 和可观测能力的要求远超当前水平。基础设施本身的工程复杂度，可能不亚于 Agent 应用层。
  2. 企业知识还没有做到 Agent 友好。 大量组织知识散落在文档、口头传递和个人经验中，即便进了知识库，也往往停留在「人能查到」，距离被 Agent 高效检索、准确理解和可靠引用还有很大差距。
  3. 组织设计影响深远，尚无确定答案。 一方面需要新的激励机制释放个体潜力，另一方面「蒸馏焦虑」真实存在。
  4. 技术迭代速度持续冲击现有架构。 SWE-bench Verified 成绩两年间从不足 30% 跳到 80% 左右，今天设计的架构、工具和流程，可能半年后就要重新审视。

此外还有一个常被低估的问题：审阅是瓶颈。X 上一位开发者的经验是，生成越来越快，人不再逐行阅读所有代码，而是依靠小 MR、端到端测试和对核心业务逻辑的重点审查。

工程实践与数字

明天就能做的 5 件事：

  1. 写一份项目规则文件（AGENTS.md / CLAUDE.md）：技术栈、构建与测试命令、禁止事项、需要请示的操作，提交到 Git。
  2. 把验证一键化：编译、类型检查、lint、单元测试一条命令跑完，让 Agent 每次改完都执行。
  3. 下一个需求先写 Spec：让 Agent 追问澄清，分开写约束和假设，验收标准尽量能转成测试。
  4. 测量一个基线：记录需求从提出到上线的周期和返工次数，而不是统计 AI 代码占比。
  5. 给 Agent 划权限边界：只读优先，高风险操作必须人工确认，外部内容视为数据而非指令。

常见误区

  • 「等技术成熟再开始。」 手册明确提醒，不要因为等更好的模型而推迟必要的基础设施建设。
  • 「这些问题解决了才能用 AI。」 未解问题是关于规模化和高风险环节的；个人和小团队的闭环今天就能建立。
  • 「照搬某家公司的做法。」 手册自称不是成熟的方法论，更不是标准答案，应根据自己的约束取舍。
