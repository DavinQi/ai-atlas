未解问题，和明天就能做的 5 件事

对应图 #38 · 第六章「AI 改变研发流程」

这是本手册的最后一篇，回到两个问题：哪些事情还没有答案？明天能做什么？ 未解问题部分主要依据阿里巴巴实践手册的总结；「5 件事」是讲者基于全书内容给出的建议。

一、四个尚未解决的问题

据阿里巴巴实践手册：

1. 从写代码到可靠交付，仍有较多技术问题。 软件交付的最后一公里，即构建、集成测试、灰度发布、生产验证、故障恢复，容错空间极小，对 Sandbox 隔离、凭证管理、Guardrail 和可观测能力的要求远超当前水平。基础设施本身的工程复杂度，可能不亚于 Agent 应用层。

这意味着什么？回想第三章的 SWE-bench：在一个准备好的仓库里修一个 issue，用现成的测试判断。真实交付比这复杂得多：环境要自己搭，测试可能不全，发布要过流程，出了问题要能回滚。基准测的是「写对代码」，交付需要的是「安全地把代码送到用户面前」。

2. 企业知识还没有做到 Agent 友好。 大量组织知识散落在文档、口头传递和个人经验中；即便进了知识库，也往往停留在「人能查到」，距离被 Agent 高效检索、准确理解和可靠引用还有很大差距。「人能查到」和「Agent 能用」之间的差别在于：人会自己补全上下文、判断文档是否过时，Agent 往往不会。

3. 组织设计影响深远，尚无确定答案。 一方面需要新的激励机制释放个体潜力，另一方面「蒸馏焦虑」真实存在（上一篇）。

4. 技术迭代速度持续冲击现有架构。 SWE-bench Verified 成绩两年间从不足 30% 跳到 80% 左右。今天设计的架构、工具和流程，可能半年后就要重新审视。一个具体的例子是第四章提到的观察：模型变强后，一些原本有用的约束和流程（比如重型的 Spec 和 TDD Skill）正在变成噪声。

二、两个常被低估的问题

审阅是瓶颈。 X 上一位开发者的经验是：生成越来越快，人不再逐行阅读所有代码，而是依靠小 MR、端到端测试和对核心业务逻辑的重点审查。但这种做法本身就是一种取舍：没人看的代码，就只能依赖测试。审阅能力如何跟上生成速度，是从个人到组织都还在摸索的问题。

安全没有万无一失的方案。 第二章介绍过：2023 年的间接提示注入研究表明，Agent 读到的外部内容可能包含恶意指令；OWASP LLM01 把提示注入列为头号风险，并指出目前没有万无一失的防御。Agent 能做的事越多，这个问题就越重要。

效果仍需谨慎测量。 2025 年 METR 的随机对照试验提醒：AI 对资深开发者的实际影响，必须用客观数据测量。

三、明天就能做的 5 件事

全书讲了很多原则，最后压缩成五件事。每一件都对应前面的某一章，也都不依赖未解问题的答案：

1. 写一份项目规则文件（AGENTS.md / CLAUDE.md）。写技术栈、构建与测试命令、禁止事项、需要请示的操作，提交到 Git。→ 第四章上下文工程。

2. 把验证一键化。 编译、类型检查、lint、单元测试用一条命令跑完，让 Agent 每次改完都执行。→ 第三章「自主度越高越依赖验证」、第四章分层验证。

3. 下一个需求先写 Spec。 让 Agent 追问澄清，分开写约束和假设，验收标准尽量能转成测试。→ 第四章 Spec 驱动。

4. 测量一个基线。 记录需求从提出到上线的周期和返工次数，而不是统计 AI 代码占比。→ 第四章阿姆达尔定律与度量。

5. 给 Agent 划权限边界。 只读优先，高风险操作必须人工确认，外部内容视为数据而不是指令。→ 第二章护栏、第六章风险分级。

这五件事有一个共同点：它们都不是在优化模型，而是在建设模型周围的东西：上下文、验证、需求、度量和边界。这也是全书反复出现的主题：从第一章的「模型只知道上下文里的东西」，到第三章的「自主度越高越依赖验证」，再到第四章的「编码之外才是瓶颈」。

四、常见误区

  • 「等技术成熟再开始。」 手册明确提醒，不要因为等更好的模型而推迟必要的基础设施建设。
  • 「这些问题解决了才能用 AI。」 未解问题是关于规模化和高风险环节的；个人和小团队的闭环今天就能建立。
  • 「照搬某家公司的做法。」 手册自称不是成熟的方法论，更不是标准答案，应根据自己的约束做取舍。
