传统 CI/CD：流水线自动跑，判断仍在人

对应图 #34 · 第六章「AI 改变研发流程」

概述

持续集成与持续交付（CI/CD）把构建、测试、部署变成了自动运行的流水线，是过去十几年软件工程最重要的进步之一。但在传统的 CI/CD 和运维体系中，执行是自动的，判断仍然在人：测试失败了谁来看原因？告警响了谁来定位？发布要不要继续？事故之后怎么复盘？这些都依赖工程师的经验。

核心机制

1. 流水线自动化。 典型流程：提交 → 构建 → 单元测试 → 集成测试 → 制品 → 预发 → 灰度 → 生产。Google SRE Book 中的发布工程章节强调了两个原则：团队要能自助发布（self-service）；构建要「封闭」（hermetic），不受构建机器上安装的库和软件影响，保证可重复。

2. 人负责判断的环节：

  • 测试失败与构建报错的分析
  • 告警分诊与故障定位
  • 发布的继续、暂停或回滚决策
  • 事故复盘与改进措施

3. 琐事（toil）。 SRE Book 对琐事的定义是：与运行生产服务相关、手动的、重复的、可自动化的、战术性的、没有持久价值的，并且随服务增长线性增加的工作。Google 的目标是把每位 SRE 花在琐事上的时间控制在 50% 以下，至少一半时间用于能减少未来琐事或增加服务功能的工程工作；书中提到季度调查显示 Google SRE 平均约 33% 的时间花在琐事上。

4. 用数据而不是感觉做决策。 SRE 用基于服务等级目标（SLO）的错误预算决定发布节奏：错误预算给出一个季度内服务允许多不可靠的客观指标。事故复盘则强调「无责」：聚焦找出导致事故的因素，而不是指责个人或团队。

关键论文与里程碑

  • Google SRE Book：琐事、错误预算、发布工程、无责复盘
  • DORA 指标：变更前置时间、部署频率、失败部署恢复时间、变更失败率、部署返工率

工程实践与数字

  • DORA 的五个指标是衡量这条流水线的通用语言：吞吐看变更前置时间（从提交到部署到生产）、部署频率和失败部署恢复时间；不稳定性看变更失败率和部署返工率。
  • AI 最先切入的是琐事：重复、可自动化、没有持久价值的工作，正是 Agent 的理想对象。
  • 阿里巴巴实践手册的观察：编码 1 小时就能完成的需求，经过多个内部平台、发布流程和环境约束，从代码完成到最终生效仍可能需要数周。流水线之外的人工节点，是端到端效率的主要瓶颈。

常见误区

  • 「有了 CI/CD 就是 DevOps。」 自动化执行只是基础，判断环节仍大量依赖人。
  • 「琐事说明团队不够努力。」 SRE Book 把琐事视为需要用工程手段系统消除的对象，而不是个人问题。
  • 「AI 会替代流水线。」 恰恰相反，可靠的流水线是 Agent 获得验证信号的基础设施。
