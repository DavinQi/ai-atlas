AIOps 自修复闭环：低风险自动，高风险过人

对应图 #35 · 第六章「AI 改变研发流程」

概述

把 Agent 接入运维流程后，可以形成一个自修复闭环：发现问题 → 收集证据 → 诊断 → 生成修复 → 验证 → 发布 → 观察。关键设计不在于 Agent 能修多少，而在于按风险分级：低风险、可快速回滚的操作可以自动执行；高风险、不可逆的操作必须经过人。

核心机制

1. 闭环的每一步：

  • 发现：告警、错误率、用户反馈，或 CI 中的失败。
  • 证据：按排障证据链先收集 TraceId、日志、上下游状态、代码位置和最近变更（见第四章）。
  • 诊断：明显错误由诊断 Agent 直接定位；证据不足或矛盾时升级。
  • 修复：生成补丁，同时补一条能复现问题的回归测试。
  • 验证：分层验证，先过机器的关。
  • 发布与观察：渐进式发布，观察关键指标，异常即回滚。

2. 风险分级。 OWASP 的缓解建议明确要求：对特权操作实施人在回路控制，高风险操作须人工批准；为应用提供独立令牌并实行最小权限。MCP 规范也要求调用工具前获得用户明确同意。一个实用的分级：

风险 示例 处理方式
低 重启无状态实例、扩容、回滚到上一版本 自动执行并通知
中 配置修改、小范围代码修复 自动生成，人一键批准
高 数据库迁移、权限变更、资金相关 必须人决策

3. 渐进式发布。 Anthropic 在其多 Agent 系统中使用「彩虹部署」：新旧版本同时运行，逐步把流量从旧版本切到新版本，避免更新打断正在运行的 Agent。同样的思路适用于 Agent 生成的修复：灰度、观察、再扩大。

工程实践与数字

  • 人工节点会吞掉自动化收益：手册记录，自动修复 bug 的比例达到 60% 以上，但 bug 日清率只从 53% 提升到最高 63%，原因是触发依赖人、校验依赖人。闭环要真正打通，必须让触发和低风险校验也自动化。
  • 最后一公里容错极小：手册指出，构建、集成测试、灰度发布、生产验证、故障恢复涉及真实环境、真实数据和真实用户，对 Sandbox 隔离、凭证管理、Guardrail 和可观测能力的要求远超当前水平。
  • 让 Agent 先拿只读权限：先在诊断环节建立信任，再逐步开放低风险写操作。
  • 所有自动操作留痕：谁（哪个 Agent）、代表谁、基于什么任务、做了什么。

常见误区

  • 「自修复就是全自动。」 风险分级和人工关卡是自修复系统的核心组成。
  • 「修复后测试通过就可以全量发布。」 生产环境的验证需要渐进式发布和观察。
  • 「Agent 出错率高，所以不能用在运维。」 关键是限定作用范围，让错误可回滚、可审计。
