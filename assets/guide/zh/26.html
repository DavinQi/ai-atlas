排障证据链：先收集证据，再推断根因

对应图 #26 · 第四章「当前如何做 AI 编程」

概述

线上排障最常见的错误是先猜根因，再找证据证明。人会这样做，Agent 更会这样做：模型天生擅长给出「看起来合理」的解释。排障证据链把顺序反过来：先按固定方式收集事实证据，再基于完整的请求链推断根因；证据不足时升级，而不是硬猜。

核心机制

千问用增团队的做法（据阿里巴巴实践手册）：

  1. 统一 TraceId：打通日志、上下游状态与代码调用关系。
  2. 先采证据：排障不从猜测根因开始，优先收集 TraceId、结构化日志、上下游状态、代码位置和调用关系等事实。
  3. 基于完整请求链判断。
  4. 分级诊断：明显错误由诊断 Agent 直接基于日志定位；证据不足或状态矛盾时，把已有证据交给具备完整代码上下文的 Agent 继续分析。
  5. 标准化：固定证据采集方式、升级条件和结论格式，让排障从依赖个人经验转向可复用、可验证的工程流程。

一条最小证据链：

现象（报错 / 告警 / 用户反馈）
→ TraceId → 链路上每一跳的日志与状态
→ 对应的代码位置与最近变更
→ 假设 → 用证据验证或否定
→ 结论（根因 + 证据 + 修复 + 回归测试）

工程实践与数字

  • 可观测性是前提：没有统一的 TraceId 和结构化日志，Agent 再强也无从下手。
  • 给 Agent 只读权限：排障阶段 Agent 应能查日志、查库表、查调用链，但不应直接修改生产。前述 X 上的开发者使用只读数据库 MCP 和日志 Skill。
  • 结论格式固定：根因、证据、影响范围、修复方案、回归测试。证据要能被人复核。
  • 证据沉淀为资产：手册指出，线上证据链和诊断能力会被后续 Agent 持续读取、验证和更新。
  • 把多端依赖纳入证据：手册中的另一个团队提到，统一 Workspace 判断跨工程契约，避免「改了公共能力但消费端没重建」导致在陈旧依赖上误判「已修复」。

常见误区

  • 「模型给出的根因听起来很合理，应该就是对的。」 没有证据支持的解释只是假设。
  • 「修复后测试通过就结束了。」 应补一个能复现原问题的回归测试。
  • 「证据收集太慢，直接让 Agent 改。」 固定的采集流程可以自动化，比反复试错更快。
