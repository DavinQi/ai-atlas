排障证据链：先收集证据，再推断根因

对应图 #26 · 第四章「当前如何做 AI 编程」

线上排障最常见的错误，是先猜根因，再找证据证明。人会这样做，Agent 更会：模型天生擅长给出「看起来合理」的解释。排障证据链把顺序反过来：先按固定方式收集事实证据，再基于完整的请求链推断根因；证据不足时升级，而不是硬猜。

一、一个「猜错」的例子

告警：下单接口的错误率在 14:05 突然升到 5%。

先猜的做法。 Agent 看到告警，又看到 13:50 有一次发布，于是推断：「是 13:50 的发布引入了 bug。」它找到那次发布的 diff，发现确实改了下单相关的代码，于是给出结论和回滚建议。这个推理链条每一步都「说得通」。

先采证据的做法。 拿一个失败请求的 TraceId，沿链路看每一跳：网关正常 → 订单服务正常 → 调用库存服务超时。再看库存服务：它依赖的缓存集群在 14:04 发生主从切换。最近的发布和这条链路完全无关。

如果按第一种做法回滚，错误率不会下降，团队还要再花时间排查，期间故障一直在持续。第一章讲过，模型生成的是「最可能的下一个 token」，不是「真的原因」。 「发布导致故障」是统计上很常见的模式，所以模型很容易说出来，但这次它不是事实。

二、为什么要「先证据」

第二章介绍的 ReAct（2022）有一个核心观察：通过与外部环境交互获取信息，可以缓解纯推理中的幻觉和错误传播。排障证据链就是这一原则在运维场景中的应用：每一步推断都要锚定在一个可以复核的事实上，而不是锚定在上一步推断上。

三、千问用增团队的做法

据阿里巴巴实践手册：

  1. 统一 TraceId：打通日志、上下游状态与代码调用关系。
  2. 先采证据：排障不从猜测根因开始，优先收集 TraceId、结构化日志、上下游状态、代码位置和调用关系等事实。
  3. 基于完整请求链判断，而不是只看报错的那一跳。
  4. 分级诊断：明显错误由诊断 Agent 直接基于日志定位；证据不足或状态矛盾时，把已有证据交给具备完整代码上下文的 Agent 继续分析。
  5. 标准化：固定证据采集方式、升级条件和结论格式，让排障从依赖个人经验，转向可复用、可验证的工程流程。

第 4 步的「分级」值得注意：大部分故障是简单的（空指针、配置错误），轻量的诊断 Agent 就能处理；只有少数复杂情况才需要动用更重的上下文。这和人类团队里一线值班、二线专家的分工是一样的。

四、一条最小证据链

现象（报错 / 告警 / 用户反馈）
→ TraceId → 链路上每一跳的日志与状态
→ 对应的代码位置与最近变更
→ 假设 → 用证据验证或否定
→ 结论（根因 + 证据 + 修复 + 回归测试）

注意「假设」出现在证据之后，而且后面跟着「验证或否定」。上面那个例子里，「发布导致故障」本可以作为一个假设，但证据（链路显示故障在库存服务）直接否定了它。

五、工程要点

  • 可观测性是前提。 没有统一的 TraceId 和结构化日志，Agent 再强也无从下手。证据链的质量上限，就是可观测性的质量。
  • 给 Agent 只读权限。 排障阶段，Agent 应能查日志、查库表、查调用链，但不应直接修改生产。前述 X 上的开发者使用只读数据库 MCP 和日志 Skill。
  • 结论格式固定：根因、证据、影响范围、修复方案、回归测试。证据要能被人复核，例如附上 TraceId 和日志片段，而不是只写「经分析，原因是……」。
  • 证据沉淀为资产。 手册指出，线上证据链和诊断能力会被后续 Agent 持续读取、验证和更新。今天的排障记录，就是明天的上下文。
  • 把多端依赖纳入证据。 手册中的另一个团队提到，用统一的 Workspace 判断跨工程契约，避免「改了公共能力但消费端没重建」，导致在陈旧依赖上误判「已修复」。

六、常见误区

  • 「模型给出的根因听起来很合理，应该就是对的。」 没有证据支持的解释只是假设。听起来越合理，越要检查。
  • 「修复后测试通过就结束了。」 应补一个能复现原问题的回归测试，否则同样的问题可能再次发生。
  • 「证据收集太慢，直接让 Agent 改。」 固定的采集流程可以自动化，比反复试错更快。上面的例子里，「先猜」看似快，实际慢得多。
