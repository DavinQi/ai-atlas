推理部署：Prefill 一次算完，Decode 逐 token 生成

对应图 #8 · 第一章「大模型如何训练」

训练只发生一次，推理却每天发生上亿次。一个模型好不好用、贵不贵，很大程度上是在推理阶段决定的。图 #8 把推理拆成三块：上面是 Prefill 与 Decode 两个阶段以及连接它们的 KV Cache；中间是三项服务化技巧（量化、连续批处理、PagedAttention）；下面是 MoE 的路由。这篇文章先讲清楚「为什么生成文字这么慢」，再看每项技术分别撬动了哪个瓶颈。

一、两个阶段，两种瓶颈

你在聊天框里按下回车，模型要做两件性质完全不同的事。

Prefill（预填充）：把整段提示一次性并行送入模型，计算所有位置的 K/V，并产出第一个 token。几千个 token 同时做矩阵乘法，GPU 的算力被充分利用，这一阶段是计算密集型，决定首 token 延迟（TTFT）。

Decode（解码）：之后每一步只输入上一步生成的 1 个 token，读取此前缓存的 K/V，生成下一个 token，直到结束。Leviathan 等人概括得很直接：生成 K 个 token 需要串行运行模型 K 次。每一步的计算量很小，却要把全部权重和 KV Cache 从显存读一遍。GPU 大部分时间在等数据，所以这一阶段是访存密集型，决定每个 token 的生成速度。

举一个量级：一个 70B 模型的 FP16 权重约 140 GB（70B × 2 字节）。如果一次只服务一个请求，每生成一个 token 都要把这 140 GB 读一遍。这就是几乎所有推理优化都围绕两件事展开的原因：让每次访存更省，让每次访存服务更多请求或产出更多 token。

二、KV Cache：用显存换计算

因果注意力里，历史位置的 K/V 一旦算出就不会改变。与其每生成一个 token 都把整段前文重算一遍，不如把它们缓存起来。代价是显存，每个 token 的缓存大小为：

bytes/token=2×L×nkv​×dhead​×b

2 代表 K 和 V，L 是层数，nkv​ 是 KV 头数，dhead​ 是每头维度，b 是每个数值的字节数。代入 Llama 3 70B（80 层、8 个 KV 头、每头 128 维、FP16）：2×80×8×128×2=327,680 字节，约 320 KB/token。一个 128K token 的上下文，仅 KV Cache 就要约 40 GB；如果同时服务 10 个这样的请求，就是 400 GB，远超权重本身。

长上下文的真正瓶颈往往是 KV Cache，而不是权重。 所以压缩 KV 是近几年架构演进的一条主线：

  • GQA：多个 query 头共享一组 KV 头。Llama 3 70B 用 8 个 KV 头对 64 个 query 头，KV 缩小到 1/8。如果是标准多头注意力，上面的 320 KB 会变成约 2.5 MB。
  • MLA：DeepSeek-V2 的多头潜在注意力把 KV 压缩成一个低维潜在向量，相比 DeepSeek 67B 减少了 93.3% 的 KV Cache，最大生成吞吐提升到 5.76 倍。

三、服务化三件套：让一次读取服务更多请求

连续批处理。 把多个请求拼成一批，读一次权重就能为整批各算一个 token，吞吐成倍提升。传统的静态批处理要等一批里最长的请求结束才能接新请求；连续批处理在每一步都可以让结束的请求离开、新请求加入，GPU 不会空等。代价是批越大，单个请求的延迟越高，吞吐和延迟需要按业务权衡。

PagedAttention。 批处理的上限取决于显存里能放多少 KV Cache。vLLM 论文测得，已有系统里只有 20.4%–38.2% 的 KV Cache 显存真正用来存放 token 状态，其余被「按最大长度预留」和碎片浪费了，因为没人事先知道一个回答会写多长。PagedAttention 借鉴操作系统的虚拟内存分页：把 KV Cache 切成固定大小的块，按需分配，逻辑上连续、物理上分散，几乎消除浪费。它还支持在不同序列之间共享块，比如很多请求共用同一段系统提示或同一份 RAG 文档时，前缀的 KV 只存一份。在相同延迟水平下，吞吐提升 2–4 倍。

量化。 权重从 16 bit 压到 8 bit 或 4 bit，显存占用和每步要读的字节数都成比例下降，正好打在 Decode 的访存瓶颈上。GPTQ 可在约 4 个 GPU 小时内把 175B 模型的权重量化到 3–4 bit，精度损失可以忽略；AWQ 观察到少量权重通道对激活特别敏感，根据激活分布保护这些关键权重。4 bit 权重量化在大模型上通常损失很小，但仍应在自己的任务上评测。

四、推测解码：一次验证好几个 token

既然 Decode 的瓶颈是「每个 token 都要串行跑一次大模型」，能不能一次多产出几个？推测解码的做法是：让一个小模型先快速起草 k 个 token，再让大模型一次前向并行验证这 k 个位置，接受与自己分布一致的前缀，在第一个不一致处用自己的结果替换。数学上可以保证输出分布与只用大模型完全相同，不是近似。小模型猜得越准，一次被接受的 token 越多；论文在 T5-XXL 上报告了 2–3 倍加速。

五、MoE：参数很多，每次只用一小部分

混合专家（MoE）把 Transformer 里的 FFN 换成多个「专家」，由一个路由器为每个 token 选出少数几个专家来计算。思路来自 Shazeer 等人 2017 年的稀疏门控 MoE 层；Switch Transformer 简化为每个 token 只路由到 1 个专家，在同等算力下预训练提速最多 7 倍。

  • Mixtral 8x7B：每层 8 个专家，每个 token 选 2 个，总参数 47B、每 token 激活 13B。
  • DeepSeek-V3：总参数 671B，每 token 激活 37B。

图中路由器选中了 E2 和 E5（top-2 示意）。MoE 的收益和代价要分清：它降低的是每个 token 的计算量，所以训练和推理的 FLOPs 按激活参数算；但显存并不省，全部专家权重都要加载，671B 的模型仍需要按 671B 准备显存。此外还有专家负载不均衡、跨卡通信等工程难题。

六、生成的最后一步：从概率表里挑一个

模型每一步输出的是一张概率表，怎样从中挑 token 也会影响输出质量。假设「他口渴了，于是喝了一杯」后面，模型给出水 69%、茶 25%、书 6%：

  • 贪心永远选最高的「水」，稳定但容易单调、重复。
  • 温度先把分数除以温度再做 softmax：温度 0.5 时分布变为约 88% / 12% / 0.7%，更集中、更保守；温度 2 时约为 53% / 32% / 16%，更多样，也更容易出错。
  • Top-p（核采样）从高到低累加概率，达到 p 就停：p=0.9 时，水 + 茶 = 94% 已超过 90%，只在这两者里按 73% / 27% 抽，「书」被排除。和固定保留 k 个候选的 Top-k 相比，它保留的候选数随情况自动变化。

Holtzman 等人发现，在开放式写作里一味追求最可能的文本，往往平淡、重复，甚至陷入循环，这也是核采样被提出的原因。写代码、抽取信息用低温度；写作、头脑风暴用较高温度。但要记住：采样只能在模型给出的概率里挑，改变不了模型本身的能力。

七、部署时的算账清单

  • 显存 = 权重 + KV Cache + 激活。 KV Cache 随并发数和上下文长度线性增长，常常是真正的上限。
  • 长上下文的成本不只是线性。 KV Cache 线性增长，但 Prefill 的注意力计算随长度平方增长。
  • 共享前缀要复用。 系统提示、RAG 文档放在固定位置，便于前缀缓存命中。
  • 优先用成熟引擎。 vLLM 等开源引擎已集成 PagedAttention、连续批处理、量化和推测解码。
  • 别被 MoE 的激活参数误导。 671B 总参数、37B 激活的模型，算力按 37B 估，显存按 671B 估。
