推理部署：Prefill 一次算完，Decode 逐 token 生成

对应图 #8 · 第一章「大模型如何训练」

概述

LLM 推理分两个阶段：

  • Prefill（预填充）：把整段提示一次性并行送入模型，计算所有位置的 K/V 并产出第一个 token。这一阶段是计算密集型，决定首 token 延迟（TTFT）。
  • Decode（解码）：每步只输入上一步生成的 1 个 token，读取此前缓存的 K/V，生成下一个 token，直到结束。这一阶段每步都要读一遍全部权重和 KV Cache，是访存密集型，决定生成速度（每 token 延迟）。

Leviathan 等人概括得很直接：生成 K 个 token 需要串行运行模型 K 次。几乎所有推理优化都围绕两件事展开：让访存更省，让每次访存服务更多请求或产出更多 token。

核心机制

1. KV Cache。 因果注意力中，历史位置的 K/V 不会改变，可以缓存复用，避免每步重算整段前文。每个 token 的缓存大小为：

bytes/token=2×L×nkv​×dhead​×b

（2 代表 K 和 V，L 为层数，nkv​ 为 KV 头数，dhead​ 为每头维度，b 为每个数值的字节数。）以 Llama 3 70B 为例（80 层、8 个 KV 头、隐藏维度 8192 / 64 头 = 每头 128 维），FP16 下每 token 约 2×80×8×128×2=327,680 字节，约 320 KB；128K token 的上下文仅 KV Cache 就要约 40 GB。

2. 压缩 KV。 GQA 让多个 query 头共享 KV 头，Llama 3 用 8 个 KV 头对 64 个 query 头，KV 缩小到 1/8。DeepSeek-V2 的多头潜在注意力（MLA）把 KV 压缩为潜在向量，相比 DeepSeek 67B 减少 93.3% 的 KV Cache，最大生成吞吐提升到 5.76 倍。

3. PagedAttention 与连续批处理。 vLLM 论文测得，已有系统中只有 20.4%–38.2% 的 KV Cache 显存真正用来存放 token 状态，其余被预留和碎片浪费。PagedAttention 借鉴操作系统的分页机制，把 KV Cache 切成固定大小的块按需分配，几乎消除浪费，并支持在不同序列间共享块；在相同延迟水平下吞吐提升 2–4 倍。

4. 混合专家（MoE）。 把 FFN 换成多个「专家」，由路由器为每个 token 选少数几个。思路来自 Shazeer 等人 2017 年的稀疏门控 MoE 层；Switch Transformer 简化为每个 token 只路由到 1 个专家，在同等算力下预训练提速最多 7 倍。

  • Mixtral 8x7B：每层 8 个专家、每个 token 选 2 个，总参数 47B、激活 13B。
  • DeepSeek-V3：总参数 671B、每 token 激活 37B。

MoE 降低的是每 token 的计算量，不是显存：全部专家权重都要加载。

5. 其他手段。

  • 量化：GPTQ 可在约 4 个 GPU 小时内把 175B 模型的权重量化到 3–4 bit，精度损失可忽略；AWQ 根据激活分布保护少量关键权重。
  • 推测解码：用小模型先起草多个 token，再由大模型一次并行验证，输出分布不变；论文在 T5-XXL 上报告 2–3 倍加速。
  • FlashAttention：Prefill 和长上下文场景的标准内核。

工程实践与数字

  • 显存 = 权重 + KV Cache + 激活。 70B 模型 FP16 权重约 140 GB（70B × 2 字节），再加上随并发数和上下文长度线性增长的 KV Cache。
  • 吞吐与延迟要权衡。 批越大，每次读权重服务的请求越多，吞吐越高，但单请求延迟上升。
  • 长提示复用：共享前缀（系统提示、RAG 文档）的 KV 块可以复用，PagedAttention 的块共享正是为此设计。
  • 框架选择：vLLM 等开源引擎已集成 PagedAttention、连续批处理、量化和推测解码，自建服务优先基于它们。

常见误区

  • 「MoE 模型 671B 只要按 37B 的显存部署。」 计算按激活参数算，显存仍要装下全部参数。
  • 「上下文越长成本只是线性增加。」 KV Cache 线性增长，但 Prefill 的注意力计算随长度平方增长。
  • 「量化一定掉点严重。」 4 bit 权重量化在大模型上通常损失很小，但应在自己的任务上评测。
