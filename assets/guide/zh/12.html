ReAct、Plan-and-Execute 与 Reflection：三种组织「思考与行动」的范式

对应图 #12 · 第二章「Agent 设计原理与范式」

同一个模型、同一套工具，换一种组织方式，Agent 的可靠性、成本和可解释性就可能完全不同。图 #12 并排画了三种最常用的范式：ReAct 是思考、行动、观察的小循环；Plan-and-Execute 先由规划器拆出步骤，再交给执行器逐个完成；Reflection 在做完之后评估结果，把反馈带进下一次尝试。三者不是互相替代，而是回答了三个不同的问题：下一步该做什么？整件事该怎么拆？做错了怎么改进？

为了看清它们的差别，下面用同一个任务贯穿全文：「修复 issue #123：用户上传超过 10 MB 的头像时服务返回 500。」

一、ReAct：走一步，看一步

机制。 Yao 等人 2022 年提出 ReAct，让 LLM 以交错的方式生成推理轨迹和具体动作。推理帮助模型归纳、跟踪和更新计划、处理异常；动作让模型与知识库或环境交互，拿到新的信息。循环长这样：

Thought → Action(tool, args) → Observation → Thought → … → Final Answer

放到我们的任务里：

  • Thought：500 说明服务端抛了异常，先看上传接口。
  • Action：grep -r "avatar" src/api/
  • Observation：找到 upload_avatar()，调用了 resize_image()。
  • Thought：可能是大图在缩放时内存溢出，先看日志确认。
  • Action：读取最近的错误日志。
  • Observation：PayloadTooLarge 未被捕获……

每一步的思考都建立在上一步的真实观察之上，这就是它的价值。

为什么有效？ 纯思维链只在模型自己的「脑子里」推理，一旦某个中间事实错了，后面会一路错下去。ReAct 在 HotpotQA 问答和 Fever 事实核查上，只是调用了一个简单的维基百科 API，就缓解了纯思维链推理中常见的幻觉和错误传播，而且生成的解题轨迹更容易被人理解。环境的观察不断把模型拉回现实。

代价。 轮次多，每一轮都要把越来越长的历史重新喂给模型；没有全局规划时，容易在局部绕圈，比如反复 grep 同一个关键词。今天主流的 Coding Agent 本质上仍是这个循环，只是模型更强、工具更多，并配上了上下文压缩和最大轮次限制。

二、Plan-and-Execute：先想清楚，再动手

机制。 Wang 等人 2023 年的 Plan-and-Solve 针对零样本思维链「漏步骤」的问题，让模型先制定计划，把任务拆成子任务，再按计划逐个执行；扩展版 PS+ 增加了更细的指令以减少计算错误。在 GPT-3 上的十个数据集实验中，它稳定优于 Zero-shot-CoT。工程上的 Plan-and-Execute 沿用这一思路：规划器（Planner）产出步骤列表，执行器（Executor）逐步完成，必要时回到规划器重新规划。

同一个任务，规划器可能先给出：

  1. 复现：用 11 MB 的图片调用上传接口。
  2. 定位异常来源并补上测试。
  3. 在网关和应用层统一大小限制，返回 413 而不是 500。
  4. 跑全部测试并提交。

执行器拿到的是边界清楚的小任务，每一步都可以用更便宜的模型，甚至可以并行（这就是第 5 篇编排者—工作者模式的雏形）。

优点。 全局结构清晰，人可以在执行前审阅计划；成本更可控；步骤之间的依赖一目了然。

代价。 计划是基于执行前的信息做的。如果第 2 步发现问题其实出在 CDN 配置，原计划的第 3 步就过时了。所以 Plan-and-Execute 必须支持重新规划，否则就会出现「严格执行一个错误计划」的情况。计划也并非越详细越好：环境越不确定，详细计划越容易失效。

三、Reflection：做完回头看，用语言当梯度

机制。 Shinn 等人 2023 年的 Reflexion 不更新模型权重，而是通过「语言反馈」来强化 Agent：每次尝试后，Agent 根据任务反馈信号写一段反思，存入情景记忆，下一次尝试时把这些反思放进上下文，据此改进决策。论文报告它在 HumanEval 编程基准上 pass@1 达到 91%，高于当时 GPT-4 的 80%。

放到我们的任务里：第一次修复后测试仍然失败，反思写道：「我只在应用层加了检查，但 nginx 的 client_max_body_size 先拒绝了请求，返回的是网关的错误页。下次先检查请求链路上每一层的限制。」第二次尝试带着这条经验，直接从网关配置查起。

相关的 Self-Refine 让同一个 LLM 依次担任生成者、反馈者和修改者，迭代优化输出，在 7 类任务上平均绝对提升约 20%。

关键前提：反馈信号要可靠。 Reflexion 在编程任务上效果好，很大程度上是因为测试结果提供了客观反馈：通过就是通过，失败会附带报错信息。如果没有外部信号，只让模型「自己检查一下」，自我评价可能并不可靠，甚至会强化原来的错误判断。图中写的「适合：有明确检验标准的任务」就是这个意思。

四、怎么选？怎么组合？

范式 适合的任务 主要代价 失败时的典型表现
ReAct 步骤不可预知、要边探索边决策 轮次多，易绕圈 在局部反复试探
Plan-and-Execute 结构清晰、可预先拆解的长任务 计划可能过时 坚持执行错误计划
Reflection 有明确检验标准、允许多次尝试 每轮额外调用 无信号时自我强化错误

实际系统几乎总是组合使用。一个典型的 Coding Agent：先用规划把 issue 拆成步骤（Plan-and-Execute），每一步内部用 ReAct 循环读代码、改代码、跑命令，测试失败时把报错和反思带入下一轮（Reflection），整个过程有最大轮次和预算上限。

这些范式也能对应到 Anthropic 的模式库：Plan-and-Execute 接近「编排者—工作者」；Reflection 接近「评估者—优化者」，后者在有清晰评价标准、迭代确实能带来可衡量提升时效果最好。

五、三个常见误解

  • 「ReAct 已经过时。」 主流 Coding Agent 的核心仍是「思考—调用工具—观察」的循环。
  • 「计划越详细越好。」 环境变化时详细计划容易失效，关键是能重新规划。
  • 「自我反思一定能改进。」 缺乏外部验证时，反思可能只是换一种说法重复错误。给反思接上测试、类型检查或真实运行结果，它才真正有效。
