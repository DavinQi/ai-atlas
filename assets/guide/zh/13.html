MCP 协议：M 个应用 × N 个工具，变成 M + N 个适配器

对应图 #13 · 第二章「Agent 设计原理与范式」

假设你的团队用三款 AI 工具：一个 IDE 插件、一个聊天客户端、一个内部的工单 Agent。它们都需要访问 GitHub、公司数据库和文件系统。没有统一标准时，每个应用都要为每个工具单独写一套集成：3 个应用 × 3 个工具 = 9 套代码，每套的认证、错误处理和数据格式都略有不同，而且每加一个工具，所有应用都要跟着改。这就是「M × N」的组合爆炸。

Model Context Protocol（MCP）是 Anthropic 于 2024 年 11 月发布的开放协议，目标正是解决这个问题：应用只需实现一次 MCP 客户端，工具只需实现一次 MCP 服务器，任意组合即可互通，9 套集成变成 3 + 3 = 6 个适配器。图 #13 从上到下画了它的结构：Host 里有 LLM 和多个 MCP Client，经 JSON-RPC 2.0 连接到各自的 Server，Server 暴露 Tools、Resources、Prompts 三类能力，底部是一次工具调用的三步流程。

一、设计参照：LSP 做过同样的事

MCP 规范明确说明它借鉴了 Language Server Protocol（LSP）。在 LSP 出现之前，每个编辑器要为每种编程语言单独实现补全、跳转和诊断；LSP 把「语言能力」抽成独立的服务器，编辑器只需实现一个客户端。结果是 VS Code、Vim、Emacs 等编辑器都能用上同一个 TypeScript 或 Rust 语言服务器。

MCP 想做的是 AI 时代的 LSP： 正如 LSP 统一了编程语言支持接入开发工具的方式，MCP 统一了上下文和工具接入 AI 应用的方式。理解了这个类比，后面的设计决策就都很自然了。

二、三种角色

协议在三种角色之间用 JSON-RPC 2.0 消息通信：

  • Host（宿主）：发起连接的 LLM 应用，比如 IDE 或聊天客户端。它掌握用户界面，也掌握最终的授权决定。
  • Client（客户端）：宿主内部的连接器。每个客户端对应一个服务器，一对一维持一条有状态的连接，便于隔离：一个服务器出问题，不影响其他连接。
  • Server（服务器）：提供上下文和能力的服务，可以是本地进程，也可以是远程服务。

注意 Host 和 LLM 的关系：模型本身并不「连接」任何服务器。模型只是在上下文里看到可用工具的描述，决定调用哪个；真正发起请求、执行、把结果放回上下文的，是 Host 和它的 Client。

三、服务器提供的三种能力：谁来决定用？

MCP 把服务器能提供的东西分成三类，区分标准很有意思：由谁来控制使用。

原语 是什么 由谁控制 例子
Tools 供模型执行的函数 模型决定调用（需用户授权） 创建 issue、执行查询
Resources 上下文和数据 应用或用户选择放入上下文 某个文件、某张表的结构
Prompts 模板化的消息和工作流 用户主动选用 「生成发布说明」模板

这个划分对应了三种不同的信任级别：Tools 有副作用，最需要把关；Resources 是只读数据；Prompts 是用户显式触发的快捷方式。

反过来，客户端也可以向服务器提供能力：Sampling 允许服务器请求宿主代为调用一次 LLM（服务器不必自带模型和 API 密钥）；Roots 让服务器询问自己可以操作哪些 URI 或文件系统边界；Elicitation 让服务器在需要时向用户请求补充信息。本文依据的是 2025-06-18 版规范，Elicitation 就是这一版新增的能力。

四、一次工具调用的完整旅程

以「帮我在 GitHub 上为这个 bug 开一个 issue」为例：

  1. 初始化与能力协商。 连接建立时，客户端和服务器交换各自支持的能力和协议版本。连接是有状态的，之后双方都知道对方能做什么。
  2. 发现工具。 客户端请求工具列表，服务器返回每个工具的名称、描述和参数的 JSON Schema。宿主把这些描述放进模型的上下文。
  3. 模型决定调用。 模型读到 create_issue 的描述，生成一个结构化的 tool_call，参数包括标题和正文。
  4. 用户授权，客户端执行。 宿主向用户确认后，客户端把调用请求发给 GitHub 服务器，服务器真正调用 GitHub API。
  5. 结果回到上下文。 服务器返回新 issue 的链接，宿主把结果放进上下文，模型据此回复用户。

如果服务器那边的工具列表变了（比如管理员开放了一个新工具），服务器可以主动发通知，客户端无需轮询。

五、两层架构与两种传输

MCP 分为两层。数据层定义基于 JSON-RPC 的协议本身：生命周期管理、能力协商和上述各种原语。传输层负责字节怎么送达，常见的有两种：

  • STDIO：宿主把服务器作为本地子进程启动，通过标准输入输出通信。简单、无需网络，通常只服务一个客户端，适合文件系统、本地 Git 这类工具。
  • Streamable HTTP：客户端用 HTTP POST 发送消息，服务器可选用 Server-Sent Events 流式返回。远程服务器通常同时服务多个客户端，适合公司内部的共享服务，便于接入统一认证。

两层分离的好处是：同一个服务器实现，换个传输方式就能从本地工具变成团队共享服务。

六、安全：规范自己说「协议无法强制」

MCP 让模型能访问任意数据、执行任意代码，所以安全是规范的核心部分。规范列出了几条原则：

  • 用户必须明确同意并理解所有数据访问和操作。
  • 宿主在把用户数据暴露给服务器前，必须获得明确同意。
  • 工具代表任意代码执行，必须谨慎对待；来自不受信服务器的工具描述（如注解）应视为不可信。
  • 调用任何工具前，宿主必须获得用户明确同意；用户必须批准任何 Sampling 请求。

最值得注意的是规范的坦白：协议本身无法强制执行这些原则，需要实现者在应用中构建同意与授权流程。工具描述会被放进模型的上下文，一个恶意服务器完全可以在描述里藏指令，这正是第 6 篇要讲的提示注入。

七、落地建议

  • 先只读，后写入。 内部系统先做查库、查日志、查文档这类只读服务器，验证价值后再逐步开放写操作，并对写操作加人工确认。
  • 工具描述就是提示词。 描述要具体：什么时候用、什么时候不用、参数的含义和约束、典型示例。描述质量直接影响模型能否选对工具。
  • 少而精。 工具描述会占用上下文，过多功能相近的工具会让模型选错。按任务场景只挂载需要的服务器。
  • 远程服务走统一认证。 用 Streamable HTTP 部署，接入公司的身份系统，并记录完整的调用日志。

八、三个常见误解

  • 「MCP 就是函数调用。」 函数调用是模型层的能力；MCP 是应用与服务之间的协议，还包括资源、提示、能力协商和通知。
  • 「接了 MCP 就安全了。」 规范明确说协议无法强制安全原则，授权和审计都要自己做。
  • 「工具越多越好。」 工具描述占用上下文，相似工具会互相干扰。
