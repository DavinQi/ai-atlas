未来形态：人定目标与验收，Agent 团队交付

对应图 #36 · 第六章「AI 改变研发流程」

先说明：本篇是趋势判断，不是已经实现的事实。图中描绘的未来形态是：人负责定义目标和验收标准，由 Agent 团队完成从需求澄清到发布归档的大部分交付工作，人只在关键节点介入。这一判断延伸自第四、五章的实践，并与阿里巴巴实践手册描述的演进路线一致；手册本身也坦言，其中不少方向「看得到趋势但尚未跑通」。

所以这一篇的重点不是描绘一幅美好的图景，而是回答：要走到那一步，中间还缺什么？

一、三个阶段

据阿里巴巴实践手册，人与 Agent 的协作大致按三个阶段演进：

  1. 完全辅助：人使用 Coding Agent 完成工作，主导权在人。这是今天大多数团队所处的位置。
  2. 云端自主：云端托管的 Agent 接收任务后，独立拉代码、跑环境、生成变更、等待 Review。已经有多个产品形态在这一阶段使用，比如第三章提到的 Copilot 云端编码 Agent。
  3. 多 Agent 协同：多个 Agent 按角色完成需求澄清、方案设计、编码、测试、发布和归档，人只在关键节点介入。

手册指出，这条路线实质上是在不断外移信任边界：从人，扩展到云端运行环境，再扩展到 Agent 团队、工具链、任务状态和跨系统授权。每外移一步，都要求更强的隔离、授权和可观测能力来支撑这份信任。

二、两条路线：嵌入旧流程，还是重新组织

手册区分了两条路线：

  • Workflow 化改造（当前主流）：把 AI 嵌入既有的研发流程，每个节点局部提效，但整体仍然沿着为人设计的流程运转。
  • Agentic 方向（更被看好）：Agent 能自主获得验证信号，并据此持续推进任务；流程仍然存在，但主要负责调度、权限、状态、审计和高风险检查，而不是规定 Agent 每一步怎么想。

手册用电气化作类比：早期工厂只是用电动机替换蒸汽机，保留了原有的传动轴和布局；真正的生产率跃升，发生在每台机器拥有独立的电机、生产流程被重新组织之后。

这个类比很贴切。蒸汽时代的工厂，所有机器都通过一根长长的传动轴连到一台中央蒸汽机，所以工厂布局必须围绕传动轴来安排。换成一台中央电动机，传动轴还在，布局也没变，收益有限。直到每台机器都有自己的小电机，传动轴被拆掉，工厂才能按照工序的逻辑重新布局。

对应到研发流程：今天的很多流程（需求评审会、分阶段的提测、按岗位划分的交接）是为「人力有限、沟通昂贵」而设计的。把 AI 塞进每一个环节，就像用电动机替换蒸汽机；真正的变化，可能需要重新设计流程本身。

三、实现前提：还缺什么

要让 Agent 团队可靠交付，至少需要四样东西。每一样都能对应到本书前面的某一章：

前提 含义 对应章节
可复现、可调用的研发环境 Agent 能独立构建、启动服务、准备数据、操作浏览器、查日志和指标 第四章分层验证、第五章 worktree
分层验证体系 秒级、分钟级的机器反馈，人只看机器判断不了的 第四章
Agent 身份、委托授权和全链路可观测 知道哪个 Agent 以谁的名义做了什么 第五章数字员工
被结构化的组织知识 知识能被 Agent 检索、理解和引用 第四章上下文工程

四、现实的约束

技术上。 Anthropic 指出，大多数编码任务可并行的部分有限，LLM Agent 还不擅长实时协调和委派。

落地上。 手册中的团队经历了一条从兴奋到务实的曲线，遇到的四个卡点是：环境搭不起来、上下文拼不全、验证跑不通、发布卡在流程上。 值得注意的是，这四个卡点没有一个是「模型不够聪明」。

手册还认为，从模型能力到企业研发效能的提升之间，存在三个 gap：Agent 基础设施、上下文、组织。模型的进步只能填补其中很小的一部分。

五、今天就能做的准备

未来形态尚未到来，但为它做准备的事情，今天就有价值，而且即使未来形态不来，它们本身也能提升效率：

  • 把内部系统翻译成 Agent 可调用的工具（MCP / CLI / Skill）。
  • 把验证做成秒级和分钟级的反馈。
  • 给 Agent 独立身份和最小权限。

手册提醒：要接受技术快速迭代带来的不确定性，同时避免因为「等更好的模型」而推迟必要的基础设施建设。

六、常见误区

  • 「未来就是无人化。」 手册中的团队明确表示，AI Native 不是追求无人化，而是重新划分系统、AI 与人的职责边界。
  • 「模型够强就自然实现。」 三个 gap 中，模型能力只是很小的一部分。
  • 「这是遥远的事。」 第二阶段（云端自主）已经有多个产品形态在使用。
