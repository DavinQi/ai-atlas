未来形态：人定目标与验收，Agent 团队交付

对应图 #36 · 第六章「AI 改变研发流程」

概述

本篇是趋势判断，不是已经实现的事实。图中描绘的未来形态是：人负责定义目标和验收标准，由 Agent 团队完成从需求澄清到发布归档的大部分交付工作，人只在关键节点介入。这一判断延伸自第四、五章的实践，并与阿里巴巴实践手册描述的演进路线一致；手册本身也坦言，其中不少方向「看得到趋势但尚未跑通」。

核心机制

1. 三阶段演进（据阿里巴巴实践手册）：

  • 完全辅助：人使用 Coding Agent 完成工作，主导权在人。
  • 云端自主：云端托管的 Agent 接收任务后，独立拉代码、跑环境、生成变更、等待 Review。
  • 多 Agent 协同：多个 Agent 按角色完成需求澄清、方案设计、编码、测试、发布和归档，人只在关键节点介入。

手册指出，这条路线实质是在不断外移信任边界：从人，扩展到云端运行环境，再扩展到 Agent 团队、工具链、任务状态和跨系统授权。

2. 从 Workflow 到 Agentic。 手册区分了两条路线：

  • Workflow 化改造（当前主流）：把 AI 嵌入既有研发流程，每个节点局部提效，但整体仍沿着为人设计的流程运转。
  • Agentic 方向（更被看好）：Agent 能自主获得验证信号并据此持续推进任务；流程仍然存在，但主要负责调度、权限、状态、审计和高风险检查，而不是规定 Agent 每一步怎么想。

手册用电气化作类比：早期工厂只是用电动机替换蒸汽机，保留原有的传动轴和布局；真正的生产率跃升发生在每台机器拥有独立电机、生产流程被重新组织之后。

3. 实现前提。 要让 Agent 团队可靠交付，至少需要：

  • 可复现、可调用的研发环境：Agent 能独立构建、启动服务、准备数据、操作浏览器、查日志和指标。
  • 分层验证体系。
  • Agent 身份、委托授权和全链路可观测。
  • 被结构化的组织知识。

工程实践与数字

  • 当前的现实约束：Anthropic 指出大多数编码任务可并行的部分有限，LLM Agent 还不擅长实时协调和委派；手册的团队经历了从兴奋到务实的曲线，四个卡点是环境搭不起来、上下文拼不全、验证跑不通、发布卡在流程上。
  • 今天就能做的准备：把内部系统翻译成 Agent 可调用的工具（MCP / CLI / Skill），把验证做成秒级和分钟级反馈，给 Agent 独立身份和最小权限。
  • 别等更好的模型：手册提醒，要接受技术快速迭代带来的不确定性，同时避免因为「等更好的模型」而推迟必要的基础设施建设。

常见误区

  • 「未来就是无人化。」 手册的团队明确表示 AI Native 不是追求无人化，而是重新划分系统、AI 与人的职责边界。
  • 「模型够强就自然实现。」 手册认为从模型能力到企业研发效能提升之间存在 Agent 基础设施、上下文、组织三个 gap。
  • 「这是遥远的事。」 第二阶段（云端自主）已经有多个产品形态在使用。
