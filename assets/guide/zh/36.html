AIOps 自修复闭环：低风险自动，高风险过人

对应图 #36 · 第六章「AI 改变研发流程」

把 Agent 接入运维流程后，可以形成一个自修复闭环：发现问题 → 收集证据 → 诊断 → 生成修复 → 验证 → 发布 → 观察。关键的设计不在于 Agent 能修多少，而在于按风险分级：低风险、可快速回滚的操作可以自动执行；高风险、不可逆的操作必须经过人。

一、跟着一次故障走一遍闭环

凌晨 2 点，某服务的错误率开始上升。

  1. 发现。 告警触发。在传统流程里，这里要先把值班工程师叫醒；在自修复闭环里，告警直接创建一个任务给诊断 Agent。
  2. 证据。 按第四章的排障证据链，Agent 先收集事实：取几个失败请求的 TraceId，沿链路查日志和上下游状态，对照代码位置和最近的变更。它发现：所有失败都发生在一个新上线的配置项被读取之后，该配置项的值格式错误。
  3. 诊断。 证据清晰，属于「明显错误」，诊断 Agent 直接定位。如果证据不足或互相矛盾，就升级给拥有完整代码上下文的 Agent 或人。
  4. 修复。 有两个选项：把配置回滚到上一版本（低风险），或者修改解析代码以兼容新格式（中风险）。Agent 先执行前者止血，同时为后者生成补丁，并补一条能复现问题的回归测试。
  5. 验证。 补丁经过分层验证：编译、单测、集成测试。
  6. 发布与观察。 配置回滚后，错误率恢复正常。代码补丁不在凌晨自动上线，而是生成一个待批准的变更，早上由人一键批准后渐进发布。

早上 9 点，工程师看到的是一份结构化报告：现象、证据、根因、已执行的止血操作、待批准的修复。人没有被叫醒，但关键的决定仍然由人做。

二、风险分级：闭环的核心

上面例子里最关键的一步，是第 4 步对「回滚配置」和「改代码」的区别对待。这背后是一套风险分级：

风险 示例 处理方式
低 重启无状态实例、扩容、回滚到上一版本 自动执行并通知
中 配置修改、小范围代码修复 自动生成，人一键批准
高 数据库迁移、权限变更、资金相关 必须由人决策

分级的依据有两个维度：可逆性（出错了能否快速恢复）和影响面（出错了会影响多少用户、多少数据）。回滚到上一版本是「回到一个已知的好状态」，可逆、风险低；数据库迁移可能不可逆，影响全部数据。

这与安全领域的规范一致。OWASP 的缓解建议明确要求：对特权操作实施人在回路控制，高风险操作须人工批准；为应用提供独立的令牌并实行最小权限。MCP 规范也要求调用工具前获得用户的明确同意。

三、渐进式发布：让修复也接受检验

Agent 生成的修复，即使通过了所有测试，也可能在生产环境中出问题：测试环境的数据和流量永远不完全等同于生产环境。所以修复也要灰度、观察、再扩大。

Anthropic 在其多 Agent 系统中使用「彩虹部署」：新旧版本同时运行，逐步把流量从旧版本切到新版本，避免更新打断正在运行的 Agent。同样的思路适用于 Agent 生成的修复。

四、人工节点会吞掉自动化收益

第四章提过手册里的一个「反常数据」：自动修复 bug 的比例达到 60% 以上，但 bug 日清率只从 53% 提升到最高 63%，原因是触发依赖人、校验依赖人。

对照上面的闭环，就能看清问题在哪里：如果第 1 步要等人发现问题并手动创建任务，第 5 步要等人逐个检查修复，那么无论第 2–4 步多快，整体吞吐都上不去。闭环要真正打通，必须让触发和低风险的校验也自动化，只把真正需要判断的部分留给人。

五、最后一公里的难度

手册也很清醒地指出：构建、集成测试、灰度发布、生产验证、故障恢复涉及真实环境、真实数据和真实用户，容错空间极小，对 Sandbox 隔离、凭证管理、Guardrail 和可观测能力的要求，远超当前水平。

所以，建立信任要循序渐进：

  • 先给只读权限，在诊断环节建立信任。Agent 的诊断报告准确率如何？人可以先「旁观」一段时间。
  • 再逐步开放低风险写操作，例如重启、扩容、回滚。
  • 所有自动操作留痕：谁（哪个 Agent）、代表谁、基于什么任务、做了什么（第五章「数字员工」）。

六、常见误区

  • 「自修复就是全自动。」 风险分级和人工关卡是自修复系统的核心组成部分。
  • 「修复后测试通过就可以全量发布。」 生产环境的验证需要渐进式发布和观察。
  • 「Agent 出错率高，所以不能用在运维。」 关键是限定作用范围，让错误可回滚、可审计。人也会出错，运维体系本来就是为「会出错」而设计的。
