记忆与 RAG：在对的时候，把对的内容放进上下文

对应图 #14 · 第二章「Agent 设计原理与范式」

模型部署后权重是固定的，上下文窗口又是有限的。Agent 要用上私有知识、最新信息和长期经验，就必须反复解决同一个问题：此刻该把哪些内容放进上下文？ 放少了，模型只能凭记忆猜；放多了，成本上升、注意力被稀释，关键信息反而被淹没。

图 #14 分成两半：上半部分是四类记忆（上下文窗口、会话摘要、向量库与文档、规则文件），下半部分是 RAG 的两条流水线（离线建索引、在线查询）。底部一句话把它们串起来：参数记忆在权重里，非参数记忆在检索索引里。这篇文章先讲清楚为什么需要分层记忆，再把 RAG 的每一步拆开，看质量损失通常发生在哪里。

一、四类记忆：像计算机的存储层级

把 Agent 的记忆类比为计算机的存储层级，最容易理解：

记忆 类比 容量 访问方式 例子
上下文窗口（工作记忆） 寄存器 / 内存 小，按 token 计费 模型直接看到 当前对话、刚读的文件
会话摘要（短期记忆） 缓存 中 压缩后放回上下文 前 50 轮对话的要点
向量库 · 文档（长期记忆） 磁盘 大 检索后放回上下文 产品文档、历史工单
规则文件（程序性记忆） 配置 小而稳定 每次会话开头加载 AGENTS.md、编码规范

MemGPT 把这个类比做成了真正的系统：借鉴操作系统的分层内存管理，让 Agent 自己在快慢存储之间移动数据，在有限的上下文窗口里获得「更大内存」的效果，用于分析远超窗口的长文档和长期多轮对话。Generative Agents 则用自然语言保存完整的经历记录，随时间合成为更高层次的反思，在规划时按相关性、时间远近和重要程度检索。

核心洞察： 上下文窗口是唯一能被模型「看见」的地方，其他所有记忆都只是候选。记忆系统的本质，是一套决定「何时把什么调入上下文」的策略。

二、RAG：把开卷考试的书带进考场

基本思想。 Lewis 等人 2020 年提出检索增强生成（RAG）：把预训练的参数化记忆（模型权重）与非参数化记忆（可检索的文档索引）结合起来生成答案。论文指出，这样做有助于提供答案来源，也便于更新知识：改文档就行，不用重训模型。

离线流水线：文档 → 切块 → Embedding → 向量库。

  1. 切块。 文档被切成几百个 token 左右的片段。切得太大，一块里混着多个主题，检索不准，也浪费上下文；切得太小，丢失上下文（一个表格被拆成几块，表头和数据分家）。按标题、段落等语义边界切，并保留少量重叠，通常比按固定长度硬切效果好。
  2. 向量化。 用嵌入模型把每个片段变成一个向量，语义相近的片段向量也相近。
  3. 建索引。 存入向量库，同时附上元数据（来源、时间、权限、产品线），后面可以先过滤再检索。

在线流水线：查询 → 检索 top-k → 重排 → 拼入 Prompt → LLM。

  1. 检索。 把用户问题也向量化，找出最相近的 k 个片段。纯向量检索擅长语义相近，但对精确的名字、版本号、错误码不敏感，所以实践中常和关键词检索（BM25）混合使用。
  2. 重排（可选，但通常值得）。 用一个更精细的模型对候选重新打分，把真正相关的放到前面。
  3. 拼入提示。 把片段连同来源一起放进上下文，并要求模型基于这些资料作答、注明出处、资料不足时说明。

质量损失通常发生在哪？ 不在生成，而在检索。模型拿到的是错的或不全的资料，再强也答不好。Gao 等人的综述把 RAG 的演进分为三代：Naive RAG（检索—生成直连）、Advanced RAG（在检索前后加入查询改写、重排等优化）和 Modular RAG（可组合的模块化流水线）。切块粒度、元数据过滤和重排，往往比换一个更大的模型更有效。

全局问题怎么办？ 「这批文档的主要主题是什么」这类问题，答案分散在所有文档里，普通检索取回的几个片段无法回答。微软的 GraphRAG 先用 LLM 从文档中抽取实体与关系，构建知识图谱，再为相关实体群预生成社区摘要，回答时汇总各社区的部分答案。

三、长上下文能取代 RAG 吗？

上下文窗口越来越长，一个自然的想法是：把所有资料都塞进去，不就不用检索了？研究给出了否定的答案。

中间的信息容易被忽略。 Liu 等人的「Lost in the Middle」研究发现，相关信息位于输入开头或结尾时表现最好，位于长上下文中间时显著下降，即使是专门的长上下文模型也如此。

上下文越多，回忆越弱。 Anthropic 提到 needle-in-a-haystack 类评测揭示的「context rot」现象：上下文中的 token 越多，模型准确回忆其中信息的能力越弱。他们把上下文比作有限的注意力预算，边际收益递减。

成本随长度上升。 第一章讲过，Prefill 的注意力计算随长度平方增长，KV Cache 线性增长。

所以 Anthropic 把这个问题概括为上下文工程：找到最小的高信号 token 集合，最大化得到期望结果的可能性。

四、Agent 时代的新做法：即时上下文

传统 RAG 是「先检索好，再一次性塞进去」。Anthropic 观察到，越来越多的 Agent 改用即时（just-in-time）上下文：只保存轻量的标识（文件路径、查询语句、链接），运行时用工具按需加载。Coding Agent 用 grep、glob 浏览代码库就是典型：它不需要预先把整个仓库向量化，而是像人一样，先看目录，再搜关键词，再打开相关文件。

对于跨越几小时的长任务，他们总结了三种技术：

  • 压缩（compaction）：对话接近窗口上限时做摘要，用摘要开一个新窗口继续。
  • 结构化笔记：Agent 把进度、待办和关键决定写进上下文之外的文件，之后需要时再读回来。
  • 多 Agent 架构：子 Agent 在各自的上下文里探索，只把精华返回给主 Agent（下一篇）。

五、常见误解

  • 「上下文窗口够大就不需要 RAG。」 长上下文会出现中段信息利用率下降和 context rot，成本也随长度上升。
  • 「RAG 能消除幻觉。」 它降低了无依据生成的概率，但检索错误或文档本身有误时仍会出错。要求注明出处，并在资料不足时允许回答「不知道」。
  • 「记忆就是向量库。」 记忆还包括摘要、结构化笔记和规则文件。选择什么、何时放入上下文才是关键。
  • 「把关键内容随便放。」 利用「Lost in the Middle」的规律，把最重要的指令和资料放在开头或结尾。
