上下文工程：0→1 靠生成能力，1→N 靠上下文

对应图 #23 · 第四章「当前如何做 AI 编程」

概述

在新项目里，AI 生成代码的速度令人惊艳；但到了已有代码库，问题就从「会不会写」变成「看不看得懂」。阿里巴巴实践手册把这总结为：0→1 靠生成能力，1→N 靠上下文工程。 Anthropic 的定义是：上下文工程是在 LLM 推理时，策划和维护最优 token 集合的一系列策略；由于注意力预算有限，好的上下文工程就是找到最小的高信号 token 集合，最大化得到期望结果的可能性。

核心机制

1. 为什么上下文有限。 Anthropic 指出 needle-in-a-haystack 类评测揭示了「context rot」：上下文中的 token 越多，模型准确回忆信息的能力越弱，因此上下文是边际收益递减的有限资源。「Lost in the Middle」研究也发现，信息位于长上下文中间时，模型的利用效果显著下降。

2. 上下文的组成。 对 Coding Agent 而言，上下文通常包括：

  • 项目地图：架构、模块职责、代码入口
  • 规则：技术栈约束、编码规范、禁止事项（CLAUDE.md、AGENTS.md、.cursor/rules）
  • 需求：Spec、验收标准
  • 工具：Skill、MCP、CLI
  • 运行事实：日志、测试结果、数据库状态

3. 「即时」加载。 与其预先塞满上下文，不如只保留轻量标识（文件路径、查询、链接），运行时用工具按需加载。Claude Code 用 glob、grep 浏览代码库就是例子。

4. 长任务管理。 压缩（对接近上限的对话做摘要后开启新窗口）、结构化笔记（把进度写到上下文之外）、子 Agent（各自探索，只返回精华）。

工程实践与数字

千问用增 Agent 的三阶段经历（阿里巴巴实践手册）：

  • 第一阶段：约 15 名服务端工程师各自探索 AI Coding，部分场景下代码生成速度可达传统方式的数倍甚至约 10 倍。
  • 第二阶段：0 到 1 建设完成后，单纯依赖代码生成的边际收益下降；真正的难题变成让 AI 在已有代码库中准确理解项目结构、业务需求和工程约束。
  • 第三阶段：工程建设重点转向组织上下文、明确边界和建立验证机制。

团队用三类资产解决「AI 如何理解项目」：代码文档说明「为什么这样设计」，代码图谱精确查询定义、调用关系和影响范围，Rules 把团队经验固化为可执行约束。

手册把上下文视为组织资产：Skill、MCP、Spec、README / runbook、模板与 checklist。如果不沉淀这些资产，团队就会停留在「每个人临时问 AI」的阶段。

实用建议：

  • 规则文件提交到 Git，新的 worktree 才能读到（X 上分享 Orca 用法的开发者特别提醒了这一点）。
  • 规则不要一次写几十条，Agent 在同一件事上反复犯错时再补一条。
  • 一个流程重复超过三次，就可以整理成 Skill 复用。

常见误区

  • 「上下文越多越好。」 context rot 说明多余的 token 会稀释注意力。
  • 「换更强的模型就能解决看不懂老代码。」 手册的经验是，持续建设高质量上下文、明确约束和可验证反馈，往往比单纯追求更强模型更能提升输出稳定性。
  • 「规则写一次就完事。」 上下文资产需要持续更新和验证。
