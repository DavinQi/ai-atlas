上下文工程：0→1 靠生成能力，1→N 靠上下文

对应图 #23 · 第四章「当前如何做 AI 编程」

在新项目里，AI 生成代码的速度令人惊艳；到了已有代码库，问题就从「会不会写」变成「看不看得懂」。阿里巴巴实践手册把这总结为：0→1 靠生成能力，1→N 靠上下文工程。

一、一个让人困惑的现象

想象两个任务，交给同一个模型：

  • 任务 A：「用 FastAPI 写一个待办事项的增删改查服务。」
  • 任务 B：「在我们的订单系统里，给退款接口加一个『部分退款』功能。」

任务 A 模型几乎一次就能写对，因为网上有成千上万个类似的例子，它要的知识都在训练数据里。任务 B 往往一塌糊涂：它不知道你们的订单状态机长什么样，不知道退款要走哪个内部服务，不知道金额字段用的是分还是元，也不知道上次有人改这里引发过一次资损事故。

这些知识不在模型的权重里，只在你们的代码库、文档和人的脑子里。 模型唯一能用到它们的途径，是被放进上下文。这就是上下文工程要解决的问题。

二、定义：在有限的注意力里放最有用的东西

Anthropic 的定义是：上下文工程是在 LLM 推理时，策划和维护最优 token 集合的一系列策略；由于注意力预算有限，好的上下文工程就是找到最小的高信号 token 集合，最大化得到期望结果的可能性。

注意「最小」二字。直觉上，既然模型缺信息，那就把整个代码库都塞进去？行不通，原因有二：

  • context rot（上下文腐化）。 Anthropic 指出，needle-in-a-haystack 类评测揭示了：上下文中的 token 越多，模型准确回忆信息的能力越弱。上下文是一种边际收益递减的有限资源。
  • Lost in the Middle。 2023 年的研究发现，关键信息位于长上下文的中间时，模型的利用效果显著下降，明显不如放在开头或结尾。

所以问题不是「给多少」，而是「给什么、什么时候给」。

三、上下文由什么组成？

对 Coding Agent 而言，上下文通常包括五类：

类别 内容 典型载体
项目地图 架构、模块职责、代码入口 架构文档、README
规则 技术栈约束、编码规范、禁止事项 CLAUDE.md、AGENTS.md、.cursor/rules
需求 目标、范围、验收标准 Spec（下一篇）
工具 能做什么、怎么调用 Skill、MCP、CLI
运行事实 日志、测试结果、数据库状态 测试输出、Trace、只读查询

回到任务 B：状态机和退款服务属于「项目地图」，「金额用分」属于「规则」，「部分退款的边界条件」属于「需求」，查订单数据的能力属于「工具」，上次事故的日志属于「运行事实」。少了任何一类，模型都只能猜。

四、三种关键技巧

1. 即时加载，而不是预先塞满。 与其一开始就把所有文件放进去，不如只保留轻量的标识（文件路径、查询语句、链接），运行时再用工具按需加载。Claude Code 用 glob、grep 浏览代码库就是例子：它需要退款逻辑时，才去搜索、打开对应文件。这和人的工作方式一样：你不会把整个代码库背下来，而是知道去哪里找。

2. 长任务的三种续航方式。

  • 压缩：对话接近上限时做摘要，带着摘要开启新窗口。
  • 结构化笔记：把进度、决策和待办写到上下文之外的文件里，需要时再读回来。
  • 子 Agent：各自探索，只把精华返回主会话（第三章第 4 篇）。

3. 把隐性知识变成显性资产。 手册中的团队用三类资产解决「AI 如何理解项目」：代码文档说明「为什么这样设计」；代码图谱精确查询定义、调用关系和影响范围；Rules 把团队经验固化为可执行的约束。手册还把上下文视为组织资产：Skill、MCP、Spec、README / runbook、模板与 checklist。如果不沉淀这些资产，团队就会停留在「每个人临时问 AI」的阶段，每次都从零开始解释。

五、一线案例：千问用增 Agent 的三个阶段

阿里巴巴实践手册记录了一个团队的经历，很典型：

  • 第一阶段：约 15 名服务端工程师各自探索 AI Coding，部分场景下代码生成速度可达传统方式的数倍，甚至约 10 倍。
  • 第二阶段：0 到 1 建设完成后，单纯依赖代码生成的边际收益下降；真正的难题变成让 AI 在已有代码库中准确理解项目结构、业务需求和工程约束。
  • 第三阶段：工程建设的重点转向组织上下文、明确边界和建立验证机制。

从任务 A 走到任务 B，几乎每个团队都会经历这个转折。

六、实用建议

  • 规则文件提交到 Git。 只在本地的规则，新的 worktree 读不到（X 上分享 Orca 用法的开发者特别提醒了这一点）。
  • 规则逐条补，不要一次写几十条。 Agent 在同一件事上反复犯错时再补一条。规则写得太多，本身就会稀释注意力。
  • 三次原则。 一个流程重复超过三次，就可以整理成 Skill 复用。
  • 写「为什么」，不只写「是什么」。 「金额字段用分」不如「金额字段用分，因为浮点误差曾导致对账失败」：模型知道原因，才能在没写到的情况下做出正确判断。

七、常见误区

  • 「上下文越多越好。」 context rot 说明多余的 token 会稀释注意力。
  • 「换更强的模型就能看懂老代码。」 手册的经验是，持续建设高质量上下文、明确约束和可验证反馈，往往比单纯追求更强模型更能提升输出稳定性。更强的模型也不知道你们公司的状态机。
  • 「规则写一次就完事。」 上下文资产需要随代码持续更新和验证，过时的文档比没有文档更危险。
