两种打法：赛跑挑最优，流水线分工协作

对应图 #31 · 第五章「多 Agent 编程」

概述

多 Agent 编程有两种基本打法：

  • 赛跑（race）：同一个任务交给多个 Agent 同时做，挑最好的结果。
  • 流水线（pipeline）：一个任务拆成不同阶段或不同部分，由不同 Agent 分工完成。

两者分别对应 Anthropic 模式库中「并行化」的两种变体：投票（voting）——同一任务多次运行以获得多样化输出；分段（sectioning）——把任务拆成独立子任务并行运行。

核心机制

1. 赛跑：用多样性降低风险。 Orca 官方文档把「让三个 Agent 同时修同一个 bug，挑出赢家」列为典型用法。X 上分享 Orca 用法的开发者转述了官方对这一打法的解释：不同的 Agent 犯不同的错。三个都改成一样的地方，大概率是对的；三个各改各的地方，就是这个问题真正难的部分。等于花一份等待时间，拿到三份答案和一张「哪里有分歧」的地图。

学术上也有对应的证据：Codex 论文发现，对同一问题重复采样是获得正确解的有效策略（单次采样解决 28.8%，每题 100 次采样时为 70.2%）；多 Agent 辩论研究表明，多个模型实例提出并辩论各自答案，可以提升推理能力和事实准确性。

2. 流水线：用分工处理复杂任务。 MetaGPT 把标准作业流程（SOP）编码进提示序列，采用流水线范式为不同 Agent 分配角色，把复杂任务拆成多个 Agent 协作的子任务，并让具备领域专长的 Agent 校验中间结果以减少错误。一个常见的编码流水线：

需求澄清 → 方案设计 → 编码 → 测试 → 交叉审查 → 集成

  • 赛跑只用在关键处：前述开发者的建议是，只在支付、权限、数据迁移这类改错了很麻烦的地方赛跑，改文案就别这么干。
  • 赛跑不会自动合并：三份结果各对一半时，可以让获胜的 Agent 参考另一份改动再改一轮，或手动挑选好的部分。
  • 流水线的交接靠文件：Spec、CONTEXT.md、测试结果等共享产物，让下游 Agent 不必重读上游的全部对话。
  • 交叉审查：另一位开发者的做法是编码 Agent 完成后，引入其他厂商的 Agent 做对抗性审查，问题统一反馈给主编码 Agent 修复并重新验证。

常见误区

  • 「赛跑越多越好。」 收益递减，而成本线性增长，审阅负担也成倍增加。
  • 「流水线角色分得越细越好。」 每次交接都可能丢失信息，Anthropic 也提醒多 Agent 间依赖多的任务目前不适合。
  • 「三个 Agent 结果一致就一定对。」 一致性提高了可信度，但仍需测试验证。
