从补全到 AI IDE：模型先进了光标，再进了编辑器

对应图 #19 · 第三章「编程的进化」

AI 进入开发工具分了两步。第一步是光标处的补全：根据当前文件和光标位置，预测接下来的一行或一段代码。第二步是AI IDE：模型不再只盯着光标，而是可以理解整个项目、跨文件修改、在对话中解释和重构代码。两者有一个共同点：人仍然在编辑器里主导每一次修改，AI 是「副驾驶」。

这一篇不按时间顺序复述，而是围绕三个问题展开：补全模型到底在做什么？从补全到 AI IDE，多出来的能力是什么？它真的让人更快了吗？

问题一：补全模型在做什么？

补全本质上就是第一章讲的「下一个 token 预测」，只是语料换成了代码。 OpenAI 2021 年的 Codex 论文介绍了在 GitHub 公开代码上微调的 GPT 模型，并说明其生产版本驱动 GitHub Copilot。论文同时发布了 HumanEval 基准：164 道手写的编程题，每道题给出函数签名和文档字符串，模型生成函数体，再用单元测试判断是否正确。

看一个具体的样子。编辑器把光标前的内容作为提示交给模型：

def is_palindrome(s: str) -> bool:
    """判断字符串在忽略大小写和非字母数字字符后是否是回文。"""

模型续写出函数体。签名、类型标注、文档字符串，甚至变量命名，都是给模型的线索。写得清楚的注释和命名，本身就是提示词。 这也是为什么同一个补全工具，在规范的代码库里表现明显更好。

为什么补全工具常常给多个候选？ Codex 论文有个重要发现：单次采样时，模型能解决 28.8% 的 HumanEval 问题；每题采样 100 次、只要有一个通过测试就算解决，比例升到 70.2%。也就是说，正确答案常常「在」模型的分布里，只是不一定是第一个被采出来的。 补全工具提供多个候选、让人挑，利用的正是这一点；而后来的 Agent 用测试自动挑选，则把「人挑」换成了「机器挑」。

还有一个容易被忽略的细节：补全的上下文远不止当前文件。 现实的补全系统会把光标前后的代码、打开的其他标签页、相邻文件中的相关片段一起放进提示。这在第一章讲过：模型只知道放进上下文里的东西，所以「选什么进上下文」是补全质量的关键工程问题。

2021 年 6 月 29 日，GitHub 发布 Copilot 技术预览版，官方称首批对 Python、JavaScript、TypeScript、Ruby 和 Go 效果尤其好。这些恰好是公开代码量很大的语言，与「模型能力来自训练数据」相吻合。

问题二：AI IDE 多了什么？

补全回答的是「接下来写什么」；AI IDE 回答的是「这件事要怎么改」。它在补全之外加入了三件事：

  1. 对话：针对选中的代码或整个项目提问、解释、生成。可以问「这个函数为什么在空列表时会抛异常？」，而不只是让它续写。
  2. 多文件编辑：一次修改可以涉及多个文件，以 diff 的形式呈现给人审阅。比如给一个接口加字段，需要同时改数据模型、序列化、接口文档和测试。
  3. 项目级上下文：索引代码库，按需检索相关文件。模型改接口时能找到所有调用方。

从补全到 AI IDE，人审阅的单位从「一行」变成了「一个 diff」。这是一个值得注意的变化：一行代码对不对，人扫一眼就知道；一个跨五个文件的 diff 对不对，需要真的读懂。审阅成本上升了，这也预示了下一代工具必须引入自动验证。

规则文件让模型持续遵守团队约定。 模型每次会话都从零开始，不会记得上周你纠正过它「本项目用 pnpm 而不是 npm」。解决办法是把约定写进仓库里的文件，每次自动加载。Cursor 文档说明：规则在提示层提供持久、可复用的上下文；项目规则存放在 .cursor/rules 中，纳入版本控制；也支持 AGENTS.md 作为更简单的替代。AGENTS.md 被定位为「给 Agent 看的 README」，官网称已有超过 6 万个开源项目使用；Claude Code 则读取 CLAUDE.md。

一份好的规则文件通常写的是：技术栈与版本、构建和测试命令、代码风格中「模型容易弄错」的部分、禁止做的事。规则不是越多越好：它们占用上下文，写太多反而稀释重点。比较好的做法是：模型在某件事上反复犯错，就补一条。

边界正在模糊。 GitHub Copilot 的文档如今已经覆盖 IDE 中的 agent 模式、CLI，以及在云端异步工作、可以直接开启或更新 PR 供人审阅的编码 Agent。「补全工具」和「Agent 工具」已经越来越像同一个产品的不同模式。

问题三：它真的让人更快了吗？

这是最容易被感觉误导的问题。两项严谨的随机对照实验给出了看起来相反的结论：

实验 A：快了 55.8%。 2023 年的一项 Copilot 随机对照实验，让开发者用 JavaScript 实现一个 HTTP 服务器。使用 Copilot 的一组比对照组快 55.8%。

实验 B：慢了 19%。 METR 2025 年的随机对照试验，招募了 16 位经验丰富的开源开发者，在他们自己长期维护的成熟项目里完成 246 个真实任务。每个任务随机分配为「允许使用 AI」（主要是 Cursor Pro 和 Claude 3.5/3.7 Sonnet）或「不允许」。结果是，允许使用 AI 时完成时间增加了 19%。更有意思的是：开发者事前预计会缩短 24%，事后仍然认为缩短了 20%。

两项研究并不矛盾，差别在场景：

实验 A 实验 B
任务 边界清晰的新建任务 真实项目中的维护任务
代码库 从零开始 开发者非常熟悉的大型代码库
质量标准 通过测试即可 符合项目长期的隐性标准

在从零开始、边界清晰的任务上，模型的「平均水平代码」正好够用；在一个开发者烂熟于心、有大量隐性约定的大型项目里，理解、提示、等待、审阅和修正 AI 输出的时间，可能超过自己直接写的时间。收益高度依赖任务类型、代码库熟悉度和质量标准。

更重要的教训是：主观感受不可靠。 实验 B 中的开发者在实际变慢的情况下，仍然觉得自己变快了。评估 AI 工具的效果，必须看客观的交付指标，而不是问卷（见第四章「度量」）。

实践要点

  • 把 AI 生成的 diff 当作同事的 PR 来审，不要直接接受。
  • 规则文件提交到 Git，团队共享、可审查、随代码演进。
  • 给模型好的线索：清楚的命名、类型和注释，就是最便宜的提示工程。
  • 在你自己的场景里测，不要直接套用别人的「提速百分比」。
