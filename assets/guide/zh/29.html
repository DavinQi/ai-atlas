用 AI Agent 维护代码：小步、可验证、留痕的七步循环

对应图 #29 · 第四章「当前如何做 AI 编程」

上一张图讲的是“这一周把地基打好”。这一篇往下走一步：地基有了以后，每天维护一个真实的代码仓库时，具体怎么和 Agent 配合。它写给两类人：刚开始用 Claude Code、Codex、Cursor 或 Copilot 的新手，以及已经在用、但总觉得“时灵时不灵”的中高级工程师。

先说结论：会用 Agent 的人和不会用的人，差别不在于背了多少命令，而在于有没有一个闭环。Anthropic 官方的最佳实践把它放在第一条：给 Agent 一个它自己能运行的检查（测试、构建、截图对比），这决定了一次会话是你盯着看，还是你可以走开。Karpathy 在 2026 年初那篇被广泛转发的笔记里说得更直接：不要告诉它怎么做，给它成功标准，然后看它跑；让它先写测试，再让测试通过。下面的七步，就是围绕这个闭环展开的。

一、七步循环

步骤 0：项目地图。 在仓库根目录放一份给 Agent 看的说明：AGENTS.md（Codex、Cursor、Copilot 都会读）或 CLAUDE.md（Claude Code；新版在没有 CLAUDE.md 时也会读 AGENTS.md）。不用从零写，Claude Code 和 Codex 都有 /init，会扫一遍仓库生成初稿。你要做的是删减和补充：怎么装依赖、怎么跑测试、目录约定、哪些地方不能碰。

这份文件越短越好。官方文档专门列了一个失败模式叫“过度详细的 CLAUDE.md”：写得太长，重要的规则反而被淹没。判断标准很简单——如果删掉某一行，Agent 也不会犯错，那这一行就该删。Claude Code 的作者 Boris Cherny 分享过团队的做法：每次纠正 Agent 之后，补一句“更新 CLAUDE.md，别再犯这个错”，并持续修剪，直到错误率明显下降。这样它是“从错误里长出来”的，而不是一次写成的规章。

步骤 1：只读探索。 接手一段陌生代码，第一件事不是让它改，而是让它讲。可以直接问：“登录流程从哪里进来、经过哪些文件？”“这个函数被谁调用？”“为什么这里要加锁？”这些问题在新人带教里本来要找资深同事问，现在可以先问 Agent，再用自己的眼睛核对它给出的文件和行号。

步骤 2：先出计划。 只要改动跨多个文件、你不确定方案、或者你不熟悉这块代码，就先进入 Plan 模式。Claude Code 和 Cursor 都是在输入框里按 Shift+Tab 切换；Plan 模式下 Agent 只读不写，最后给出一份计划。好的计划要回答三件事：改哪些文件、按什么顺序、怎么证明改对了。反过来，如果你能用一句话描述整个 diff（改个拼写、加一行日志），就跳过计划直接做——官方文档也明确说，计划是有开销的。

Claude Code 团队的经验是：在计划上多花力气，让实现一次到位；实现中途一旦跑偏，不要硬推，立刻切回 Plan 模式重新规划。还有人会开第二个会话，让它以“资深工程师”的身份审这份计划。

步骤 3：小步实现。 让 Agent 一次只做一件事。原因不是 Agent 做不了大事，而是你审不了大 diff。一个 50 行的 diff 你能逐行读完，一个 2000 行的 diff 你只会点“接受”。Karpathy 观察到的典型错误恰恰在这种地方：替你做了错误的假设然后一路跑下去、把代码写得过度复杂、顺手改掉它没看懂的注释和代码。小步走，这些问题在每一步都会暴露出来。

步骤 4：跑检查。 这是闭环的核心，图上用橙色标出。把“跑测试、跑构建、跑 lint”直接写进任务里，让 Agent 自己读结果、自己修，直到通过。并且要它拿出证据：贴出跑了什么命令、输出是什么，而不是一句“已完成”。看证据比你自己重跑一遍快得多。

步骤 5：审 diff。 机器的关过了，才轮到人。你读的重点不是语法，而是：有没有改动任务以外的东西、有没有删掉不该删的、有没有更简单的写法。Boris 团队的常用招式是让 Agent 反过来考你：“把这些改动给我讲清楚，我答不上来就不许开 PR”；或者在一次平庸的修复之后说：“以你现在知道的一切，推倒重来，写一个优雅的版本。”另一种做法是开一个干净的会话或子 Agent 专门挑错——写代码的和评判代码的不要是同一个上下文。

步骤 6：提交 / PR。 让 Agent 写清楚提交信息并开 PR，然后让 CI 再把一道关。Anthropic 内部每个 PR 的第一轮评审由 Claude 完成，方式是在 GitHub Action 里跑无交互的 claude -p；Codex 对应的是 codex exec。人看到 PR 的时候，低级问题已经被筛过一轮。

二、四个常见场景怎么套用

修 Bug。 先让它写一个能复现问题的测试，确认这个测试是失败的，再去修，直到通过。这一步“先失败”非常关键：一个从来没失败过的测试，证明不了任何事。日志、报错栈、CI 失败输出直接贴进去，比你自己转述准确得多。Boris 团队甚至只说一句“去把失败的 CI 修好”，不规定怎么修。

重构。 先补测试把现有行为锁住，再分批改。每一批都单独跑测试、单独提交，出问题可以精确回退。重构时要特别提醒 Agent“行为不变”，并在审 diff 时盯住它有没有顺手“优化”了业务逻辑。

依赖升级。 让它先读目标版本的变更日志，列出可能受影响的调用点，然后一次只升一个依赖，每升一个跑一次全量测试。把多个大版本升级捆在一个 PR 里，是最难审、也最难回退的做法。

补文档。 让 Agent 读代码起草 README、接口说明或架构说明，人负责核对事实。Agent 写文档很快，但它也会把“看起来合理”的东西写成事实，所以凡是涉及版本号、命令、默认值的地方都要实际跑一遍。

三、只记这几招就够了

各家工具的命令很多，而且更新很快。日常维护里真正高频的只有下面几类，思路在各工具之间是相通的：

招式 作用 在哪些工具里
/init 扫描仓库，生成项目说明初稿 Claude Code（CLAUDE.md）、Codex（AGENTS.md）
/clear 换任务时清空上下文 Claude Code
/compact 长会话压缩成摘要，继续干 Claude Code、Codex
Shift+Tab 切换到 Plan 模式，只读出计划 Claude Code、Cursor
@文件 精确把某个文件放进上下文 Claude Code、Cursor 等
/review 审查当前未提交的改动 Codex（Claude Code 对应 /code-review）
claude -p / codex exec 无交互运行，适合脚本和 CI Claude Code、Codex

另外两个值得记住的按键：Claude Code 里按 Esc 可以随时打断、纠正方向；连按两次 Esc（或用 /rewind）可以回退到之前的检查点。

其中最被低估的是 /clear。官方文档列出的两个高频失败模式都和它有关：一是“大杂烩会话”，一个会话里先做 A、又问 B、再回到 A，上下文全是无关信息；二是“反复纠正”，错了改、改了还错，上下文里堆满失败的尝试。处理办法一样：纠正两次还不对，就 /clear，把学到的教训写进一个更好的初始提示，重新开始。

四、规范：让团队都能放心用

  • 规则文件进仓库。 AGENTS.md / CLAUDE.md / .cursor/rules/ / .github/copilot-instructions.md 和代码一起评审、一起演进。个人偏好放本地文件（例如 CLAUDE.local.md），不要污染团队规则。
  • 一个任务一个分支。 Agent 的改动永远在分支上，经过 PR 合并；不要让它直接推主干。
  • 测试先行。 修 Bug 先有失败的测试，重构先有锁住行为的测试。
  • 小 diff。 一个 PR 只解决一个问题，审得完才合得进。
  • 密钥不进上下文。 不要把 .env、令牌、生产凭据贴进对话；高风险命令（删数据、改权限、推生产）保持需要人确认，不要为了省事全局放开。Codex 的 --sandbox / --ask-for-approval、Claude Code 的 /permissions 就是用来划这条线的。
  • 审的是证据。 没有测试输出、没有截图的“已完成”，等于没完成。

五、可直接复制的提示模板

理解代码：

先不要修改任何文件。阅读 src/auth/，告诉我：登录请求从哪里进入、
经过哪些函数、会话存在哪里。每个结论标出文件和行号。

修 Bug：

问题：<粘贴报错 / 日志>。
先写一个能复现它的测试，运行并确认它失败；然后修复根因，
不要靠吞掉异常来消除报错。最后运行全部测试，把命令和输出贴给我。

重构：

目标：把 OrderService 中的价格计算拆成独立模块，行为保持完全不变。
先确认现有测试覆盖了价格计算，不够就先补；然后分步修改，
每一步都运行测试。不要改动和价格计算无关的代码。

审查：

以资深评审的身份审查当前分支相对 main 的改动：找出行为变化、
缺失的测试、可以更简单的写法。只列问题，不要动手改。

六、两条成长路线

新手路线：一个会话，一件事，每一步都看 diff。 头两周不追求快，追求“看得懂”。固定按“探索 → 计划 → 小步实现 → 跑检查 → 读 diff → 提交”的顺序走；每次被 Agent 坑了，就把教训补进规则文件。把 Agent 当作一个能干但会想当然的新同事：它干活，你验收。Claude Code 团队还推荐把输出风格切到“解释型 / 学习型”，让它在改动时讲清楚为什么——这是读懂一个陌生仓库最快的方式之一。

中高级路线：并行、复用、自动化。

  1. 并行。 Claude Code 团队公认最大的提效点，是同时开 3–5 个 git worktree，每个跑一个独立会话，做互不相关的任务（Claude Code 自带 claude -w <名字> 直接在 worktree 里开会话）。前提是任务真的能拆开，而且你审得过来——第五章会细讲这背后的代价。
  2. 复用。 一天里做两次以上的事，就做成自定义命令或 Skill，提交进仓库给全队用（Claude Code 放在 .claude/skills/ 或 .claude/commands/）。需要专门角色时定义子 Agent（.claude/agents/），比如只读的代码评审员；子 Agent 有独立上下文，还能让主会话保持干净。
  3. 连接。 用 MCP 把 issue 系统、日志、浏览器接进来，让 Agent 自己拿证据，而不是你复制粘贴。
  4. 确定性的关卡。 规则写在提示里，Agent 可能忘；写进 hooks 就每次都执行，比如每次编辑后自动跑格式化和 lint。
  5. CI 里的 Agent。 用 claude -p 或 codex exec 在流水线里做第一轮评审，或者把一个 issue 直接指派给 Copilot 的编码 Agent，让它开 PR 回来给你审。

两条路线的终点是同一个：你花在“写”上的时间越来越少，花在“定义问题和验收结果”上的时间越来越多。Karpathy 的提醒值得一直记着——这些模型的错误已经不是语法错误，而是一个有点马虎、有点急的初级工程师会犯的概念性错误。只要你守住验证这一关，它就是一个永远不累的帮手；一旦放掉这一关，它就会自信地把错误放大。
