为什么多 Agent：用并行换时间，代价是 token 与审阅

对应图 #29 · 第五章「多 Agent 编程」

单个 Coding Agent 一次只能做一件事。当任务可以拆成彼此独立的部分时，同时运行多个 Agent 就能用并行换时间。但并行不是免费的：每个 Agent 都消耗 token，每份产出都需要人审阅。多 Agent 编程的核心问题，就是这笔账什么时候划算。

这一篇先讲收益从哪里来，再讲代价，最后给出一个判断框架。

一、收益来自哪里？

收益一：并行。 最直观的一点。三个彼此独立的子任务，串行做要三份时间，并行做只要一份（加上拆分和合并的开销）。

收益二：上下文隔离。 这一点更不明显，但同样重要。第四章讲过，上下文越长，模型的注意力越分散。一个 Agent 先调研支付模块、再调研用户模块、再写代码，到写代码时上下文里已经塞满了调研的中间结果。如果让两个子 Agent 分别调研，各自只把结论交回来，主 Agent 的上下文就是干净的。

Anthropic 的多 Agent 研究系统正是这样工作的：子 Agent 在各自的上下文窗口中并行探索问题的不同方面，再把最重要的信息压缩后交给主 Agent。他们的内部研究评测显示，多 Agent 系统比单 Agent 高出 90.2%；在复杂查询上，并行化把研究时间缩短了最多 90%。

二、代价是什么？

代价一：token。 同一篇文章给出了一组数字：Agent 的 token 用量约为普通聊天的 4 倍，多 Agent 系统约为 15 倍。而且他们发现，token 用量本身就解释了 80% 的性能差异。换句话说，多 Agent 效果好，很大程度上是因为它花了更多 token 去思考和探索。这不是坏事，但意味着它是一种「花钱买质量和时间」的手段，而不是免费的午餐。

代价二：编码任务天然更难并行。 Anthropic 明确指出：大多数编码任务中真正可并行的部分比研究任务少，而且 LLM Agent 还不擅长实时协调和委派。研究任务（「调研五家竞品的定价策略」）天然可以拆成五份独立的工作；编码任务的各部分常常紧密耦合：改了接口，调用方就要跟着改。需要所有 Agent 共享同一上下文、或者 Agent 之间依赖很多的任务，目前不适合多 Agent。

代价三：人的审阅成为新瓶颈。 X 上分享 Orca 用法的开发者总结了多开之后会撞上的四件事：

  1. 跑不起来：新副本缺依赖和密钥。
  2. 盯不过来：分不清哪个在干活、哪个在等确认。
  3. 看不过来：生成越来越快，瓶颈变成了验收。
  4. 被绑住：被一家厂商的额度绑住。

第三条最根本。回到第四章的阿姆达尔定律：三个 Agent 并行，编码时间可能缩短到三分之一，但审阅时间变成了三倍。如果审阅本来就是瓶颈，多 Agent 只会让队列更长。

三、算一笔账

假设一个需求包含三个独立模块，单 Agent 每个模块要 1 小时，人审阅每个模块要 20 分钟。

  • 单 Agent 串行：编码 3 小时 + 审阅 1 小时 = 4 小时，token 花费 1 份（记为 T）。
  • 三 Agent 并行：编码约 1 小时 + 审阅仍是 1 小时（审阅三份一样多）= 2 小时，token 约 3T。

时间省了一半，但审阅时间没有减少，成了总时间中占比最大的部分。如果这三个模块并不独立，而是需要在中途反复对齐接口，并行的收益还会被协调成本吃掉。

这个账本告诉我们：多 Agent 的收益上限，取决于任务的可并行程度和审阅能力。

四、判断框架

值得用多 Agent：

  • 子任务彼此独立：不同模块、不同页面、前后端分头审查。
  • 改错代价高，值得多个方案对比（见第 3 篇「赛跑」）。
  • 信息量超出单个上下文：大规模调研、代码库探索。

别用：

  • 小改动、文案调整。
  • 改动高度耦合，必须在同一上下文里协调。
  • 还没有自动化验证，审阅能力跟不上。

最后一条值得强调：第四章的分层验证，是多 Agent 的前提。 没有自动化验证，每多一个 Agent，就多一份要人从头审的产出。

前述开发者引用一篇评测的说法：赛跑「省下的是来回重试的时间，额度照付三份」，所以只在支付、权限、数据迁移这类改错了很麻烦的地方这么做。

五、这一路是怎么来的

  • 2023 MetaGPT、ChatDev、AutoGen：早期多 Agent 软件开发框架，探索让不同角色的 Agent 协作。
  • 2023 多 Agent 辩论：多个模型实例多轮辩论，提升推理能力和事实性。
  • 2025 Anthropic 多 Agent 研究系统：主 Agent 规划，并行派生子 Agent。
  • Claude Code / Codex / Cursor 的子 Agent：每个子 Agent 在自己的上下文窗口中工作，把结果返回给主 Agent。多 Agent 从研究框架变成了日常工具的内置功能。

六、常见误区

  • 「多 Agent 一定更快。」 取决于任务可并行的程度，协调和审阅都有成本。
  • 「token 便宜，不用算。」 15 倍的消耗在规模化后非常可观。
  • 「Agent 多了可以少看代码。」 产出越多，越需要自动化验证和更好的审阅工具。
