分层验证：让 Agent 先过机器的关，再来找人

对应图 #25 · 第四章「当前如何做 AI 编程」

概述

当 Agent 的产出速度远超人的审阅速度时，人就成了瓶颈。解决办法不是让人看得更快，而是让机器先把能判断的都判断掉，只把机器无法可靠裁决的问题留给人。阿里巴巴实践手册把这称为「分层验证体系」，并认为「我们的主战场在验证与环境」。

核心机制

三层反馈（据阿里巴巴实践手册）：

层级 内容 用途
秒级 编译、类型检查、单元测试 高频自主迭代
分钟级 集成测试、契约测试、浏览器自动化 覆盖更真实的行为
人工 业务价值、用户体验、伦理边界 机器无法可靠裁决的部分

金字塔越往下越快、越便宜、越频繁；越往上越慢、越贵、越少。Agent 应该在底层循环中自我纠错，只有通过了下层，才进入上层。

为什么有效？ Anthropic 指出 Agent 每一步都需要从环境获得「真实反馈」来评估进展。DeepSeek-R1 在训练中也明确只用规则奖励（答案核对、编译和测试），因为神经网络奖励模型容易被钻空子。同样的道理适用于使用阶段：可执行的检查是客观信号，模型的自我评价不是。

测什么比测多少更重要。 手册中千问团队的经验：测试重点覆盖需求边界、关键分支和已知故障模式，而不是单纯追求覆盖率。他们发现可靠性往往不是单点问题：并发场景下 Agent 沙箱重复创建，需要保证的不只是接口层幂等，还包括请求入口、数据库事务、消息发布和消费执行共同形成的「链路幂等」。

工程实践与数字

为 Agent 搭建端到端测试环境。 一位开发者在 X 上分享了四件事：

  1. 让 Agent 熟悉环境：一键启动测试环境、创建测试数据，明确版本、测试账号和权限，并提供清理与重置能力。
  2. 让 Agent 能操作业务系统：通过浏览器、API 或 CLI 执行真实业务流程。
  3. 让 Agent 方便地查库表和日志：只读数据库 MCP 确认落库结果，日志 Skill 和 Trace 查询链路状态。
  4. 把繁琐但稳定的流程写成脚本和 Skill。

他的结论是：AI 很擅长写测试用例，但没有端到端环境时，上线后仍会遇到预期之外的错误。

成效。 千问用增团队 2026 年 5 月至 8 月的纵向对比：平均交付周期缩短一半，千行代码缺陷率下降 70%，变更失败率下降 90% 以上。手册的解读指出，质量指标改善幅度大于速度指标，说明主要收益来自验证机制而非生成速度。

人审阅什么。 前述开发者不再逐行阅读所有生成的代码，而是主要看测试结果和核心业务逻辑，前提是每次 MR 范围足够小，并逐步验证完整业务路径。

常见误区

  • 「覆盖率高就安全。」 追求覆盖率会让 AI 生成大量无意义断言，覆盖故障模式才是关键。
  • 「让另一个模型审查就算验证。」 模型审查是补充，不能替代可执行的检查。
  • 「人工审查越多越安全。」 人的注意力有限，应集中在机器无法判断的部分。
