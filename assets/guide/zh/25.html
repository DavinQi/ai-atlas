分层验证：让 Agent 先过机器的关，再来找人

对应图 #25 · 第四章「当前如何做 AI 编程」

当 Agent 的产出速度远超人的审阅速度时，人就成了瓶颈。解决办法不是让人看得更快，而是让机器先把能判断的都判断掉，只把机器无法可靠裁决的问题留给人。阿里巴巴实践手册把这称为「分层验证体系」，并说「我们的主战场在验证与环境」。

一、先算一笔注意力账

假设一位工程师同时指挥三个 Agent，每个 Agent 一天产出 5 个 MR，每个 MR 平均改 300 行。一天就是 4,500 行代码。认真审阅 4,500 行，一个人一天做不完，更不用说还要做别的工作。

于是只剩两个选择：要么审阅流于形式（看一眼就点通过），要么人成为瓶颈（Agent 产出堆在队列里）。按上一篇阿姆达尔定律的说法，审阅就是新的「不可加速部分」。 分层验证的思路是：把审阅工作中机器能做的那部分拿走，让人只看真正需要人判断的东西。

二、三层反馈

据阿里巴巴实践手册：

层级 内容 用途
秒级 编译、类型检查、单元测试 高频自主迭代
分钟级 集成测试、契约测试、浏览器自动化 覆盖更真实的行为
人工 业务价值、用户体验、伦理边界 机器无法可靠裁决的部分

这像一个金字塔：越往下越快、越便宜、越频繁；越往上越慢、越贵、越少。Agent 应该在底层循环中自我纠错，只有通过了下层，才进入上层。

一次修改走过三层的样子。 Agent 改了一个函数签名：

  1. 秒级：类型检查立刻报出三处调用方参数不匹配。Agent 修正，重跑，十几秒内完成。人完全不知道发生过这件事。
  2. 分钟级：集成测试发现下游服务的契约测试失败，因为返回字段名变了。Agent 加了兼容字段，重跑通过。
  3. 人工：人打开 MR 时，看到的是一个已经编译通过、测试全绿、契约兼容的变更。人只需要判断：这个改动的业务意义对吗？兼容字段要保留多久？

如果没有前两层，这些问题都会落到第三层，由人一个个发现。

三、为什么可执行的检查如此重要？

Anthropic 指出，Agent 每一步都需要从环境获得「真实反馈」来评估进展。DeepSeek-R1 在训练中也明确只用规则奖励（答案核对、编译和测试），因为神经网络奖励模型容易被钻空子。同样的道理适用于使用阶段：可执行的检查是客观信号，模型的自我评价不是。 模型说「我检查过了，没有问题」，这句话本身也是生成出来的。

四、测什么比测多少更重要

追求覆盖率是一个常见陷阱。让 AI「把覆盖率提到 90%」，它很擅长做到：生成大量调用函数、断言返回值不为空的测试。覆盖率上去了，但这些测试几乎什么都没保护。

手册中千问团队的经验是：测试重点覆盖需求边界、关键分支和已知故障模式，而不是单纯追求覆盖率。他们还发现，可靠性往往不是单点问题。例如在并发场景下，Agent 沙箱被重复创建。要防止这类问题，需要保证的不只是接口层幂等，还包括请求入口、数据库事务、消息发布和消费执行共同形成的「链路幂等」。单元测试只测接口，就测不出这种跨环节的问题。

五、为 Agent 搭建端到端测试环境

一位开发者在 X 上分享了四件事：

  1. 让 Agent 熟悉环境：一键启动测试环境、创建测试数据，明确版本、测试账号和权限，并提供清理与重置能力。
  2. 让 Agent 能操作业务系统：通过浏览器、API 或 CLI 执行真实的业务流程。
  3. 让 Agent 方便地查库表和日志：用只读数据库 MCP 确认落库结果，用日志 Skill 和 Trace 查询链路状态。
  4. 把繁琐但稳定的流程写成脚本和 Skill。

他的结论是：AI 很擅长写测试用例，但没有端到端环境时，上线后仍会遇到预期之外的错误。他自己不再逐行阅读所有生成的代码，而是主要看测试结果和核心业务逻辑，前提是每次 MR 范围足够小，并逐步验证完整的业务路径。

六、效果

千问用增团队 2026 年 5 月至 8 月的纵向对比：平均交付周期缩短一半，千行代码缺陷率下降 70%，变更失败率下降 90% 以上。手册的解读是：质量指标的改善幅度大于速度指标，说明主要收益来自验证机制，而不是生成速度。这与阿姆达尔定律的预期一致：交付周期只缩短了一半，而不是像代码生成那样快好几倍；但质量的提升，是验证体系直接带来的。

七、常见误区

  • 「覆盖率高就安全。」 追求覆盖率会让 AI 生成大量无意义的断言，覆盖故障模式才是关键。
  • 「让另一个模型审查就算验证。」 模型审查是有益的补充，但不能替代可执行的检查。
  • 「人工审查越多越安全。」 人的注意力有限，应集中在机器无法判断的部分。审查太多，反而每一处都看不仔细。
