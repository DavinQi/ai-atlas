多人 + 多 Agent：人定义与审阅，数字员工执行

对应图 #33 · 第五章「多 Agent 编程」

概述

当不只一个人、而是一个团队同时与多个 Agent 协作时，问题就从工具变成了组织：谁定义任务？谁审阅？Agent 的身份和权限如何管理？阿里巴巴实践手册中的 AIDC 数字投手团队经历了「超级个体 → 数字员工 → 云上 Scrum」三个时期，是这个问题的一个真实样本。

核心机制

1. 超级个体的瓶颈。 据手册记录，团队统一使用一款主流 Agent 工具后，单人指挥 3～5 个会话工作成为常态，夜间也能完成部分长程任务，体感上一人能干两到三人的活，帮助团队完成了首版 MVP。但很快出现了问题：

  • 消化障碍：消耗大量 token 产出的中间产物，理解、评审和应用很难靠人完成；和同事沟通方案时，同事也讲不清设计，只能把问题抛给 Agent。
  • 复用障碍：一个任务交付后，经验很难被他人复用。

2. 数字员工。 手册把 Agent 视为企业系统中的独立行动主体：平台过去只需回答「这个人有没有权限」，现在必须回答「哪个 Agent、在什么运行时、代表哪个用户、基于哪个任务、访问哪个资源、做什么动作、是否需要人批准」。人与 Agent 协同大致经历三个阶段，本质是不断外移信任边界：

阶段 信任边界 人的职责
本地辅助 人 + 本地工具 提供上下文、批准命令、检查结果
云端自主 人 + 云端运行时 + 仓库 设定目标、检查 MR、关键审批
多 Agent 团队 主 Agent + 专家 Agent + 多系统 设计协作流程、治理边界、承担最终责任

手册提醒，用「实习生」理解 Agent 只能用一半：Agent 需要导师、职责、权限边界和 Review，但它没有职业伦理和隐含常识，治理还要靠机器可执行的护栏。

3. 职责重新划分。 数字投手团队的结论是：系统负责状态、权限、规则等高确定性事务；AI 负责分析、生成和跨步骤的长程执行；人负责目标设定、关键决策、风险取舍和最终责任。交付单元从「人和人协作完成任务」转向「人定义目标与验收标准、数字员工分工执行」。

工程实践与数字

  • 给 Agent 独立身份：手册分析，复用人的账号会让审计分不清是人还是 Agent 操作；复用服务账号会看不清谁负责、谁授权、谁能停用。
  • 审阅是团队级瓶颈：X 上的开发者经验是保持每个 MR 足够小，人工 Review 聚焦业务逻辑和测试结果是否足以支撑交付。
  • 把产出变成可复用资产：手册中的团队建了两条「云上 Scrum」供给线：经验 Loop 由两个数字员工分别负责发现和上线策略，策略交付周期从约 10 天缩短至 2 天；手脚 Loop 把线上失败轨迹转化为能力建设需求，约 80% 的核心能力实现 Skill 化。
  • 数字员工的边界：手册明确，增长机会的发现仍高度依赖人的业务理解；目标设定、业务门槛、发布门禁和高风险决策仍需人承担。

常见误区

  • 「Agent 越多，需要的人越少。」 定义、审阅和治理的工作量会随 Agent 数量上升。
  • 「用个人账号跑 Agent 最方便。」 审计和责任会变得模糊。
  • 「数字员工能替代组织共识。」 手册指出，它更适合高质量执行那些已经被想清楚、形成明确标准的工作。
