多 Agent 与 Harness 闭环：分工之外，更重要的是验证与回炉

对应图 #15 · 第二章「Agent 设计原理与范式」

当一个 Agent 的上下文装不下、时间不够用时，很自然的想法是：多找几个 Agent 分工。图 #15 上半部分画了三种常见的分工形态：编排者—工作者、流水线、生成者—评审者。下半部分画的是更重要的东西：一个 Harness 闭环。任务进入规划，规划交给工具执行，执行结果必须经过验证（测试、lint、类型检查），不通过就把报错和测试输出带回上下文重试，通过了才提交 PR。整个执行和验证过程被框在沙箱里。

这张图想传达的核心观点是：多 Agent 的价值，必须在一个受控的闭环里才能稳定兑现。 这里的 Harness，指的是包住模型的那层工程：工具、权限、上下文管理、验证规则与停止条件。下面先看三种分工形态，再看 Harness 为什么比分工本身更关键。

一、三种分工形态

编排者—工作者（orchestrator-workers）。 在 Anthropic 的模式库里，中心 LLM 动态拆解任务、分派给工作者 LLM，再综合结果。它和简单的并行化不同：子任务不是预先写死的，而是编排者看了输入后才决定。这特别适合「事先不知道要改哪些文件」的编码任务：编排者读完 issue 和代码结构后，才决定派一个工作者改 API 层、一个改数据层、一个补测试。

流水线（pipeline）。 任务按固定顺序流经几个专门的 Agent：比如需求分析 → 编码 → 测试。MetaGPT 把软件公司的标准作业流程（SOP）编码进多 Agent 协作，让产品经理、架构师、工程师等角色按流程交接产物；ChatDev 则用对话推进各阶段。流水线的好处是每个环节职责单一、产物可检查；风险是上游的错误会一路传到下游。

生成者—评审者（debate / review）。 一个 Agent 生成，另一个评审并给出反馈，循环改进，对应 Anthropic 的「评估者—优化者」模式。多 Agent 辩论的研究也发现，让多个模型实例就同一问题多轮辩论，可以提升推理和事实准确性。AutoGen 等框架把这类对话式协作做成了通用的编程接口。

二、一个公开的真实案例

Anthropic 公开了他们多 Agent 研究系统的做法和数据，是目前少有的一手资料：

  • 结构：主 Agent 规划研究过程，再创建多个并行的子 Agent 同时搜索；每个子 Agent 在自己的上下文窗口里探索问题的一个方面，把最重要的信息压缩后交回主 Agent。
  • 效果：以 Claude Opus 4 为主 Agent、Claude Sonnet 4 为子 Agent 的系统，在其内部研究评测上比单 Agent 的 Claude Opus 4 高出 90.2%。
  • 原因：在他们的分析中，token 用量本身就解释了 80% 的性能差异，工具调用次数和模型选择是另外两个因素。换句话说，多 Agent 的主要作用是让系统能「花更多 token」：每个子 Agent 都有一个干净的上下文，可以并行地读更多资料。
  • 代价：Agent 的 token 用量约为普通聊天的 4 倍，多 Agent 系统约为 15 倍。

这组数据给了一个很清晰的判断标准：多 Agent 适合「可高度并行、信息量超出单个上下文、需要大量工具调用」的任务，而且任务价值要高到能覆盖约 15 倍的成本。

三、为什么编码任务要格外谨慎？

同一篇文章明确指出两点限制：需要所有 Agent 共享同一上下文、或 Agent 之间依赖很多的领域，目前不适合多 Agent；而且大多数编码任务里真正可以并行的部分比研究任务少，LLM Agent 也还不擅长实时协调和委派。

道理不难理解。研究任务中，「查 A 公司的财报」和「查 B 公司的财报」互不影响；编码任务中，改了接口签名，所有调用方都要跟着改，两个 Agent 各自改一半，合并时就会冲突。第五章会讲到，工程上常用 git worktree 给每个 Agent 一份隔离的工作副本，正是为了把这种依赖显式化。

四、Harness：把「可能对」变成「验证过的对」

无论是一个 Agent 还是一群 Agent，模型的输出本质上都是「可能对」。Harness 的作用，是把它变成「验证过的对」。图中闭环的每一步都有讲究：

任务 / Spec。 入口必须有清晰的目标和验收标准。「修好登录 bug」不是好任务；「用户用过期 token 登录时返回 401，补充对应的单测，现有测试全部通过」才是。验收标准就是后面验证环节的依据。

沙箱 / 受控环境。 工具执行和验证都在隔离环境里进行：独立的容器或工作目录，按需开放网络和文件系统。Agent 犯错的代价被限制在沙箱之内。

验证：用客观信号，而不是主观判断。 Anthropic 强调 Agent 每一步都要从环境获得真实反馈。在编码场景中，最可靠的「评估者」是测试、类型检查、lint 和构建结果，而不是另一个模型的意见。模型评审可以补充（比如检查可读性），但不能替代可执行的检查。

失败回炉。 验证失败时，把报错信息和测试输出原样带回上下文，让模型据此修正。这就是上一篇 Reflection 范式的工程化版本：外部信号越具体，下一轮修正越准。

停止条件。 必须设最大迭代次数和预算上限。连续失败若干次后，升级给人，而不是无限循环下去。

状态与错误累积。 Anthropic 还提醒，Agent 是有状态的，错误会累积：一个早期的错误决定会影响之后所有步骤。他们在更新系统时采用「彩虹部署」逐步切流，避免打断正在运行的长任务；评估时更关注最终状态是否正确，而不是逐轮分析每一步。

五、一份最小 Harness 清单

组成 作用 编码场景的例子
任务说明与验收标准 定义「做完」 issue + 需要通过的测试
隔离的执行环境 限制出错范围 容器、独立 worktree
自动化验证 提供客观反馈 单测、类型检查、lint、构建
反馈回路 让失败变成信息 把报错原文放回上下文
停止与升级规则 防止失控 最多 N 轮，超限转人工
完整日志 便于审计和复盘 每次工具调用的输入输出

六、三个常见误解

  • 「Agent 越多越快。」 并行收益取决于任务能否拆成独立部分，协调本身有成本，token 消耗也成倍增加。
  • 「让另一个模型审查就够了。」 模型审查可以补充，但可执行的测试和检查提供的是客观信号。
  • 「多 Agent 是默认架构。」 它是单 Agent 不够用时的升级手段。先把单 Agent 的 Harness 做扎实，收益往往更大，见下一篇的决策树。
