多 Agent 与 Harness：在受控闭环里迭代到验证通过

对应图 #15 · 第二章「Agent 设计原理与范式」

概述

当单个 Agent 的上下文或时间不够用时，可以让多个 Agent 分工；但多 Agent 的价值必须在一个受控的闭环（harness）里才能稳定兑现：任务被拆分、执行、验证，不通过就带着反馈回炉，直到验证通过或升级给人。这里的 Harness 指包住模型的那层工程：工具、权限、上下文管理、验证与停止条件。

核心机制

1. 编排者—工作者模式。 Anthropic 的模式库中，中心 LLM 动态拆解任务、分派给工作者 LLM，再综合结果。它与并行化的区别在于子任务不是预先定义的，而是由编排者根据输入决定，适合「无法预知需要改哪些文件」的编码任务。

2. Anthropic 多 Agent 研究系统。 主 Agent 规划研究过程，再创建并行的子 Agent 同时搜索；子 Agent 在各自的上下文窗口中探索问题的不同方面，把最重要的信息压缩后交给主 Agent。公开数据：

  • 以 Claude Opus 4 为主 Agent、Claude Sonnet 4 为子 Agent 的系统，在其内部研究评测上比单 Agent 的 Claude Opus 4 高出 90.2%。
  • 在其分析中，token 用量本身就解释了 80% 的性能差异，工具调用次数和模型选择是另外两个因素。
  • Agent 的 token 用量约为普通聊天的 4 倍，多 Agent 系统约为 15 倍。

3. 闭环验证。 Anthropic 强调 Agent 每一步都要从环境获得真实反馈。评估者—优化者模式让一个 LLM 生成、另一个给出评估和反馈，循环改进，适用于有明确评价标准的任务。在编码场景中，最可靠的「评估者」是测试、类型检查和构建结果，而不是另一个模型的主观判断。

4. 状态与错误累积。 同一篇文章指出 Agent 是有状态的，错误会累积；他们用「彩虹部署」逐步切流，避免更新打断正在运行的 Agent；评估上更关注最终状态，而不是逐轮分析。

工程实践与数字

  • 适合多 Agent 的任务：可高度并行、信息量超出单个上下文、需要调用大量工具。Anthropic 明确指出，需要所有 Agent 共享同一上下文或 Agent 之间依赖很多的领域，目前不适合多 Agent；大多数编码任务可真正并行的部分比研究任务少，而且 LLM Agent 还不擅长实时协调和委派。
  • 成本核算：约 15 倍于聊天的 token 消耗意味着只有高价值任务才划算。
  • Harness 的最小组成：任务说明与验收标准、隔离的执行环境、自动化验证、最大迭代次数、失败时升级给人的规则。

常见误区

  • 「Agent 越多越快。」 并行收益取决于任务能否拆成独立部分，协调本身有成本。
  • 「让另一个模型审查就够了。」 模型审查可以补充，但可执行的测试和检查提供的是客观信号。
  • 「多 Agent 是默认架构。」 它是在单 Agent 不够时的升级手段，见下一篇的决策树。
