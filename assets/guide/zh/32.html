两种打法：赛跑挑最优，流水线分工协作

对应图 #32 · 第五章「多 Agent 编程」

多 Agent 编程有两种基本打法：

  • 赛跑（race）：同一个任务交给多个 Agent 同时做，挑最好的结果。
  • 流水线（pipeline）：一个任务拆成不同阶段或不同部分，由不同 Agent 分工完成。

两者分别对应 Anthropic 模式库中「并行化」的两种变体：投票（voting），同一任务多次运行以获得多样化输出；分段（sectioning），把任务拆成独立子任务并行运行。它们解决的是不同的问题：赛跑对付「难」，流水线对付「大」。

一、赛跑：用多样性降低风险

场景。 线上支付偶发重复扣款，原因不明。这是一个典型的「难」问题：改动可能不大，但改错了代价很高。

做法。 Orca 官方文档把「让三个 Agent 同时修同一个 bug，挑出赢家」列为典型用法。三个 Agent 各自在独立的 worktree 里分析和修复，完成后人来比较。

它为什么有效？ X 上分享 Orca 用法的开发者转述了官方对这一打法的解释：不同的 Agent 犯不同的错。 三个都改成一样的地方，大概率是对的；三个各改各的地方，就是这个问题真正难的部分。等于花一份等待时间，拿到三份答案和一张「哪里有分歧」的地图。

这张「分歧地图」常常比任何一份答案都更有价值。假设三个 Agent 都在扣款回调里加了幂等检查（一致），但对「幂等键用订单号还是支付流水号」各有选择（分歧）。一致的部分可以放心采纳；分歧的部分，恰好就是人需要投入注意力的地方。

学术上的对应。 Codex 论文发现，对同一问题重复采样是获得正确解的有效策略：单次采样解决 28.8%，每题 100 次采样时达到 70.2%。多 Agent 辩论研究则表明，多个模型实例提出并辩论各自的答案，可以提升推理能力和事实准确性。赛跑结合了这两种思路：多次采样增加命中正确答案的机会，比较分歧则帮助识别哪个是对的。

注意不同厂商的价值。 如果三个 Agent 都是同一个模型，它们的错误往往是相关的，同一个盲点可能三个都有。用不同厂商的 Agent（这也是 Orca 不绑定模型的意义之一）能让错误更独立，「一致」也就更有说服力。

赛跑不会自动合并。 三份结果各对一半时，可以让获胜的 Agent 参考另一份改动再改一轮，或手动挑选好的部分。

二、流水线：用分工处理复杂任务

场景。 开发一个新的「会员积分」功能，涉及需求、设计、后端、前端和测试。这是一个「大」问题：每一步不一定难，但总量超出了一个上下文能舒适容纳的范围。

做法。 MetaGPT 把标准作业流程（SOP）编码进提示序列，采用流水线范式为不同 Agent 分配角色，把复杂任务拆成多个 Agent 协作的子任务，并让具备领域专长的 Agent 校验中间结果以减少错误。一个常见的编码流水线：

需求澄清 → 方案设计 → 编码 → 测试 → 交叉审查 → 集成

交接靠文件，不靠对话。 流水线最大的风险是交接时丢失信息。解法是让每一阶段产出明确的共享产物：Spec、CONTEXT.md、接口定义、测试结果。下游 Agent 读这些文件，而不必重读上游的全部对话。这也是第四章 Spec 驱动的另一个价值：Spec 就是流水线的「接口」。

交叉审查。 另一位开发者的做法是：编码 Agent 完成后，引入其他厂商的 Agent 做对抗性审查，问题统一反馈给主编码 Agent 修复并重新验证。这是流水线中「校验中间结果」的一个具体形式，同样利用了「不同的 Agent 犯不同的错」。

三、怎么选？

维度 赛跑 流水线
对付的问题 难：改错代价高的单点问题 大：可拆分的大任务
成本 N 倍 token 按阶段累加
人的工作 比较、挑选、合并 定义接口与验收
主要风险 审阅负担成倍增加 交接丢失信息

两者也可以组合：在流水线里，对风险最高的那一个环节（比如支付回调的修改）单独做一次赛跑。

赛跑只用在关键处。 前述开发者的建议是：只在支付、权限、数据迁移这类改错了很麻烦的地方赛跑，改文案就别这么干。

四、常见误区

  • 「赛跑越多越好。」 收益递减，而成本线性增长，审阅负担也成倍增加。从 1 个到 3 个，多出的「分歧地图」很有价值；从 3 个到 10 个，多出来的主要是审阅工作。
  • 「流水线角色分得越细越好。」 每次交接都可能丢失信息。Anthropic 也提醒，多 Agent 间依赖多的任务目前不适合。
  • 「三个 Agent 结果一致就一定对。」 一致性提高了可信度，但仍需测试验证，尤其当它们用的是同一个模型时。
