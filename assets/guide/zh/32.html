编排层：一个 Agent 当项目经理，人只守关卡

对应图 #32 · 第五章「多 Agent 编程」

概述

当同时运行的 Agent 多到人盯不过来时，就需要编排层：让一个 Agent 担任「项目经理」，负责拆解任务、分派给工作者 Agent、跟踪进度、汇总结果；人只在关键的决策关卡介入。这正是 Anthropic 所说的「编排者—工作者」模式：中心 LLM 动态拆解任务、委派给工作者 LLM 并综合结果，适合无法预知子任务的编码任务。

核心机制

1. 子 Agent：编排的基本单元。 主流工具都已内置：

  • Claude Code：子 Agent 是带 YAML 前置元数据的 Markdown 文件；每个子 Agent 在自己的上下文窗口中运行，有自定义系统提示、特定工具权限和独立权限设置。
  • Codex：可以并行派生专门的 Agent，再把结果汇总到一个响应中；当前版本默认启用子 Agent 工作流。
  • Cursor：子 Agent 是主 Agent 可以委派任务的专门助手，每个都在自己的上下文中工作并把结果返回给父 Agent，用于拆解复杂任务、并行工作和保持主会话上下文干净。

2. Orca 的编排层。 Orca 文档把编排描述为结构化的多 Agent 层（实验性功能），核心模型包括：

  • Run：持久的命名空间和协调者收件箱
  • Task：带规格说明、依赖和状态的工作项，可组成 DAG
  • Dispatch：任务在某个终端上的一次执行尝试
  • Message：worker_done、escalation、question、heartbeat 等消息
  • Decision gate：由协调者创建的问题，在决策记录之前阻塞相应任务

工作者的契约包括：无论成败都必须恰好发送一次 worker_done 并注明结果；附上做了什么、发现了什么、还剩什么的摘要；长时间工作时发送心跳；有阻塞问题时通过协调者提问，而不是在本地等待。

3. 人守关卡。 关卡放在不可逆或高风险的步骤上：合并共享组件、数据库迁移、发布。X 上分享 Orca 用法的开发者举例：上线前让一个 Agent 当项目经理，带两个 Agent 分头审查前后端，人只看最后的汇总；数据库迁移那一步设一道关卡，必须人拍板。

工程实践与数字

  • 完成信号要结构化：Orca 要求完成消息同时带任务 ID 和执行 ID，避免过期的重试错误地完成别的任务。
  • 编排者本身也是 Agent：前述开发者指出，Orca 不光给人用也给 Agent 用，Agent 可以自己开新工作区、读别的窗口的报错，派活的「项目经理」就是靠这套能力分配任务、收集结果。
  • 从小处开始：Anthropic 提醒 LLM Agent 还不擅长实时协调和委派，先用两三个工作者、边界清晰的任务试点。

常见误区

  • 「有了编排者，人可以完全退出。」 高风险决策仍需人负责，关卡是设计的一部分。
  • 「编排层越复杂越强。」 每层编排都增加 token 和出错点，按需增加。
  • 「工作者说完成了就是完成了。」 完成要以验证结果为准，而不是 Agent 的自我报告。
