编排层：一个 Agent 当项目经理，人只守关卡

对应图 #32 · 第五章「多 Agent 编程」

当同时运行的 Agent 多到人盯不过来时，就需要编排层：让一个 Agent 担任「项目经理」，负责拆解任务、分派给工作者 Agent、跟踪进度、汇总结果；人只在关键的决策关卡介入。这正是 Anthropic 所说的「编排者—工作者」模式：中心 LLM 动态拆解任务、委派给工作者 LLM 并综合结果，适合无法预知子任务的编码任务。

一、为什么需要编排层？

前两篇里，人自己在做编排：决定开几个 worktree、给每个 Agent 布置什么、什么时候去看结果、怎么合并。三个 Agent 时人还应付得来；十个 Agent 时，人的一整天会被「切窗口、看状态、复制粘贴报错」填满。

编排层的目的，是把「调度」这件事也交给 Agent，让人从调度员变回决策者。这延续了第三章的主线：每一代工具都把一层细节交给机器。

二、子 Agent：编排的基本单元

主流工具都已内置子 Agent：

  • Claude Code：子 Agent 是带 YAML 前置元数据的 Markdown 文件；每个子 Agent 在自己的上下文窗口中运行，有自定义的系统提示、特定的工具权限和独立的权限设置。
  • Codex：可以并行派生专门的 Agent，再把结果汇总到一个响应中；当前版本默认启用子 Agent 工作流。
  • Cursor：子 Agent 是主 Agent 可以委派任务的专门助手，每个都在自己的上下文中工作，并把结果返回给父 Agent，用于拆解复杂任务、并行工作和保持主会话上下文干净。

这些子 Agent 的生命周期通常在一次会话内。更大规模、更长时间的编排，需要更结构化的协调机制。

三、一个结构化编排的例子：Orca

Orca 文档把编排描述为结构化的多 Agent 层（实验性功能），核心模型包括五个概念：

  • Run：持久的命名空间和协调者收件箱。
  • Task：带规格说明、依赖和状态的工作项，可组成 DAG（有向无环图）。
  • Dispatch：任务在某个终端上的一次执行尝试。
  • Message：worker_done、escalation、question、heartbeat 等消息。
  • Decision gate：由协调者创建的问题，在决策记录之前阻塞相应任务。

可以用一个上线前审查来理解它们的关系。X 上分享 Orca 用法的开发者举过这样的例子：上线前让一个 Agent 当项目经理，带两个 Agent 分头审查前后端，人只看最后的汇总；数据库迁移那一步设一道关卡，必须人拍板。映射到上面的模型：

Run: 上线前审查
├─ Task A: 审查前端   → Dispatch 到终端 1 → worker_done
├─ Task B: 审查后端   → Dispatch 到终端 2 → worker_done
├─ Task C: 执行迁移   (依赖 A、B)
│    └─ Decision gate: 「迁移脚本可以执行吗？」 ← 人
└─ 协调者汇总 → 交给人

Task C 依赖 A 和 B，所以构成 DAG；Decision gate 让 C 在人回答之前不会执行。

工作者的契约。 Orca 对工作者有明确的要求：无论成败，都必须恰好发送一次 worker_done 并注明结果；附上做了什么、发现了什么、还剩什么的摘要；长时间工作时发送心跳；有阻塞问题时通过协调者提问，而不是在本地等待。

这些规则看似琐碎，其实都在解决分布式系统的经典问题：

  • 「恰好一次」：防止任务被重复标记完成，或者永远没有完成信号。
  • 完成消息同时带任务 ID 和执行 ID：Orca 这样要求，是为了避免过期的重试错误地完成别的任务。比如某次执行超时被重新派发，旧的那次后来才回报完成，如果只带任务 ID，就会把新执行的结果也覆盖掉。
  • 心跳：让协调者区分「还在干活」和「已经卡死」。
  • 通过协调者提问：避免工作者在本地无限等待，把所有阻塞集中到一个人看得见的地方。

四、人守关卡

关卡应放在不可逆或高风险的步骤上：合并共享组件、数据库迁移、发布。这与第二章的护栏原则一致：可逆的操作可以放手，不可逆的操作必须有人确认。

关卡的价值还在于集中。没有编排层时，十个 Agent 会在十个不同的时间点、在十个窗口里请求确认；有了编排层，确认请求集中到协调者那里，人可以一次性处理。

五、工程要点

  • 编排者本身也是 Agent。 前述开发者指出，Orca 不光给人用，也给 Agent 用：Agent 可以自己开新工作区、读别的窗口的报错，派活的「项目经理」就是靠这套能力来分配任务、收集结果。
  • 从小处开始。 Anthropic 提醒，LLM Agent 还不擅长实时协调和委派。先用两三个工作者、边界清晰的任务试点。
  • 以验证为准。 工作者报告「完成」，只是一个信号；任务是否真的完成，要看测试和检查的结果。

六、常见误区

  • 「有了编排者，人可以完全退出。」 高风险决策仍需人负责，关卡是设计的一部分。
  • 「编排层越复杂越强。」 每一层编排都增加 token 和出错点，按需增加。
  • 「工作者说完成了就是完成了。」 完成要以验证结果为准，而不是 Agent 的自我报告。
