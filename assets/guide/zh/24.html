Spec 驱动：先澄清再动手，约束与假设分开写

对应图 #24 · 第四章「当前如何做 AI 编程」

Agent 写代码越快，需求理解偏差的代价越大：方向错了，写得越多，返工越多。Spec 驱动的做法是先把需求澄清成一份可验证的规格说明，再让 Agent 动手。阿里巴巴实践手册给出了一个关键写法：把「约束」和「假设」分开写。Spec 负责划定「什么算对」的边界，不负责规定实现路径。

一、从一句话需求开始

产品同学提了一个需求：「文档支持生成公开分享链接。」

看起来一句话就说完了。把它直接交给 Agent，它会很快做出一个能用的功能：生成一个随机 URL，任何人打开都能看文档。但这里藏着一串没人说出口的问题：

  • 链接能撤销吗？撤销后已打开的页面怎么办？
  • 有没有有效期？
  • 文档被删除、或者分享者离职了，链接还有效吗？
  • 能看到文档的历史版本和评论吗？
  • 敏感文档是否允许公开分享？谁能开这个开关？
  • 同一文档重复点「生成」，是返回同一个链接，还是生成新的？

手册指出，人在写需求时往往会省略权限边界、并发处理、幂等策略等默认知识，而 AI 缺少这类组织记忆，只能猜测或忽略。「生成公开分享链接」这个简单需求，背后就涉及撤销机制、访问控制和数据一致性等多个决策。这些问题在写代码前回答，成本是几分钟的讨论；上线后才发现，成本可能是一次数据泄露。

二、让 AI 主动追问

手册中团队的做法是：不假设需求是完整的。 让 AI 先读需求和相关代码，主动追问隐含的业务和技术决策，人逐条确认，再把结果沉淀为可追溯的 Spec 和 Tasks，在开发成本最低的阶段暴露风险。

这把模型的一个「缺点」变成了优点：正因为它没有组织记忆，它才会问那些老员工觉得「理所当然」、所以从不写下来的问题。

三、约束 vs 假设：最关键的一刀

Spec 里的内容分两类，必须分开写：

约束 假设
含义 必须满足，否则就是错的 当前认为合理的做法
例子 数据不能出域；接口必须向后兼容；分享链接撤销后 1 分钟内失效 用 Redis 缓存链接；链接用随机 token 而非签名
生命周期 长期保存 可随反馈调整
如何检查 尽可能写成自动检查项 由实现和运行数据验证
Agent 能否改动 不能 可以，但要说明理由

为什么要分开？如果把「用 Redis」和「撤销后 1 分钟内失效」写在同一层级，Agent 会把二者当作同等的硬性要求。实现中发现 Redis 不合适时，它要么硬着头皮用，要么连同真正重要的约束一起「灵活处理」。分开写之后，Agent 知道哪里是红线，哪里可以根据实际情况调整。

四、一份够用的 Spec

综合手册与一线实践，一份够用的 Spec 通常包含：

  1. 要解决的问题与非目标（「本期不支持密码保护」）
  2. 范围与优先级
  3. 约束（能自动检查的尽量写成检查项）
  4. 关键决策及理由
  5. 验收标准（最好能直接转成测试）
  6. 待确认事项

「非目标」常被忽视，却很重要：Agent 有过度设计的倾向，明确告诉它不做什么，比告诉它做什么更能防止范围膨胀。「验收标准」则是 Spec 与测试之间的桥梁：「撤销后访问返回 404」可以直接变成一条测试。

五、澄清要适可而止

Spec 驱动也有走过头的风险。一位开发者在 X 上分享的经验是：用连续追问把目标、约束和取舍问清楚，沉淀到 Spec 或 CONTEXT.md；当剩下的问题已经不会显著改变实现方向和验收结果时，就可以开始开发，不必要求提前规划所有实现细节，否则需求对齐本身又会变成一套很重的流程。他同时提到，Superpowers 这类围绕 Spec 和 TDD 的重型 Skill 会消耗大量 token；模型变强后，一些原本有用的约束和流程正在变成噪声。

一个实用的停止判据：问自己，下一个问题的答案会改变架构或验收标准吗？ 不会，就开始写代码。

六、Spec 在流程中的位置

  • 先规划再执行。 Plan-and-Solve（2023）表明，先规划再执行可以减少漏步骤错误，是「先澄清后动手」在模型层面的对应。
  • Spec 是多 Agent 的共享上下文。 负责实现和负责审查的 Agent 读同一份 Spec，不需要重读之前的全部对话。
  • 验收标准先行。 千问用增团队引入 TDD：先用失败测试固定需求边界，再用最小实现让测试通过，最后在测试保护下重构。
  • 复杂需求拆成可独立验收的 Issue，只有能独立推进的部分才并行（第五章）。

七、常见误区

  • 「Spec 越详细越好。」 把实现路径写死，会剥夺 Agent 根据反馈调整的空间，也会让流程过重。
  • 「需求写清楚是产品经理的事。」 手册的做法是让 AI 主动追问，把澄清前置为团队流程。
  • 「有 Spec 就不需要测试。」 Spec 定义什么算对，测试才能证明做对了。

八、延伸卡：大任务先清零不确定性，再拆卡按波次并行

一句话结论：大任务不能直接让 AI「拆成十几张卡」；先做需求分析清零不确定项，再由人拍板架构并冻结契约，最后按依赖层拆成可独立验收的小卡，按波次并行。

  • 四步＋四闸口：需求分析（A 行为清单／B 不确定与冲突项／C 非功能需求）→ 架构（2–3 方案对比＋契约＋ADR，人选方案）→ 拆卡（先画依赖图再写卡）→ 排波次（同波互不依赖、写死合并顺序）。Q 清单有未决不许出架构，契约未冻结不许拆卡。
  • 颗粒度红线（经验值）：一张卡＝一个可独立验收的行为切片；改动 3–10 个文件、diff 约 150–600 行、人类等价 2–6 小时、上游依赖 0–2 张、只跨 1 个主模块。超限必须在卡面写理由，解释不了就拆。
  • 分层：L0 地基（契约/表/枚举/spike）→ L1 领域 → L2 接口与编排 → L3 联调与补偿；联调单独成卡成波，不塞进接口卡尾巴。
  • 真例：订单/库存/支付下单链路拆 11 张卡（CARD-01 spike 到 CARD-11 全链路联调），L1 三卡并行、L2 两卡并行，同模块同波先合一张再重跑全量。完整版见图 #29 实操手册 §33。
